# 产品反馈闭环

产品负责人 2026-08-29：「是不是需要建立一个前端agent和后端agent交互的skill呢。因为
需要及时反应客户的需求然后修改内容传达给用户。」

这条回路本来就一直在跑，只是散在我的记忆里。写成 Skill 是为了**它每次都一样**。

## 两个 Agent，一条台账

| 谁 | 在哪 | 能做什么 |
| --- | --- | --- |
| **前端 Agent** | 应用右栏的「开发」窗口 | 记他的意见、告诉他有哪些提案在等他、记下他的答复、替他要一份方案 |
| **后端 Agent（我）** | 这个仓库 | 读意见、写提案、**真正改代码**（测试 / commit gate / 独立审查 / 可回滚的提交） |

它们之间只有一个共享物：账户级台账
`%LOCALAPPDATA%\motv\feedback.json`（POSIX：`$XDG_DATA_HOME/motv/`）。

```
items[]      他提的意见            前端写，我读
proposals[]  我给的修改方案         我写（或应用替他要），他在窗口里拍板
  .decision  他的答复 + 他的原话     前端写，我读
```

**永远用工具读写，不要手改这个文件**（它同时被运行中的服务端写）：

```bash
python .claude/tools/read_feedback.py                 # 待处理的意见
python .claude/tools/read_feedback.py --all           # 连处理过的
python .claude/tools/read_feedback.py --proposals     # 提案 + 他的答复
python .claude/tools/read_feedback.py --propose "标题" --body "方案"
python .claude/tools/read_feedback.py --done 3 7      # 标记处理过（不删除）
python .claude/tools/read_feedback.py --json          # 给别的工具吃
```

## 四个时刻

### 1. 开场：先看有没有新东西

`read_feedback.py` + `--proposals`。**先读再问** —— 他已经说过的话，不该再问一遍。

一条意见带着**他在哪一页说的**（前端会把页面、分集、选中的镜头写进 text）。
读到只写着「左边太挤」而没有位置的，是老条目；新的都带位置。

### 2. 他要一份方案（应用里触发的 `dev.request`）

应用会**自己**跑一轮「开发出方案」，产出的方案作为提案落进 `proposals`，标题前面
带着「（开发正在写方案）」直到跑完。那一轮**没有工具**，产出的是文字方案，不是改动。

我这边要做的是**收口**：读那条提案 → 判断它是否可行 → 需要修正就用 `--propose`
写一条更准的，并在正文里说清与自动方案的差别。**不要**把自动方案当成我的承诺。

### 3. 我做完一批 / 我有想法 → 写提案

```bash
python .claude/tools/read_feedback.py --propose "版本行只留最新一版，旧的收起来" \
  --body "现在：版本行一排铺着 v1…v6，占掉大半行
改完：只剩最新那一颗，旁边一个「历史版本 5」，点开才展开
不变：一个版本都不删，随时能切回去
要你定：分集切换要下拉选集器，还是可折叠列表？"
```

写法要求（产品负责人 2026-08-29:「简洁的告诉我改变前后用户能看到的前端变化是什么。
不用解释技术细节」）：

```
现在：版本行一排铺着 v1…v6，占掉大半行
改完：只剩最新那一颗，旁边一个「历史版本 5」，点开才展开
不变：一个版本都不删，随时能切回去
要你定：分集切换要下拉选集器，还是可折叠列表？
```

- **只写他在屏幕上看得到的变化**。不写文件名、函数名、数据结构、实现方式 ——
  他不关心，而且那会把方案变成他读不下去的东西。
- **「不变」那一行不能省**：他最怕「改一个地方，别的悄悄变了」。
- 有歧义就列出要他确认的一两点，不要替他选。
- 一条提案一件事。三件事写三条 —— 他能分别答复。
- 三到六行。长了他不会读完。

### 4. 他拍了板 → 按 verdict 走

| verdict | 我要做的 |
| --- | --- |
| `approved` | 直接实施（立卡 → 实现 → 测试 → 提交）。他已经点头，不要再问一遍 |
| `changes` | **`note` 里那句话是新的需求**。按它改方案再实施；改动大就先写一条新提案 |
| `rejected` | 不做。把它记进任务卡或 Follow-up 说明「他否了，理由是…」，不要静默丢掉 |

实施完成后：`--done <意见号>` 标掉对应的意见，并**写一条新提案**告诉他「做好了、
做成了什么样」—— 那是他在应用里唯一看得到的回执。

## 及时性：会话内盯着台账

他要的是「及时反应」。在一次会话里，用 Monitor 盯住台账的变化，而不是等他再说一次：

```bash
# bash（Monitor 用 bash）
F=~/AppData/Local/motv/feedback.json
until [ "$(stat -c %Y "$F" 2>/dev/null)" != "$STAMP" ]; do sleep 30; done
```

盯到变化就跑一次第 1 步。**不要**为此起后台常驻进程：会话结束它就该结束。

## 这条回路是转圈的，不是单程

产品负责人 2026-08-29：「用户需要修改前端可视化页面的时候，肯定要执行修改的。执行完毕
之后用户刷新页面看到最新UI可能会有新的意见。这是个反复的流程。」「最终改好之后肯定是要
进入实际运用的。」

```
   他提意见 ──▶ 方案（他看得到的前后变化）──▶ 他拍板
       ▲                                        │
       │                                        ▼
   他刷新页面看新 UI ◀── 部署（重启服务）◀── 我实现（测试 / gate / 可回滚提交）
```

**「执行」是这条回路的一环，不是被禁的动作。** 他点了头就去做，做完就上线，别停在方案上
—— 停在那儿等于把工作退回给他（AGENTS.md §1）。

一圈的收尾动作，一个都不能省：

1. **实现**：立卡 → 改 → 跑归属测试 → 提交（可回滚）。
2. **上线**：重启 studio 服务 —— 他刷新看到的必须是刚改完的东西，否则他会拿着旧 UI
   给你新意见（这一天已经发生过一次：他那个标签页跑着部署前的旧代码）。
3. **告诉他**：`--done <意见号>` + 写一条回执提案（同样只写他看得到的变化：
   「改完了：现在你会看到…」）。他在应用里唯一看得到的就是这个。
4. **等下一圈**：他刷新之后多半有新意见 —— 那是这条回路在正常工作，不是返工。

## 三条边界（守的是这条回路本身）

1. **应用不自己改自己的源码。** 改动由**仓库里的开发 Agent**（我）执行 —— 那里有测试、
   commit gate、独立审查、可回滚的提交。让运行中的应用自动改源码会绕开每一道闸，
   而且他写的文字会进提示词，那就成了一条能写仓库的注入面（ADR-0042/0056 的既有姿态）。
   **这不限制「改不改」，只限制「谁来改」。** 应用那一轮只产出方案。
2. **作品的改动不走台账。** 创意、大纲、镜头这些走应用自己的写路径
   （ADR-0089 决策 2b / 动作注册表 `convactions.js`）。台账管的是**应用本身**。
3. **台账里的条目不删。** `--done` 只改状态。他提过的话是证据（第 13 条）。
