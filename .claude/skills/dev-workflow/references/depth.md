# 深度判定 —— 四个变量，取最高的那一档

权威是 [SKILL.md](../SKILL.md) 第 3 环的那张表；本文件是**操作面**：怎么判、
边界情形怎么办、判错了会付什么代价。一句话目标 ——

> 任务大小不是代码量，是**错误决策的代价**。

## 0. 为什么不用「小改动 / 大改动」

按行数或文件数分档，会在两个方向同时判错：

| 实际的活 | 按行数判 | 按代价判 | 判错的后果 |
| --- | --- | --- | --- |
| 挪一个按钮，碰 6 个文件 | 「大」→ 建卡、写影响分析、开一轮治理 | **QUICK** | 纯浪费：一个可逆的展示改动付了 DEEP 的流程税 |
| 一个字段 `nullable → required`，3 行 | 「小」→ 直接改，提交信息一行 | **DEEP** | 存量数据里的 null 在下一次读取时炸；回滚要写反向迁移 |

第二行是这套分档存在的全部理由。**行数从来不在刻度上。**

## 1. 四个变量各自怎么判

### U —— 不确定性：我现在说得出验收判据和它的证据吗

| 档 | 长什么样 |
| --- | --- |
| QUICK | 说得出验收判据，且这句话只有一种读法；证据我现在就能命名（哪条命令、看哪个输出） |
| STANDARD | 主体清楚，但有**一个**待确认点 —— 而且它可以写成显式假设，错了只影响这一处 |
| DEEP | 说不出验收长什么样；或同一句要求有两种读法，各自都自洽（ADR-0102 那种「问错了的问题」） |

**判 U 的动作不是想，是试着写一句验收。** 写不出来就是 DEEP，别自我安慰。

多个待确认点堆在一起也是 DEEP：一个假设可以显式记下来，三个假设互相耦合就不是
假设了，是没想清楚。

### I —— 影响面：错了会波及谁

**刻度是坏结果的传播范围，不是改动的物理范围。**

| 档 | 长什么样 |
| --- | --- |
| QUICK | 错了只有这一处表现不对，别的地方照常工作 |
| STANDARD | 错了会让**同域内**其他功能跟着不对（共享模块、同一个状态源、同一份配置） |
| DEEP | 错了跨域 / 跨层 / 跨进程传播，或者**让持久数据变脏** |

「持久数据变脏」单独列出来，因为它有一个别的档没有的性质：**错误会活过修复。**
代码改回去了，脏数据还在。

### R —— 可逆性：撤销要做什么动作

| 档 | 长什么样 |
| --- | --- |
| QUICK | `git revert` 就够，撤完世界回到原样 |
| STANDARD | 要一次反向迁移或一次重跑，但**数据没丢**，且反向路径我现在说得出 |
| DEEP | 碰用户文件 / 已经发出去的结果 / 钱 —— 撤销要么不完整，要么要向外解释 |

**R=DEEP 时先看能不能把它降下来**（AGENTS §1「回不了头是缺陷」）：写带版本的新
路径、迁移前留可回滚旧数据、加法字段优先于破坏性变更、删除做成软删除。
**降下来之后按降下来的档走** —— 这是四个变量里唯一一个「可以主动改变取值」的。

### C —— 合同变更：动了别人依赖的约定吗

| 档 | 长什么样 |
| --- | --- |
| QUICK | 没有 |
| STANDARD | 没动既有合同，但**新增**了一处内部约定（一个新的命名规则、一个新的事件名） |
| DEEP | 动了 schema / API / 持久化格式 / 公共接口 / 架构边界 / 外部合同 |

「合同」的判据是**有没有第二方按它写过代码或存过数据**。只有一个调用方且和它同
一次改完，那不是合同，是内部实现。

## 2. 取最高，不平均

```
深度 = max(U, I, R, C)
```

不投票、不「三个 QUICK 压过一个 DEEP」。理由是这四个变量各自都能单独毁掉一次
改动：需求理解错了、波及面估小了、撤不回来、把别人的合同改了 —— 任何一个成立，
剩下三个再干净也救不了。

**判错的代价不对称**：判高了多付一张卡和一节影响分析；判低了付的是上面那张表
第二行。**拿不准就取高的那一档。**

## 3. 深度 ≠ 验证强度

这是最容易混的一条：

- **深度（四变量取最高）→ 决定成果物**：建不建 REQ、建不建卡、写不写 ADR、
  影响分析写在哪。
- **影响面 I（单独一个变量）→ 决定验证与审查**：跑哪些测试域、调不调
  `codex-review-loop`（AGENTS §20 / ADR-0080 · ADR-0081）。

所以「持久化里改一行」是 **QUICK 流程 + backend/studio 两个域的验证 + 一轮审查**：
它 U/I/R/C 里只有 I 高，流程重量跟着最高档走没错，但**验证重量从来只看 I**。

反过来，「一份纯文档重写，2000 行」是 QUICK 深度、**不调审查**（纯文档不调），
即使它的 diff 比上面那一行大三个数量级。

## 4. 边界情形

| 情形 | 怎么判 |
| --- | --- |
| 「先做个 prototype 看看」 | Discovery 产物是 Evidence，不是实现 —— 探索本身不判深度；**探索之后把结论落地**的那次改动才判 |
| 一次改动里既有展示又有合同 | 按合同那部分判（取最高）。更好的做法是拆成两次改动，展示那次走 QUICK |
| 存量代码里改一行 bug fix | 看这一行**在什么位置**：叶子函数 → QUICK；共享模块 → I=STANDARD；改了返回值形状 → C=DEEP |
| 「只是改个默认值」 | 默认值写进过持久化数据吗？存量数据会因此被重新解释吗？会 → C=DEEP |
| 依赖升级 | patch 版且测试全绿 → STANDARD；minor/major 或改了调用面 → DEEP（Migration 工作流本来就默认 DEEP） |
| 改本 Skill / AGENTS.md / hooks | C=DEEP —— 它们是**所有 Agent 的合同**，改错了下一个人按错规则干活 |

## 5. 升档随时生效

深度是开工时判的，不是判完就锁死。**任一信号出现，停下升档、补齐对应记录、
再继续**：

- 改动扩散出第 5 环「明确不动」那一栏；
- 发现与已确认行为冲突（U 事后变成 DEEP）；
- 触发架构治理的任一条件（[architecture.md](architecture.md)）；
- 撤销路径比开工时想的长（R 事后变成 DEEP）。

**降档不是对称的**：开工判 DEEP、做下来发现很简单，卡已经建了就留着，
别为了「其实是 QUICK」去删记录 —— 那次判断的过程本身是 B 类历史证据。
