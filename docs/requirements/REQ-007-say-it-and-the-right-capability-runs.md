# REQ-007：他说一句话，对的那个专业能力就跑起来

- 状态：CONFIRMED
- 来源：产品负责人 2026-08-29
- 版本：v2（2026-08-29）—— v1 是「前端 Agent 自动路由并触发产品 Story Skill」；
  同日 v2 把它收敛成**三个用户能力 + 后端 resolver**（判据 6/7 为此追加，
  判据 1–5 一字未改）
- 相关 Change：[TASK-119](../tasks/done/TASK-119-three-user-capabilities-and-a-resolver.md)
- 相关 ADR：[ADR-0091](../adr/ADR-0091-three-user-capabilities-and-a-server-side-resolver.md)
  （三类能力 + 服务端 resolver）；落在 [ADR-0089](../adr/ADR-0089-conversational-agent-write-path.md)
  的对话式写路径与 [ADR-0067](../adr/ADR-0067-product-skill-package.md) 的能力包之上

## 他说的原话

> 「用户在 Studio 的『作品』对话窗口说自然语言，例如"帮我搭建世界观""设计这个角色"
> "梳理故事结构""写这一集剧本""检查前后是否矛盾"时，前端 Agent 能根据当前项目上下文
> 自动选择合适的现有 product-skill 并启动它；若输入不足，则明确说缺什么，不启动。」

v2（同日）：

> 「目标不是继续给前端 Agent 增加更多 product skill，而是让它只理解少量面向创作者的
> 『用户能力』，把具体专业 skill 的选择下沉到后端编排层。这样减少前端上下文 token、
> 降低维护成本，并避免多个 skill 的触发词互相抢路由。」

## 判据

1. **说了就跑。** 他在「作品」窗口说一句自然语言，对应的专业能力被启动 ——
   不必先去挑一个能力、填声明式输入、选执行器。
2. **不够就说缺什么，不跑。** 必要材料不齐时**不启动**，并用他看得懂的话说出缺哪几样。
   「我不知道你要什么」和「我知道但你还缺材料」必须是两个不同的答案。
3. **跑起来 ≠ 已接受。** 自动触发的是**运行**，输出照旧过 schema、照旧是提案、
   照旧版本化、照旧可撤销。作品不会被静默改动。
4. **「开发」窗口一个字节都不会被改。** 那个窗口里作品能力不许被启动 —— 服务端强制，
   不是模型自觉。
5. **一句话最多一个能力，重复不再跑。** 刷新、轮询、网络重试都不得重复启动。
6. **前端 Agent 只理解三类工作（v2 追加）。** 它看得见的能力是
   `story-development` / `episode-production` / `story-review`，**就这三个**；
   提示词的长度不随装了多少能力包增长。内部专业能力的名字、触发词、输入契约、prompt
   都不进它的上下文，它也无权指定内部执行什么。
7. **选哪个专业能力由服务端确定性地决定（v2 追加）。** 「检查这一集剧本」
   「检查镜头连续性」「检查故事多层一致性」必须分别落到三个不同的诊断器上，
   不被同一个泛化能力吞掉；同一句话永远选出同一个；为什么选它，说得出来也测得到。

## 不在范围内

- 页面里已有的专业按钮/工作流**不收敛**：它们是明确的入口，继续直连专业能力。
  这次收敛的对象只有「前端自然语言 Agent 的上下文与自动路由」。
- 付费/生成类动作的自动化（AGENTS.md §1：花钱是唯一必须问的事）。
- 每次编辑后自动跑审查 —— 只有他明确要求，或一次已落地的结构性变更明确影响多个
  层级时，才**建议**相应诊断。
- 外部 story-skills 仓库的 Markdown 持久化、file watcher、CLI、导入器：
  它们是开发 Agent 的文件型 skill，本产品保持结构化、版本化的作品数据与受控写路径。

## 验收（TASK-119 交付时实测）

- 「这一集剧本有什么问题」→ 剧本诊断；「镜头之间连续性对得上吗」→ 连续性审校；
  「我改了大纲，各层还同步吗」→ 跨层诊断；「检查一下」→ **不**跑跨层诊断
- 空项目里说「写这一集的剧本」→ 不跑，回「还缺本集规划」
- 「开发」窗口里说同样的话 → 不跑，并指出切回哪个窗口能做
- 提示词里出现的能力名只有那三个；26 个内部能力的 id 一个都不在里面
