# REQ-003：每一次实现都能从产品意图追到验证，审查先答「需求做完了吗」

- 状态：CONFIRMED
- 相关 Change：TASK-108 · ADR-0088 · `1b32047`（交错文件在 `712c7d4`）

## v1 — CONFIRMED（2026-08-26）

- 来源：产品负责人 2026-08-26 —— 「Every implementation must be traceable from
  product intent to verification.」「Codex Review 第一目标不是代码写得是否漂亮，
  而是实现是否真正完成了它声称完成的 Requirement。」「最重要的验收标准：Codex
  不再只是回答 The code looks good —— 它必须能回答：这个 Change 声称完成了哪些
  Requirement，每条 Requirement 是否真正完成，证据在哪里，是否符合当前
  Architecture，如果不能 Merge，具体缺的是哪一环。」

- 用户真正需要什么：**任何一次交付都能被逐条追问，并且追问是自动发生的**。
  具体是四件事同时成立 —— 每个 Change 说得出它为哪条需求而做；每条验收判据
  说得出谁实现了、证据在哪；越了架构边界会被拦住；缺口能指名是链条上哪一环，
  而不是一句「看起来没问题」。

- 为什么：现有审查只送 diff，需求与架构约束一个字都不进审查者的上下文，于是
  「实现了 2/3 条判据」「需求做到了但依赖方向反了」都能正当拿到
  `VERDICT: pass`（2026-08-26 盘点，证据在 ADR-0088 §1）。而本仓库最贵的缺陷
  正是这一族：声明与事实脱节，且没人当场发现。

- 验收判据（产品视角，非测试清单）：
  1. 每个 Change 能说出它服务哪条 Requirement 的哪条判据；没有产品需求的工作
     必须写明技术目标，否则被标为 `ORPHAN_TASK` 并且不得进入 Merge；
  2. 审查按固定顺序作答：需求完成度 → 架构符合性 → 证据充分性 → 技术质量，
     且普通代码问题不得盖住「需求没做完」；
  3. 每条判据得到 `PASS` / `PARTIAL` / `FAIL` / `NOT_EVIDENCED` 之一，
     不因「实施 Agent 声称完成」或「测试全绿」而判 `PASS`；
  4. 任一判据非 `PASS`、或架构越界、或证据不充分 → Merge Gate 不为 PASS，
     并且报告能指名缺的是链条上哪一环；
  5. 审查者默认只读本次 Review Package（需求 + 判据 + 约束 + diff + 证据），
     不扫全仓库、不遍历历史 ADR；
  6. 这些规则由**开发流程自动执行**，不新增用户要手工维护的追溯文档或数据库。
