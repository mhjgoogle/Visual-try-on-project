# 提案：一份「面清单」，让「我明明写了你怎么看不到」不再发生

- 日期：2026-08-31
- 起因：产品负责人「有没有更好的办法。你仔细想想整个项目有没有更适合的解法。给我个提案」
- 状态：**提案，等他拍板**。没有他的同意不动工。

## 1. 先看今天发生了什么（不是印象，是数出来的）

2026-08-30 到 08-31，他撞到六个缺陷。修的时候我以为是六件事，摊开看是**同一件**：

| 他看到的 | 实际漏在哪 |
| --- | --- |
| 「我明明写了你怎么看不到」 | Agent 的事实没读新数据 |
| 「什么是创意简报」 | Agent 的页面地图还是旧的 |
| 「还缺 创意 Brief」 | 能力的输入映射 + 上游标签还是旧的 |
| 「写好了却还是空的」 | 大纲提案的写回路径没接线 |
| 「说了点按钮但没有按钮」 | 前端字段名对不上 |
| 「本机没有可用的执行器」 | 执行器建议被当成了限制 |

**一个「面」（故事核心 / 大纲 / 结构规划 / 正文 / 人物 / 场景…）在代码里被
七处各自独立地描述：**

1. 左栏与页面标题（`ui/shell.js`）
2. 页面怎么画（`ui/*ws.js`）
3. Agent 看到的事实（`server.py`）
4. Agent 看到的页面地图（`server.py`）
5. Agent 能做的动作（`workflow/convactions.js`）
6. 能力运行时的输入（`controllers/skillctl.js`）
7. 上游标签与影响面（`workflow/canondoc.js`）

改一页要手工同步七处。**漏一处就是上面的一行。**

而 2039 条前端测试全绿 —— 因为它们各自检查**每一处的形状**，没有人检查
**七处说的是不是同一件事**。我这两天补了一条合同测试守住其中一条线（页面 ↔ 事实），
但那是事后检测，不是「结构上不可能错」。

第二组数字：前端里「拦住 / 不给做」的分支 **209 处**，其中防的是不可逆损害
（花钱、覆盖他已有的东西）的：**0 处**。他那句「前端服务器限制太多了」是准确的。

## 2. 提案（三件，按我建议的顺序）

### C. 先做：一个「体检」，对着**他的真实项目**跑

**为什么先做它**：今天每一个 bug 都是他在真实项目上撞到的，而测试全绿。
测试守的是形状，不是「他打开会看到什么」。这一件最便宜（半天），立刻止血。

跑一条命令，对着他真的那两个项目输出一页：

```
照见未明
  故事核心   2069 字   Agent 看得见 ✓   Agent 改得动 ✓   能力读得到 ✓
  故事大纲   1 个节点   ✓  ✓  ✓
  结构规划   12 行      ✓  ✓  ✓
  人物       0 个       ✓  ✓  ⚠ 能力读到的是空的
  执行器     claude-code 可用 · codex 停用（复核会降级并注明）
```

**他看到的变化**：我改完先跑它，撞见的概率大幅下降；他也能自己跑一次看现状。

### A. 再做：**一份「面清单」，其余七处由它生成**

每个面只声明一次：

```
故事核心
  叫什么      故事核心
  数据在哪    story.work.core
  谁能改      他自己（编辑器） / Agent（work.core）
  定稿规则    点「定稿」才存版本；历史可看可恢复可删
  当能力输入  brief
```

然后左栏、页面标题、Agent 的事实与页面地图、Agent 的动作表、能力输入、上游标签
**全部从它生成**。

**他看到的变化**：以后我改一页，Agent **当场就知道** —— 不会再出现
「我明明写了你怎么看不到」「什么是创意简报」这一类。新加一个面时，它自动
看得见、改得动、能力也读得到。

**代价**：一次重构，我估 1–2 天，期间界面不变（只换底下的接线）。
风险是重构本身可能带进新缺陷 —— 所以放在 C 之后，有体检兜着。

### B. 最后做：把「拦住」改成「先做，缺什么说出来」

209 处拦截里没有一处防的是不可逆损害。规则改成：

- **能做多少做多少**，缺的材料在结果里说清楚（「人物页是空的，这块我是照故事核心推的」）
- 只留两道真闸：**花钱**、**覆盖他已有的东西**

**他看到的变化**：不再有「还缺 X —— 先把这些补上」把他挡在门外。
他说「审一下」就审，用现有的材料，并告诉他哪几块没底。

**为什么放最后**：209 处要逐条看哪些该留 —— 有些「拦」其实是在防脏数据流进创作文档。
这件事需要判断，不能一刀切。

## 3. 我不建议做的

- **推倒重来**：这个应用已经有真实项目在里面（12 集、2069 字的故事核心、
  5 版定稿）。重写的第一天就要面对「怎么把这些搬过去」，而那正是今天出问题的地方。
- **再加一层「同步检查」测试**：那是给病加护士，不是治病。七处变一处才是治。
- **把 Agent 换成能读文件的**：能读文件的 Agent 会让「事实里有没有」这个问题消失，
  但它也让「他写的剧本」变成一条注入面（ADR-0042 挡的就是这个）。不值得。

## 4. 他自己给出的那条不变量（2026-08-31）

> 「所以 archi 应该是服务端的 agent 能够看到我这个项目内的所有内容然后做出判断和修改。」

**这句比第 2 节的提案 A 表述得更准**，采用它作为这次架构的一句话：

> **一个项目的全部内容 → Agent 全看得见 → 全改得动。**

「七处同步」不是目标，只是达成它的手段；目标是这一句。下面三条是它落到实处的形状。

### 4.1 「看得见全部」≠「一次全塞进提示词」

他的项目现在事实 6341 字；一部十二集的剧本会是十几万字，一次塞进去会把别的挤掉。
所以正确的实现是两层：

- **目录必须全**：项目里的每一样东西都要出现，带名字、多少字、什么状态。
  **今天他撞到的全部是「不在目录里」，不是「太长」** —— 故事核心根本没被读、
  「创意简报」是个不存在的名字、定稿版本一条都没有。
- **正文按需给全文**：他正在看的那一页、他点名的那一版，给全；其余给目录条目。
  截断时说出来（已经做了）。

### 4.2 「改得动全部」= 每个可写点都有一条真的路径

今天数出来的：动作词表声明 49 条，其中 **`proposeScript` 是「声明了、接了、
返回『尚未接线』」** —— 与 `proposeOutline` 完全同一种。能力跑完说「写好了」，
他点「用它」，什么都不会发生。**正文创作正是他下一步**，他一定会撞到。
（2026-08-31 当场接上了：写进当前这一集，原有内容先自动存一版，不静默覆盖。）

所以体检（提案 C）里必须有这一项：**每一个声明过的写动作，都要能指到一条真的写路径**；
「声明了但没接线」当场红。

### 4.3 product-skill 这一层：同一个病，三处手工映射

一次能力调用是八跳，其中**三处是手工映射**，每一处都可能漏：

| 跳 | 谁决定 | 漏了会怎样 |
| --- | --- | --- |
| manifest 说「我要 `brief`」 | 技能包 | — |
| **`brief` 是哪份数据** | `skillctl.js`（手工） | 「还缺 创意 Brief」——他明明写了 |
| 缺不缺 | `skills.js` | 材料够了却被拦 |
| 拼提示词 | `skills.js` | — |
| **谁来跑** | `runtime.js`（建议表） | 「本机没有可用的执行器」 |
| 校验输出 | `skills.js` | 好答案被丢掉（已修） |
| **结果 → 哪个写动作** | `skillapply.js`（手工） | 提案无处可去 |
| 那个动作真的写哪儿 | `app.js`（手工，可「声明未接线」） | 「写好了」但没写 |

**面清单要把这三处一起收掉**：一个面声明「我当能力输入时叫 `brief`」「我的写动作是
`work.core`」之后，`skillctl` 的映射与 `skillapply` 的映射都从它生成，
`app.js` 那一层只剩「执行」，没有「决定写哪儿」。

那时 manifest 仍然只说名字（技能包是**产品资产**，不该知道内部数据结构 ——
ADR-0067 决策 2 那条不动），但名字到数据只有**一处**答案，而不是三处各答一次。

## 5. 要他拍板的只有一句

**先做 C（体检）吗？** 做完我把 A 的形状画给他看，再决定动不动那次重构。

体检里至少要有这四项（今天四个缺陷各对一项）：屏幕上的内容是否都在事实的目录里 · 每个可写点是否都有真路径（`proposeScript` 那一类当场红）· 能力输入名到数据是否解析得到 · 执行器是否真的可用（降级要注明）。
B 需要他一起看那 209 处里哪些该留 —— 那是后话。
