## 1. 为什么三步向导正好治「太 busy」

产品负责人的抱怨有精确的技术形态：剧集制作今天是 **5 个平级页面**
（本集看板 / 分镜设计 / 镜头制作 / 粗剪审片 / 后期交付），
每页自己又是三栏 —— **任何时刻屏幕上都有十几个同级入口，没有一个说「下一步点我」。**

向导的性质正好相反：**任何时刻只有一个下一步动作。**
顶部常驻进度与真实数字（`14个镜头已就绪` / `0/10 已生成、还差 10 个` / `1/14 已合成`）。

**但我们的向导是五步，不是 LibTV 的三步** —— 见 §1.2，那是产品负责人当场补上的，
而且他补的是目标产品**自己的一个缺陷**：

```
① 确认镜头     分镜表                                      §2.1
② 准备资产     角色 / 场景 / 道具的「基础资产」             §2.2
③ 合成提示词   两份：分镜提示词 · 视频运动提示词            §2.3
④ Storyboard   低成本草图，先确认镜头设计     ← 我们新增    §2.4
⑤ Keyframe     由 ④ + ② 合成的正式画面        ← 我们新增    §2.5
                        ↓
                   批量生视频
```

> **这也修正了 TASK-091 的界面方案。** 那张卡把九步做成一条「带步号的 rail」——
> 那仍然是「十一个入口，只是排了序」。**九步作为事实是对的，作为界面不对。**
> 见 §4。

### 1.2 LibTV 从提示词直接跳到批量生视频 —— **那是缺陷，不是要照抄的形态**

产品负责人 2026-08-17：「但是我觉得缺乏几步。就是 storyboard 和 keyframe。」

他是对的，而且判据是他自己早先给的：

> 「Shot Design = 文字/结构化的拍摄设计；**Storyboard = 把这个设计先画出来看看**；
> Keyframe = 真正用于后续生成视频的高质量画面」
> 「**Storyboard 的核心价值就是：在花高成本生成正式图和视频之前，先确认镜头设计。**」

LibTV 的向导是 `确认镜头 → 准备资产 → 合成提示词` → **直接 `批量生视频`**。
也就是**从一段文字直接跳到整条链上最贵的一步**，中间没有任何一次便宜的目视确认。
**照抄它，等于把上面那句话删掉。**

成本的阶梯正是这两步存在的全部理由：

```
Storyboard   低画质 / 小尺寸 / 草图      便宜   ← 在这里否掉，只亏这一点
Keyframe     2K / 标准画质（⚡18）       贵     ← 只在设计确认之后才花
Video        整镜生成                    最贵   ← 只在画面确认之后才花
```

**这两步也是 [TASK-092](TASK-092-shot-workflow-multi-stage.md) 那个闸门的落点**：

> `keyframe` 可开工 ⟺ `storyboardStatus == skipped` 或
> （`completed` **且那张草图已 approved**）

于是 ④→⑤ 之间**不是一根箭头，是一道门**。而 `skipped` 正是 092 里
**唯一真正新增的持久化状态** —— 因为产品负责人明确说过两者不都是必需的：

| 模式 | 走法 |
| --- | --- |
| **轻量** | ④ 跳过（`skipped`），直接 ⑤ |
| **规范** | ④ 出草图 → 确认 → ⑤ |

**跳过必须是一等状态，不是「没做」** —— 否则界面永远分不清「他决定不画」和
「他还没画」，这正是 092 §2.2 按来源分配状态要解决的事。

### 1.3 而 ⑤ 不是向导上的一个按钮 —— 它必须在**单镜画布**上做

产品负责人 2026-08-17（原话见 §0）：

> 「资产准备里面也不能单单有基础资产。还得**通过 storyboard 和人物形象和场景来合成
> keyframe**。只是这个**没办法在资产准备这一步就执行**。可能需要先准备好基本的人物资产
> 以后**再在画布上执行**。」

**这句话决定了 ⑤ 的形态，而且它是对的。** Keyframe 不是「再出一张图」，它是**合成**：

| 输入 | 提供什么 |
| --- | --- |
| ④ 那张 Storyboard 草图 | **构图 / 机位 / 人物在画面里的位置** |
| ② 的角色设定图 | **人物身份**（长相、服装、特征的一致性） |
| ② 的场景设定图 | **环境** |
| ③ 的 `分镜提示词` | 文字描述与视觉风格 |

**三张图 + 一段提示词 → 一张图。** 第 2 步手上只有**基础资产**，
草图还不存在，**所以那一步在结构上就合不了 keyframe** —— 产品负责人的判断准确。

**因此 ② 的定位要写清楚：它准备的是「基础资产」，不是 keyframe。**
两者的关系是**原料与成品**，不是「先做一批、后做一批」。

**而多图合成一张图这件事，唯一放得下的地方就是
[TASK-093](TASK-093-one-canvas-per-shot.md) 那块单镜画布** ——
因为要选哪几张图、按什么顺序、每张管什么，这本身是一次**有结构的编排**，
不是一个按钮能表达的。这同时回答了产品负责人此前问的「一个 shot 一个画布是不是
有点奢侈了」：**画布不是锦上添花，它是 keyframe 合成唯一的落脚点。**

**向导第 ⑤ 步因此长这样**：一张全集清单，每镜一行，状态取自 092 的
`keyframeStatus`；行上的动作是**「进入这一镜的画布合成 →」**。
向导负责**说清还差哪几镜**，画布负责**做那一镜**。
（可批量的只有「用同一套默认编排试一遍」，产出仍是提案，逐镜确认 —— 见 §3。）

### 1.1 向导**不新增页面**（ADR-0066 决策 10 的冻结集合不动）

向导是 ⑦ 分镜设计 + ⑧ 镜头制作**已有内容的重新组织**，
以一层覆盖面（overlay）呈现，**不新增一级或二级页面**，`PAGES.length === 11`
那条冻结守卫不碰。这一点必须在实施时钉成测试 —— 新界面最容易顺手多开一页。

## 2. 三步的具体形状

### 2.0 入口（图 1）：剧集制作从「写剧本」开始

```
剧本节点（AI 根据分集规划写 → 我手动修改）
   └→ 脚本生成器  ── 点开 ──→  三步向导
```

- **剧本**：AI 依 TASK-094 定型的分集规划那一行写；人可改；追加新版本（既有写路径）。
- **脚本生成器**：一个动作 —— **从剧本自动生成分镜**，落到第 1 步的表。
- 这正是产品负责人此前说的「一镜一画布」的**上一层**：
  剧集级画布放 `剧本 → 脚本生成器 → 批量`，
  单镜精修才是 [TASK-093](TASK-093-one-canvas-per-shot.md) 的那块画布。
  **两层不矛盾**，粒度不同。

### 2.1 第 1 步「确认镜头」（图 2）：分镜表

**列（产品负责人给定，逐字）**：

```
Scene ｜ 镜号 ｜ 时长 ｜ 画面描述 ｜ 景别 ｜ 光影氛围 ｜ 对白·旁白 ｜ 音效 ｜ 运镜 ｜ 最终提示词 ｜ 操作
```

- **全部由 AI 生成，每格就地可改**（`点开每个表格都能更改`）。
- **`操作` 列可删除 shot** —— 删除走**软删除**（AGENTS.md 第 13 条），不是抹掉记录。
- 我们**已经有**其中六列：`景别 / 运镜 / 光影氛围` 是 TASK-078 刚补上的
  （在此之前它们在 HTTP 边界被 `_parse_shots` 丢掉）；`时长 / 画面描述 / 对白` 已有。
- **缺的是 `音效` 与 `最终提示词` 两列**，以及 §2.1.1 的 Scene 分组。

#### 2.1.1 Scene 是**分组行**，不是每行重复的一列

产品负责人明确要求的形态：

```
▼ Scene 01 ｜ 金銮殿 ｜ 白天
    Shot 01 …
    Shot 02 …
    （…08）
▼ Scene 02 ｜ 便利店外 ｜ 夜
    Shot 01 …
```

**这一条同时解决了 GAP-13**（真实项目 48 集**全部 0 场景**、60 个镜头全在
「未分配到场景」）。TASK-091 §1.2 的诊断是对的 —— 场景是个可以忽略的可选盒子 ——
但**修法比那张卡写的更好**：不需要「把 Scene 拆分做成一个显式步骤」，
**分组行本身就迫使 Scene 存在**，因为表要分组就必须有组。少一步，效果更强。

#### 2.1.2 Scene 需要一个新字段：时间

实测我们 `proddoc` 的 scene 已有：
`sceneId` / `title` / `location`(+`locationRef`) / `characters`(+`characterRefs`) /
`shotIds` / `bgmAssetId` / `ambienceAssetId`。

对着 `S03｜便利店外｜夜`：

| 要显示的 | 我们有吗 |
| --- | --- |
| `S03` 编号 | **有** —— 从顺序派生，不存 |
| `便利店外` 场景名 | **有** —— `title` / `location` |
| `夜` 时间 | **没有。新增 `timeOfDay`** |

- **加法字段**，不动任何既有数据（AGENTS.md 第 13 条：加法优先于破坏性变更）。
- 老数据 `timeOfDay` 缺失 → 显示为空，**不猜、不填默认值**（既有诚实纪律）。
- 起草 Scene 的 Skill 必须**一起产出 `timeOfDay`**
  —— `grep` 确认 Skill 的 schema 里今天没有这个字段，只加前端会得到一个永远为空的列。
- 产品负责人给了理由：**「这样后面做场景资产复用会更方便」** ——
  同一个 `便利店外` 的白天与夜是**两套场景图**，没有时间就没法复用也没法区分。

### 2.2 第 2 步「准备资产」（图 3 / 图 4）

**图 3**：顶部一块 **全局风格**（长文本，AI 写）；下面按 **角色 / 场景 / 道具** 分组的卡片，
每张卡是「生成或上传角色图」+ 名称 + 描述摘要，末位一个 `＋ 新增`；
底部如实提示 **`检测到 5 个人物角色和 3 个场景和 2 个道具没有设定图`**。

- **资产清单由 AI 从第 1 步的表抽取**（产品负责人：`AI 通过前面的表格抽取`）。
  我们**已有** `script-breakdown` 干这件事（产出人物/场景地）；
  本卡把它的输入从「剧本」扩到「分镜表」，并补上**道具**。
- **「还差 10 个」这类计数必须来自实际登记表**，不是清单上的空。
  （本仓库栽过的原型：`storageState` 声明「文件在」而从不核对，
  存储页因此报「媒体不可用 0」。**这里绝不能重演。**）

**图 4**：点卡片 → 弹窗 `选择图片（现代沈昭昭）`，**三个 tab**：

| tab | 说明 |
| --- | --- |
| **AI 生成** | 框里是**AI 已经写好的提示词**：名称 / 描述 / 服装 / 特征 / **构图规范** |
| **从当前画布选择** | 我们的对应物是**资产库**（产品负责人原话「从资产库中上传」） |
| **本地上传** | 已有 |

底部：`Lib Image` 模型 · `标准画质` · `2K` · `2:1` · **`⚡18`** · `确认生成`。

**那段「构图规范」要照抄进我们的 Skill prompt**，因为它是**可复用的专业知识**，
不是 LibTV 的私有实现：「必须是角色四视图 = 正面头部特写 + 全身正面/左侧/背面，
淡灰 2px 细线分割，纯白背景，中性棚灯平光，**角色必须空手、无道具、无表情、无背景、
无文字水印**」。**它的目的是让这张图能当参考图用** —— 见 §2.3.2，那是关键。

### 2.3 第 3 步「合成提示词」（图 5）—— **本轮信息量最大的一步**

产品负责人的一句话是这一步的全部要害：

> **「这个提示词是会用到现在角色图片的。」**

**所以第 2 步不是可选的前置装饰，它是第 3 步的输入。** 向导的顺序由数据依赖决定，
不是编排偏好。

点某镜的 `最终提示词` → 弹窗 `第 1 镜：最终提示词`，里面是**两个提示词，不是一个**：

#### 2.3.1 两个提示词，对应两次生成

| | 用途 | 形态 |
| --- | --- | --- |
| **分镜提示词**（`分镜图提示词·已生成`） | **出图**（Storyboard / 关键帧） | 一段散文，把角色档案**展开**进去：「特写镜头，画面主体聚焦于 **@现代沈昭昭** 疲惫的面庞。**@现代沈昭昭** 是一名 28 岁体型偏瘦的女性，留着干枯的中长发…」末尾内联 `[视觉风格：**@盛唐** 古风穿越题材，国风二次元动漫风格…]` |
| **视频运动提示词**（`视频运动提示词·已生成`） | **出视频** | **结构化**：`出场角色：@现代沈昭昭，高165cm` / `背景场景：办公室，深夜昏暗，高3米；电脑显示器，高45cm；键盘，长40cm` / `参考图使用规则：…` |

底部：`GVLM 3.1` · `⦿ 智能合成 ／ ○ 自动拼接` · **`⚡6`** · `重新合成提示词`；
右下 **`一键合成全部提示词`**；每个框 `自动保存`。

**对我们的意义**：`promptc.js` 今天编一份提示词。
**这里要两份**，因为它们喂的是两次不同的生成（TASK-092 的 Visual 组正是
`Storyboard → Keyframe → Video`）。「运动」只属于视频那一份 ——
把运镜写进出图的提示词，是在要求静态图表达运动。

#### 2.3.2 `@角色` 就是参考图绑定 —— **ADR-0071 被真实目标产品证实**

提示词里的 `@现代沈昭昭` / `@盛唐` **不是自由文本，是引用**。
它与我们抓到的 LibTV 线格式完全一致：

```
prompt: "在 {{Image 1}} 石头两侧增加 {{Image 3}} {{Image 5}} 女人…姿势参考 {{Image 2}}"
imageList: [{ nodeId, url, label:"石头", width, height }, …]
```

[ADR-0071](../adr/ADR-0071-reference-inputs-as-ordered-set.md)（**2026-08-17 已 Accepted，
报价取方案 C**）设计的 `[[ref:N]]` 内联引用 + 有序集合 + Provider 声明能吃几张，
**正是这个形状**。本卡是它的第一个真实消费者。

**因此顺序上的硬约束**：ADR-0071 的实施（TASK-083 ADR-A）**必须在本卡第 3 步之前**，
否则合出来的提示词里那些 `@角色` 在付费路线上**一张图也送不到模型**
—— 那就是 TASK-077 §1.3 修掉的那个谎，原样复活。

#### 2.3.3 「参考图使用规则」—— 一段我们完全没有的东西，而且不写会真的出错

`视频运动提示词` 里有一段显式规则：

> **参考图使用规则：**
> - 角色参考图：**只参考此图中的角色形象；不参考角度、构图、姿势、表情**；
>   **若此参考图是角色多视图，则必须保证角色不能重复出现**

**这不是客套话，是 §2.2 那段「构图规范」的必然后果。**
第 2 步刻意生成的是**四视图设定图**（一张图里四个角度）——
把它直接当参考图喂进去，模型会照着画**四个视图**。LibTV 用一段规则挡住它。

**我们今天连这个位置都没有。** `ROLE_USE` 只说了参考**进不进模型**
（`model-input` / `ai-interpretation`），**没有任何东西说「怎么用」**。
而 TASK-093 §2.4 正准备引入四视图角色库 —— **规则必须和它同时落地，不能后补。**

**交付**：每类参考在合成时带一段**用法规则**（角色 / 场景 / 道具 / 视觉参考各自不同），
规则是 Skill 包的内容（可随版本演进），**不是硬编码字符串**。

### 2.4 第 4 步「Storyboard」——**我们新增**，低成本先看一眼

**输入**：③ 的 **`分镜提示词`**（不是视频运动提示词 —— 草图不表达运动）。

- **一次出全集**：`14 个镜头` 一起出草图，因为要判断的不只是单镜，
  还有产品负责人列的第六条 **「前后 Shot 接起来是否顺」**。
- **形态是横着看的一条带**，不是一镜一张卡 —— 连贯性是**跨镜**判断，
  单镜视图看不见（[TASK-093](TASK-093-one-canvas-per-shot.md) §0c 已记下这一条）。
  复用 ⑨ 粗剪审片的既有视图模型，**不新建第二套**。
- **刻意用便宜档**：低画质 / 小尺寸。它的用途是判断构图与连贯，不是成片。
  **界面必须写明这是草图** —— 不得让创作者以为这就是最终画质。
- 每镜三选一：**通过 / 重出 / 跳过**。
  - `通过` → 绑定到那张**具体草图**（复用既有 `isApprovedFor(prod, shotId, assetId)`，
    因此**换了草图，通过自动失效** —— 这是既有机制，不要另写）
  - `跳过` → 写 `storyboardStatus = "skipped"`（轻量模式）
- **新增 asset kind `storyboard`**（TASK-092 §2.7 已登记）。

### 2.5 第 5 步「Keyframe」——**合成**，在单镜画布上做

形态与理由见 **§1.3**（产品负责人 2026-08-17 定的）。要点：

- **它是合成，不是又一次文生图**：④ 草图（构图）+ ② 角色设定图（身份）
  + ② 场景设定图（环境）+ ③ 分镜提示词。
- **闸门**：`storyboardStatus == skipped` 或（`completed` 且草图已 approved）。
  没过闸门**不置灰下一步**（既有纪律），而是**如实写出缺什么** ——
  「第 3、7 镜的草图还没确认」，并给一条直接跳过去的路。
- **多图合成必须走 [ADR-0071](../adr/ADR-0071-reference-inputs-as-ordered-set.md)
  的有序参考集合**（已 Accepted，报价取方案 C）：
  每张图**声明它管什么**（构图 / 身份 / 环境），并带 §2.3.3 的**用法规则** ——
  否则四视图设定图会让模型画出四个视图，草图会被当成风格而不是构图。
  **方案 C 的后果要如实呈现**：provider 未声明「多图不额外计费」→ `maxImages: 0`
  → **这一步在该 provider 上不可用**，界面说明原因，不静默降级成单图。
- **正式档**：`2K` / 标准画质（`⚡18` 量级）。产出**就是视频首帧**，
  接到既有 `shot.first_frame_image → packets.py → cloud_minimax` 那条路，
  **不新建第二条通道**。
- **新增 asset kind `keyframe`**（TASK-092 §2.7 已登记）。
- 通过后才解锁 `批量生视频`。

| 动作 | 单价（LibTV 实测） | 批量形态 |
| --- | --- | --- |
| 生成一张资产图（图 4） | `⚡18` | 5 角色 + 3 场景 + 2 道具 = **10 张** |

| 生成视频 | —— | **`批量生视频` = 14 镜** |

**三条都是批量付费。** 硬约束，不得放松：

1. **[ADR-0041](../adr/ADR-0041-paid-generation-write-path.md) packet-only 两步**：
   preflight → 确认。批量的 preflight 必须给出**总额**，不是单价 ×N 让人自己乘。
2. **[ADR-0071](../adr/ADR-0071-reference-inputs-as-ordered-set.md) 方案 C**：
   没有明确声明「多图不额外计费」的 provider，`maxImages: 0` → **fail-closed 拒绝**，
   界面如实说明原因。**我们不替 provider 算钱。**
3. **报价只来自 Gateway preflight**，界面永不自算（ADR-0071 决策 6）。
4. **批量必须可中止，且已花的钱如实记账** —— 中途失败不得静默把整批标成成功。
5. CLAUDE.md：**真实花钱是唯一必须先问产品负责人的事。**
   本卡实现的是**闸门与流程**；每一次实际扣费仍由他在界面上确认。

### 7.6 订正：「批量生视频」的真实交付形态（2026-08-20，批次 4E）

**链尾走这张表时，「批量生视频」不能按原文判。** 事实是：

> **Gateway 今天只有逐镜预检，没有批量预检。** 于是 §3 要求的
> 「preflight 给**总额**，不是单价 ×N 让人自己乘」**在今天无法诚实满足**。

实施方排除了两条看似方便的路，两条都排除得对：

| 走法 | 为什么不行 |
| --- | --- |
| 逐镜取价再自己加起来 | 那**就是** §2.3 第 1 条明令禁止的「单价 ×N」 |
| 总额补一个 `0` | **是谎**（`¥0` 那个缺陷的原样重演） |

**因此它退化成真实可做的那件事**（TASK-097 §2.5h 第二条）：
说清原因，并把**今天就能用的那条路**摆在同一块上 ——
「逐镜生成，每镜自己走两步确认」。

**这一行的验收判据因此改为**：

- ✅ 界面**如实说明**为什么现在给不出总额，**不伪造**任何金额
- ✅ 同一块上给出**今天真能走**的替代路径（逐镜 + 每镜两步确认）
- ✅ 未发生任何真实扣费
- ⏳ **「一次确认整批」这个形态本身仍待 Gateway 具备批量预检** ——
  **这是能力缺口，不是本链的缺陷**。登记进
  [TASK-087 总账](TASK-087-followup-ledger.md)，
  且**必须写明它阻塞的是 TASK-095 §3 的哪一条**，否则下一个读者会以为已经做完。

**判成「做完」是谎，判成「没做」是不准确。** 按上面四条判。

## 8. 边界：向导到哪儿为止（本卡明确不做，但必须说清去哪）

**这是 §7.1 里三个 ⚠️ 的答复。** 不写清楚，第 7–9 步就会变成没人认领的空白。

### 8.1 向导覆盖九步里的 1–6，止于「批量生视频」

```
向导（本卡）        ① 剧本 ② 分镜 ③ 资产 ④ 提示词 ⑤ Storyboard ⑥ Keyframe → 批量生视频
                                                                              ↓
后期（既有页面）    ⑩ 后期交付：配音 / 环境音 → 时间线剪辑 → 交付质检
                    ⑨ 粗剪审片：连起来看
```

**理由**：向导的价值是「一条只有一个下一步的路」，而它成立的前提是
**每一步的产出是下一步的输入**。到了视频之后，配音 / 剪辑 / QC 不再是一条链 ——
音频可以与视频并行准备（产品负责人原话），剪辑要反复来回，QC 是判断而不是产出。
**把它们塞进向导会重新变成「太 busy」**，只是换了个形状。

那三步的**状态**仍由 TASK-092 的 `voiceStatus` / `sfxStatus` / `qcStatus` 承载，
所以「还差什么」在任何地方都问得出来 —— 缺的只是**向导式的引导**，不是能力。

### 8.2 第 ② 步准备的是三类，不是五类

图 3 实测只有 **角色 / 场景 / 道具** 三组 + 顶部一块**全局风格**。
对着产品负责人的五个一级分类：

| 一级分类 | 在第 ② 步 |
| --- | --- |
| 人物 / 场景 / 道具 | ✅ 三组卡片 |
| 视觉参考 | ✅ 以**全局风格**那一块的形式（风格是整集共用的，不逐镜准备） |
| **声音** | **不在第 ② 步** —— 音频在视频之后（§8.1），此时准备没有可对齐的画面 |

**这是当前的读法，不是产品负责人明说的。** 如果他要在第 ② 步就准备声音资产，
那是一个小改动（加第四组卡片），**记在此处以免被当成漏项**。
