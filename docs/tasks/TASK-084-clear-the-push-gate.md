## 2. 顶层 `reviews` 无 schema 校验

**现状（清单已确认）**：`canvasschema.js` 只校验
`production.shotProduction.reviews`；**顶层 `reviews` 的 `decisions` 水合时
只查「是不是数组」，元素形状不查**，未校验的 decision 会一路喂给 G3。

**对照物就在同一个文件里**：`deliverySpec` 同为加法字段，
却是 **present-but-wrong 即拒绝整份文档**。两个加法字段两套标准。

**要做**：`reviews` 按 `deliverySpec` 的同一条规则校验 —— **复用那条规则，
不要写第二套**。缺席允许（加法字段），**存在但形状错 = 拒绝整份文档**。

**风险：高**（持久化 / schema 校验）→ **2 轮审查 + 全量**。
**不做 schema 版本升级**（这是补校验，不是改形状）。

**测试**：合法 `reviews` 通过；`decisions` 元素形状错被拒；
**缺席仍然通过**（否则会拒掉所有现存存档 —— 这是最容易做错的一处）；
`deliverySpec` 的既有行为不变（回归）。

## 3. gate 的命令文本判定 —— 本卡只出方案

**现状（清单已确认）**：`git "commit"` 引号形式 gate 直接不跑；
`git "-C"` 引号形式的重定向检测不到。清单自己写明了根因：

> **靠正则匹配命令文本判断意图，宽了误伤、窄了漏掉，加变体不收敛**。
> 真正的修法是换判定机制（拿结构化 argv 而非原始文本）。

**这和 TASK-077 跨源那条是同一个教训**：那次也是修了两遍拼写，
第三轮才改成断言性质。**不要再加第三种写法的匹配。**

**要做（本卡范围内）**：
1. 写清楚 PreToolUse hook 能不能拿到结构化 argv（**先查，不要假设**）。
2. 如果能 —— 出一份改造方案 + 影响面（`gate.ps1` / `gate.sh` 两边行为必须一致，
   ADR-0062 决策 3）。
3. 如果不能 —— 说明退而求其次的判定是什么，以及它的**已知漏洞边界**
   （诚实标注，不假装堵死）。

**产出是方案，不是实现。** 实现另开卡 —— 改的是质量门本身，
高风险，值得单独一轮。

## 4. `studio/skills` 无 containment —— 先定语义再修

**现状（清单已确认）**：`_load_skill_catalog` 的 `studio/skills`
**junction 可指向项目根之外**。与仓库既定纪律不一致
（`_resolve_upload_file` 有严格 symlink 检查）。

**为什么不能直接修**：清单自己写明 ——

> 改动会破坏「用 junction 共享 skill 包」这种**可能合法的用法**，先定这个再动。

**要做**：
1. **先回答一个产品问题**：「用 junction / symlink 把一份 skill 包共享给多个项目」
   是不是我们要支持的用法？
   - **是** → containment 要放行显式登记过的外部目录（白名单），
     而不是一刀切拒绝；
   - **否** → 按 `_resolve_upload_file` 的同一套严格检查办，
     并在文档里写明不支持共享。
2. 定完再改，**改动本身很小**。
3. **需要本地写权限才能利用** —— 不是远程可触发的洞，
   这也是它能排在 push 之后的理由。

**风险：高**（安全边界）→ 2 轮审查。
