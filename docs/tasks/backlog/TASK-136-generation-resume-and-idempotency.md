## 为什么建议在接付费视频生成之前定

**「重启后重新提交 = 重复扣费」是必然会撞上的缺陷，不是可能。** 一次视频生成动辄几十秒到
几分钟，这段窗口里任何一次重启（开发时改代码、部署、崩溃）都会留下一条状态是 running
但没有执行体的记录。此时若把它当作「失败了，重试吧」，就是第二次扣费，而用户只看到一次失败。

本仓库今天没接付费视频生成，所以现在定成本最低；接上之后再定，第一次事故已经发生了。

## ArcReel 的三个概念（可直接借的形状）

| 概念 | 定义 |
| --- | --- |
| **孤儿任务** | 记录为执行中、但实际已没有任何执行体在跑的任务；现实成因就是服务重启 |
| **续跑** | 对**持有远端任务 id** 的孤儿任务接续轮询与下载，**不重新提交** |
| **显式失败** | 供应商侧任务已过期或找不到时，续跑**显式失败，不回退为重新提交** |

最后一条是关键：不确定的时候宁可报错，也不做一次「可能是第二次」的付费调用 ——
与本仓库 §5.8 已有的「`unknown` 禁止自动重试」是同一条纪律，只是覆盖另一个触发场景。

它还有两条配套：远端 task id 与状态**必须持久化**（否则重启后连「问谁」都不知道），
以及 image / video / audio **各自独立的并发通道**（成本与延迟特征不同，共用一个池会互相饿死）。

## 立卡时的假设错了一半（2026-09-05 写 ADR 时核出来）

立卡说的是「本仓库缺续跑语义，要从零定」。核过两侧代码之后：

- **核心库（原 M1 付费路径）三个概念全都实现完了** —— `budget/reservation.py` 的
  `record_external_task_ref` 持久化远端 id，`HELD` / `NEEDS_RECONCILIATION` 就是孤儿，
  `app/paid_coordinator.py` 的 `resume_media` 完全从预留记录重建并且**从不重新提交、
  不重新定价、不再付一次**，拿不到远端 id 时显式落 `needs_reconciliation`。
- **缺口全在 Studio 侧**：`runstore._sweep_locked` 把跨重启的运行一律打成 `failed`，
  记录里没有任何字段通向上面那条路。于是 §5.8 的 `unknown` 成了终点 —— 不知道该问谁。

所以本卡要做的**不是发明续跑**，是把 Studio 的 Run 接到那条已经存在的路上。
决策见 [ADR-0099](../../adr/ADR-0099-resume-is-not-a-retry.md)。

## IN SCOPE（[ADR-0099](../../adr/ADR-0099-resume-is-not-a-retry.md) 已细化完，按它做）

1. 「孤儿任务」的判定与它在 Run 状态机（§5.2 八态）里的位置 —— 大概率不是新状态，
   而是「running 且无执行体」的派生判断；
2. 续跑路径：持有远端 id → 接续轮询；无远端 id → 那是提交前就断了，走 §5.8 的 `unknown`；
3. 远端 id 的持久化字段（§5.3 已有字段表，看是否够用）；
4. 启动时的一次性接管，以及它与 [ADR-0095](../../adr/ADR-0095-a-run-is-picked-up-from-the-thread-not-from-a-poller.md)
   「run 是从线程里捡起来的、不是轮询器捡的」的关系 —— 这两条必须对齐，不能各自实现。

## OUT OF SCOPE

- 不在本卡接入任何付费 Provider（第 10 条：窄授权不得自行扩大）。
- 不做自动重试。本卡定的恰恰是「什么时候**不许**自动重试」。
