# TASK-135：下一步该干什么由后端说了算 —— 服务端权威工作流计划

- 状态：**待开始**（2026-09-05 开卡；没有 Agent 在做）
- Workflow：Feature · 深度：DEEP（跨前后端合同，需要独立 ADR）
- 技术目标：「现在停在哪一步、下一步该干什么」目前由前端与 Agent **各自推断** ——
  靠文件存在性、靠空的资产桶、靠对话记忆。这是一类结构性缺陷的温床：同一个项目状态，
  两个消费者算出两个结论，而且谁也不知道对方算错了。
  [工作层级输入输出合同](../../design/workflow-stage-step-io-contract.md)定了 L0–S7 的逻辑
  I/O，但没定「谁来判定当前停在哪」。
- 架构约束：`CA §3`（前后端合同）· `CA §5`（当前架构约束）
- 来源：调研 GitHub 上的 ArcReel。它的编排 Agent 有一条硬规矩，值得整条搬过来。

## 要做什么

一个后端查询返回**只读计划**：有序 `steps[]`（每步带状态 / 产物时效 / 阻断原因 / 活动任务）、
`blockers[]`、以及**唯一的 `next_action`**。前端与 Agent 都按它路由，不各自推断。

## ArcReel 那条规矩的原文形状

它在产品 Agent 的 profile 里写死了两句，两句都是从事故里长出来的：

> **不要在 profile 里另建一张按创作类型或生成模式展开的步骤表。**
> `Read` / `Glob` 只用于取执行已选定动作所需的内容，**不用于另建一套状态机**。
> 不得根据空资产 bucket、文件名、旧文件存在性或对话记忆覆盖服务端结论。

并且它为此写了一条 skill 触发 eval，assertion 类型是 `constraint`：
`does_not_infer_stage` —— 「不读 project.json、不用 Glob 探测文件系统自行推断阶段」。
**约束本身被做成了可回归的测试**，这一点比那个查询本身更值得学。

## IN SCOPE（待 ADR 细化）

1. 一个 Query（名录见[创作者系统合同](../../design/creator-system-contract.md) §8.2）返回计划；
2. `next_action` 是**唯一**下一动作，调用方不得自己从 `steps[]` 里挑一个更靠前的抢跑；
3. 与既有 `episode.board` 看板模型的关系要定清楚 —— 大概率是同源，不是第二份；
4. 一条 constraint 形态的回归测试，钉住「不靠文件存在性推断阶段」。

## OUT OF SCOPE

- 不在本卡实现任何新的执行能力，它只回答「下一步是什么」。
- 不引入持久 projection（ADR-0031 未授权）—— 计划是读时计算的派生物。

## 前置

需要一份 ADR 先定合同（编号见开卡时的下一个空位）。本卡在 ADR Accepted 前不动手。
