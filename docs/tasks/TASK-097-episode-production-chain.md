## 2. 共同机制：做一次，五段复用

**批次 0 先抽出来。** 与 TASK-094 §1 同样的道理：不抽，同一套东西会被摸索五遍。

### 2.1 「一次生成 = 一张卡」

Prompt + 参考 chip + 模型 + 规格 + **报价** + 提交，**同一张卡**。
本链有五处生成（资产图 / 提示词合成 / Storyboard / Keyframe / Video），
**全部用同一个组件**。TASK-078 批次 B 已经做了「可见」那一半，本链补齐。

**报价只来自 Gateway preflight，界面永不自算**（ADR-0071 决策 6）。

### 2.2 有序参考集合 + **用法规则**

`[[ref:N]]` 内联引用 + 每张图**声明它管什么**（构图 / 身份 / 环境 / 风格）
+ 一段**用法规则**（TASK-095 §2.3.3）。

**规则是 Skill 包的内容，不是硬编码字符串** —— 它会随经验演进。
不带规则的后果是确定的：四视图设定图会让模型画出四个视图。

### 2.3 批量付费的统一形状

本链有三处批量（一键合成全部提示词 / Storyboard 全集 / 批量生视频）。
**一套代码**：

1. preflight 给**总额**，不是单价 ×N 让人自己乘
2. 一次确认（ADR-0041 两步）
3. **可中止**
4. 中途失败**不把整批标成成功**，已花的钱**如实记账**
5. provider 未声明「多图不额外计费」→ `maxImages: 0` → **fail-closed 拒绝并说明原因**
   （ADR-0071 方案 C），**不静默降级成单图**

### 2.4 「状态只有一份」

092 的六个 status 是**唯一真相**。本链所有界面（向导进度 / 画布节点 / 故事板审片 /
⑦ 分镜表 / QC 报告）都是它的**读者**。
**守卫测试：不得出现第二份计算。** TASK-079 已经立过这条，本链不许破。

### 2.5 计数必须来自实际登记表

「还差 10 个」「1/14 已合成」「14 个镜头已就绪」—— 每一个数字**查登记表**，
不查清单上的空。

前车之鉴是本仓库自己的：`storageState` 声明「文件在」而从不核对，
存储页因此报「媒体不可用 0」。**本链每一个计数都是同一个陷阱的复现机会。**

### 2.5b 批次 0 已经把两条不变量打硬了 —— **后续批次消费它，不得重新推导**

> **2026-08-18 补记，依据是批次 0 的 15 个 P1**（全真、零驳回）。
> 本节优先级与 §2.6 同级，因为它直接决定剩下十一个批次的轮次成本。

批次 0 的 15 个 P1 **不是随机分布的**，它们只落在两条不变量上：

| 不变量 | 那批 P1 在说什么 |
| --- | --- |
| **文本 ↔ 集合必须一起改** | 最危险的一条：剔除一张参考图后重新编号，`[[ref:N]]` **静默改指到另一张图**。还有：重复条目 id、无 id 条目被静默跳过、隐式 ordinal 不参与冲突检测、`validateReferenceSet` 不校验版本与 digest |
| **账 ↔ 现实必须对得上** | 总额没币种 / 不说覆盖几条 / 与本批条数不等；免费条目 `spent: null` 永远算「未知」；中止后迟到的回执被丢弃；被拒绝的批次显示成「进行中」；结算总额为 0 时账单行被省略 |

**这两条本卡此前写成了「价值」而不是「不变量」**（§2.3 第 4 条原文是
「中途失败不把整批标成成功，已花的钱**如实记账**」）。
「如实」不可测试；「`total` 必须带币种、必须声明覆盖几条、且必须等于本批条数」可测试。
**那九个金额相关的 P1，全是那一句概括没能枚举、也不可能手工枚举出来的分支。**

这正是 §2.6.1 那条判据打在本卡自己身上：**卡里写了一句概括性的要求，
那就是一处待办的不变量，不是规格。**

**「重新推导」的判定很简单**：如果一个批次里出现了金额校验、ordinal 冲突检测、

**错的是另一半：把「省下重踩」当成了「总成本低」。**
接线本身是**独立成本**，而且它的**缺陷密度不低于领域逻辑**。

#### 因此改成一条可执行的估法（这是本节现在唯一的规范内容）

> **估轮次不要按领域逻辑复杂度估，按新增几条「跨状态 / 跨持久化 / 跨异步」的接缝估。**

这与 §2.5e 是同一件事，只是从「缺陷住在缝里」升级成了**可以事先数**：
开工前列出本批新增的接缝条数，那个数字比「这批看起来大不大」更能预测轮次。

**4G 用这条估：** 闸门 + 画布合成 + 有序参考集合 + 方案 C fail-closed
+ 接既有首帧那条路 + 新 asset kind —— **至少五条缝，且其中两条在付费路径上。**
不要因为「refset / batchpay 都已打硬」就预期它便宜。

### 2.5b-2 fail-closed 必须落在「对方真正读的那条路」上（4D 买来的，**4G 是同一个形状**）

批次 4D 最值得记的那个 P1：

> 缺用法规则的参考**写进了 `text`**，只在 `missing` 里记一句。
> 而 **`missing` 是给人看的报告，模型看的是 `text`** ——
> 那条「不带规则不要送多图」的纪律**在真正要紧的路上一次也没生效**。

**这是 `¥0` / `storageState` 那个家族的又一例**（§2.5e）：两处陈述同一件事实，
而被执行的那一处不是被检查的那一处。**「记了一笔」不等于「拦住了」。**

> **判据（实施方统一出来的那句，直接用）：
> 要它进去而它没进去 → 这一镜不算合成好了。**
> 不是「记一句 warning 然后照样送」。

**4G 的方案 C 是同一个形状，必须按这条实现**：
provider 未声明「多图不额外计费」时，**拒绝发生在真正发请求的那一层**，
不是在一份人类可读的报告里记一句然后照样送单图。
静默降级会让「用了角色设定图」这句话变成谎 —— 而那正是 TASK-077 §1.3 修掉的东西。

**4D 里另外三个同族 P1，4G / 4E 全部会再遇到一次**：

- `confirm` 只把状态推到 `running`，**一条也没跑** —— 批次永远「进行中」。
- **批次不落盘**：刷新之后报价与已花多少全没了，于是**能再确认一次** ——
  对付费批量那就是**第二次真实扣费，而没有任何一处说过第一次发生过**。
  **这是本链目前为止最接近真实损失的一个缺陷。**
- **放弃之后又自己回来**：`discard` 清了内存，序列化又从 `loadedBatches` 写回去。
  **一个 kind 只能有一个主人。**

**另记一处 §2.5e 的实例**（真实屏幕抓到）：60/60 已合成时显示的是 batchpay 的
「没能建批次」，而事实是「没有需要合成的镜头」——
**两件不同的事实共用了一句话。**

#### 结果（2026-08-20，4D 实测）：**预测错了一半，而错的那一半更有用**

实际轮次 **8 轮 / 11 个 P1**（预算 2，超额 6 轮已显式声明）。按「轮次应低于体量给人的
直觉」这条，**预测被证伪**。

| 落点 | P1 数 |
| --- | --- |
| 参考编号 / ordinal 冲突 / `[[ref:N]]` 编译与校验 | **0** |

所以**「消费而不重新推导」这条是真的省了钱** —— 批次 0 打硬的三条不变量，这一批

> **接线本身是一个独立的成本，而且它的缺陷密度不低于领域逻辑。**
> 消费一个硬模块，省掉的是「重新推导那条不变量」；**没省掉**的是「把它接进一个

一个有六个状态的界面、一处「谁拥有这个 kind」的所有权划分 —— 四条缝，11 个 P1。

#### 硬规则

1. **每个批次收口前跑上面那条扫描**，把结果填进 §4 进度表的备注。
   **数字只能减不能增**：批次结束时零调用方模块的数量必须 ≤ 开工时。
2. **链尾零调用方必须为 0。** 若某个导出到链尾仍无人调用，
   只有两条出路：**接上它**，或**删掉它并说明为什么当初判断错了**。
   **不允许「留着以后用」** —— 那正是「读起来与功能完成一模一样」的成因。
3. **新导出同批必须有真实调用方。** 批次里新增的 export，
   收口时必须能指出**一条从界面到它的非测试调用路径**。
   指不出来的，要么本批接上，要么不要在本批引入。
4. **风险最高的是 `counts`**：§2.6.2 已经写明「每个计数都有多个消费者」。
   若某批就地算了一遍计数而没走 `counts.productionCounts`，
   结果是**模块永远接不上 + 多出第二份计数** —— 两个缺陷一次性达成。

### 2.5d 「枚举 → 派生」在第二个领域被证实了一次（批次 2 的 SSRF）

实施方：**「修了六轮才从『枚举』换成『白名单』。」**
前五轮每轮以为修完了类，实际只修了当轮被指出的那个拼法
（scheme → 十/十六/八进制 → 点分十六进制 → 尾部根点 + 全段十六进制 → CGNAT）；
第六轮换成 `is_global` + 「必须长得像 DNS 名」后一次覆盖整族。

**这与 §2.6.1 是同一条**（手写的「N 项」清单会漏），
现在它在**第二个完全不同的领域**（安全）被独立证实了一次。**两个领域，同一形状。**

#### 但它带来一条 §2.6.1 没有的补充：**过严的守卫等于没有守卫**

实施方差点把 `example.ca` / `example.de` 拒掉（ccTLD 多是纯 a–f 字母，
撞上「全段十六进制」那条规则）。他的话值得逐字留下：

> **「挡住正常域名的守卫会被绕开，然后什么都保护不了。」**

因此他的测试**同时钉住两个方向**：既要拒掉绕过拼法，也要放行正常域名。

**本链的适用处** —— 每一条 fail-closed 都要钉两个方向：

| 闸门 | 也必须证明它**放行**什么 |
| --- | --- |
| ADR-0071 方案 C（provider 未声明多图不额外计费 → 拒绝） | 已声明的 provider **必须真的能用** |
| ④→⑤ Storyboard 闸门 | `skipped` 与已 approved **必须真的放行** |
| 软删除 shot 的引用检查 | 无人引用的 shot **必须真的能删** |
| QC 的时长超差 | 在容差内的 **必须不报警** |

**只钉「会拒绝」的一半，就是在造一个迟早被关掉的闸门。**

### 2.5e 缝，才是缺陷住的地方（批次 3，9 个 P1 全在这里）

实施方报告：批次 3 六轮 9 个 P1，**没有一条是领域模块的逻辑错**。
纯判定模块 `canvasnodes` 六轮**零 P1**。全部 9 条落在
**「判定」与「消费判定的人」之间的缝上**：

- `available` 却**没有处理器**
- 丢掉 prefill **却说会带过去**
- 把 in-flight 归给**没有流水线**的 stage
- 一个**只可能拒绝**的闸门

#### 这就是本项目那个缺陷家族的一般形式

把这条链和审计里的每一个缺陷放在一起看，它们是**同一句话**：

> **系统里有两处在陈述同一件事实，而它们没有共用同一份事实。**

| 实例 | 两处 |
| --- | --- |
| `¥0` 预算 | 显示 vs 真实成本 |
| 「媒体不可用 0」 | `storageState` 的声明 vs 磁盘 |
| 「模型直接输入」 | 界面标签 vs Provider 真实能力 |
| 归档扫描漏 `timelines` | 手写清单 vs 实际引用 |
| 16 / 48 | 规划页 vs 另外四个消费者 |
| 未接线模块（§2.5c） | 测试里的现实 vs 应用里的现实 |
| `removalCheck`（下面轮 4） | 测试用的谓词 vs 生产用的谓词 |
| `INCONCLUSIVE`（下面轮 5） | 文档措辞 vs 探针语义 |

**因此 4A–5B 的审查重点不在新模块里，在新模块的接缝上。** 每引入一个判定，
必须同时回答：**谁消费它？消费者能不能做到它承诺的事？**

#### 轮 4：§2.5d 被字面印证 —— 但它暴露了 §2.5d 不够

`removalCheck` 的**生产谓词**写错（把资产自己的版本记录算成外部引用），
于是什么都永远删不掉；**而测试用的是另一个谓词**，所以
「无人引用的真的能删」那一半**在测试里通过、在产品里恒假**。
实施方的话：**「闸门是 born closed 的。」**

**§2.5d 因此加一条硬约束**：

> **两个方向必须用生产那一份谓词来钉，不得用测试自己写的等价物。**
> 谓词要有名字、可导出、生产与测试共用同一份。
> 否则「钉了两个方向」这句话本身就是一处新的缝（见上表）。

#### 轮 5：根因在文档里，不在代码里 —— **而那句话是本仓库自己写的**

`INCONCLUSIVE`（问过、答不上来）被算成产物存在，闸门会在未经确认的媒体上打开。
根因是 ADR-0073 决策 2 的原措辞「探针**没有判定它 MISSING**」——**实现照它写的**。

**追溯：那句话来自 [TASK-092](TASK-092-shot-workflow-multi-stage.md) §2.2 的表**
（本卡作者写的），经 ADR-0073 进入实现。实施方订正了 ADR，
**TASK-092 的两处已于 2026-08-18 一并订正**（提交 `7f7719b`）。

> **规则：修完代码要问「这个错的说法是从哪抄来的」，然后把源头也改掉。**
> 只改代码，下一个人会照同一句话再写一遍。
>
> **仍待订正**：`src/workflow/shotstage.js:14` 的模块头注释仍以宽松措辞下定义
> （代码已正确）。留给下一个提交顺手带上 —— 读那个文件的人先读到的是那句。

### 2.5f 闸门的三条（批次 4A 买来的，**4B–5B 每一批都有状态显示，会一路复现**）

#### 一、「不知道」不是「放行」

`readyOf` 在上游答不上来时落进 `else`、给不出阻塞，于是第 ③ 步**亮着「进入」，
点进去是一个空页**。

这是 §2.5b 那条「不知道 ≠ 0」在**闸门**上的同一形状：
**不知道 ≠ 放行。**

> **每一个判定都必须为「上游答不上来」留一条显式分支，
> 而那条分支不得是宽松的那一边。**
> 落进 `else` 就是把「我不知道」实现成了「可以」。

实施方顺手做对了两件事，都要在后面的批次保持：
- 上游要求**从手写改成由步骤次序派生**（§2.6.1 —— 这次手写清单漏的正是
  「第 ③ 步有没有检查上游是否可知」）。
- 判定提成**导出的纯函数 `stepReadiness`** —— §2.5d 要求钉住的必须是**生产用的
  那个谓词**；藏在 `app.js` 闭包里，测试只能钉一份等价物，**那本身就是新的一条缝**。
  变异证明 14/15。

#### 二、`blockers` 只表示「开始不了」——**不要把用户要做的工作印成拦住他的理由**

它的镜像，**测试全绿、只有看真实屏幕才抓到**：把「自己还没做完」也算成阻塞，
于是第 ② 步 —— **正是此刻该做的那一步** —— 顶着一句
「还不能开始这一步 · 还有 1 个没有设定图」。

> **这一步自己的待办 ≠ 这一步的阻塞。**
> 前者是「你要做的活」，后者是「你还不能开始」。**混起来，界面就在拦住它请你做的事。**

**4B–5B 的适用面（每一批都有）**：分镜表的「还差几镜」、资产准备的
「还差 10 个设定图」、Storyboard 的「还有几镜没通过」、Keyframe 的闸门提示、
QC 的缺口 —— **每一处都要先分清它是待办还是阻塞。**

#### 三、同一件事被决定两次 —— 兜底默认值会压掉真正的决策

「打开在哪一步」被决定了两次：shell 的 `|| "shots"` **压掉了**模型选的
「第一个没做完的那一步」。

这是 §2.5e 那张表的又一行（两处陈述同一件事实，没共用同一份）。
**特殊之处在于其中一处是「兜底默认值」** —— 它看起来无害，
实际上把上游的判断静默丢掉了。

> **写 `|| 默认值` 之前先问：上游是不是已经决定过了？**
> 如果是，兜底就不是兜底，是覆盖。

**另记一条**：`ctx.wizard` 被文件后面的旧演示向导**静默覆盖**（已改名 `prodWizard`）。
应用长大之后命名空间会撞，而撞了**不报错、只是行为变成另一个**。
本链后面几批还会往同一个 `ctx` 上挂东西 —— **挂之前先 grep 那个名字。**

### 2.5g 派生扫描替代不了「单一事实位置」（2026-08-19，第九例，**这次的受害者是本卡作者**）

交接前查待复审清单，本卡作者判定「仅剩两条未闭合」并据此写进交接指令。
**两条都在 2026-08-16 就已补审完毕**，证据在磁盘上
（`.claude/tmp/codex-rereview/F-runs-registry.out`、修复提交 `dfb6d2a`）。
差一点让两轮已经做过的审查被重跑一遍。

**成因是 §2.5e 那条缺陷的文档版本**：同一件事实记在**同一份文档的三处** ——
表格的状态列、下面的「已补完」节、「仍然待办」节 —— 而**只有后两处更新过**，
状态列停在 2026-08-14。

#### 这暴露了 §2.6.1 的一条边界

§2.6.1 说「手写清单会漏，要派生」。本卡作者照做了 —— 用 `grep` 去扫清单。
**但那个 grep 本身就是手写的模式匹配**：它匹配的是表格行的状态列文字。

> **派生扫描能替代手写清单，只在被扫的是「结构化事实」时成立**
> —— 引用关系、import、登记表记录。
> **扫自然语言的状态列，它仍然是手写的**，只是换了个地方手写。

#### 因此对文档的正确修法不是「更好的 grep」，是**单一事实位置**

实施方的处理是对的：状态列**逐行划掉并指向证据**，表头加订正
——「欠账只看『仍然待办』节」。**一件事实，一个位置。**

**本链适用**：`§4 进度表`、`§2.5c 接线账`、待复审清单、
`TASK-095 §7 对账表` —— 这四处都是「同一件事实可能被记两遍」的地方。
**每次更新，更新那一个位置；其余位置只许指过去，不许复述。**

#### 四、链令牌跳过的那部分，缺陷会**攒到链尾**——除非把它挪进定向集

**2026-08-20 实测**：4F 的提交 `3baee7b` 引入了 `studio.css` 五处 `var(--muted)`，
而 `--muted` **在 tokens.css 与 studio.css 里都没有定义**
（这个代码库的词汇表是 `--text-faint` 136 处、`--text-dim` 57 处）。

- 那五处 `color` 失效、继承父色 —— **屏幕上仍然渲染**，
  所以「看真实屏幕」（§2.6.4）**这次没抓到**。
- 抓到它的是既有的 CSS token 守卫，而那条守卫在 **pytest** 里。
- 4F 是中间批次，按 ADR-0068 带了 `MOTV_CONTINUOUS_CHAIN=1`，**跳过全量 pytest** ——
  于是它一直到本卡作者提交一份**纯文档**（没带令牌、因而跑了全量）时才露出来。

**链协议按设计工作，问题不在协议。** 但它有一个可预期的后果：

> **凡是「只有全量能抓、定向抓不到」的守卫，缺陷会一路攒到链尾。**

**可执行的对策**（剩下 4G / 4E / 5A / 5B 照此）：

> **批次动了哪一类文件，就把那一类的守卫拉进本批的定向集。**
> 动 CSS → 带上 CSS token 守卫；动 Skill 包 → 带上 digest / drift 守卫；
> 动持久化 → 带上迁移与 schema 守卫。
> **不要依赖链尾去发现本批就该发现的东西** —— 链尾发现它时，
> 你已经离开那段代码好几批了。

### 2.5h 批次 4F 买来的（2026-08-20，派工口述，按原编号记下）

> 本节由产品负责人在 4G 的派工里口述。**第三条当时没有传达**，所以这里只记一、二、四
> 三条，编号保持他给的那套 —— 以后引用「§2.5h 第二条」不会指错。

#### 一、**一处承载两件不同的事实**，和两处陈述同一件事实一样致命（§2.5e 的镜像）

4F 正踩在这上面并且拆对了：`reviews[shotId]` 记的是**审片对某个视频**的判断，
而 ④ 的草图也要「通过」。共用那一格的后果是：创作者一旦通过视频，草图那一格就
翻回未通过 —— **④→⑤ 的闸门在视频做完之后自己关上。**

> **合并前先问：这两件事会不会分别为真？**
> 会 —— 那就是两个格子。`keyframe` 的通过、`storyboard` 的通过、视频的通过是
> **三件不同的事实**，不要因为都叫「通过」就并进一个格子。

#### 二、闸门关着的时候，界面要退化成**真实可做的那件事**

多图路线在当前 provider 上没有授权时，屏幕上不该出现「已提交合成」。
4F 的**任务单**是正确形态：说明原因 + 这一镜**真实可走的那条路**（复制提示词、
外部出图、回来上传）。

> 「已提交」是一句关于未来的承诺；任务单是一件现在就能做的事。
> **闸门关着时给后者。**

#### 四、动了 CSS，就把 **CSS token 守卫**拉进本批的定向集

4F 新写的五处 `var(--muted)` 是**未定义变量**（本库词汇表是 `--text-faint` 与
`--text-dim`）。那五处 `color` 因此失效、继承父色 —— **屏幕照样渲染**，所以
「看真实屏幕」没抓到它；抓到它的是 pytest 里的 CSS token 守卫，而 4F 带链令牌
跳过了全量。

> **「看真实屏幕」抓不到「样式静默失效」**：两者的盲区不重叠。
> 本批改了哪一层，就把那一层的守卫拉进定向集 —— 定向集不是「跑得快的那些」，
> 是「能看见本批改动的那些」。

### 2.5i 批次 4E 的三条（**5A / 5B 全部适用**）

#### 一、单数形态的所有权，在**第二个成员出现时**崩塌

4D 只有一种批量，于是「摘掉自己那一种」是**一个字符串**。
4E 加进第二种，那句话就必须摘**两种** —— 漏一种的后果与 4D 轮 5 那个
「放弃之后又自己回来」**一模一样**（`discard` 清了内存，序列化又写回去）。

实施方在它咬人之前把所有权**改成了集合**。

> **判据：一个「我拥有哪一种」的字段，只要将来会有第二种，今天就写成集合。**
> 单数形态不是简洁，是一个等着第二个成员到场的缺陷。

**5A 直接适用**：它一次加进 **voice 与 sfx 两种** —— 第二个成员当场到场。

#### 二、挂载位置的混淆，这是**第三次**了 —— 结构问题，不要等链尾

`shotwork` 这一页**自己切 section**，而模块表里**另有一个 `video:`**。
4F 踩过、4E 又踩了，实施方标注为**同一处混淆的第三次**（真实屏幕抓到）。

**三次同形不是三次意外。** 与 §2.5h 第三条同源：
**锚点是「今天所处的位置」而不是「它要挂的那个事实」。**

> **5A / 5B 挂任何东西之前，先确认这一页的 section 由谁切、模块表里有没有同名的一条。**
> 这条已经花掉三次真实屏幕核对的成本，不要再花第四次。

#### 三、审查预算的正确读法（实施方的选择是对的，在此确认）

4E 高风险预算 2 轮，实施方**只用了 1 轮**：轮 1 pass 零发现，
**没有 P2 修复可复审**，重审一个未变的 diff 是纯浪费。

**这个读法正确。** §3 与 ADR-0069 决策 3 说的是
「**高风险的 P2 修复**必须用掉剩余那一轮」——
那一轮的用途是**复审修复**，没有修复就没有复审对象。

> **明确写下来免得下一批再推一遍**：
> 剩余那一轮是**为 P2 修复保留的**，不是必须消耗的配额。
> 轮 1 pass 且零修复 → **收口，不再开轮**，并在 §4 注明是显式选择而非漏跑。
> 有 P2 修复而不复审 → **违规**。

### 2.5j 批次 5A 的两条（**5B / 链尾适用**）

#### 一、fixture 发明的形状会让**生产**说谎，而测试永远是绿的

`counts.js` 的 `stageCount` 读的是 `board["videoStatus"]` 这样的键；生产传进来的
`ctx.shot.stageBoard(shotId)` 键是 `video` / `keyframe` / `storyboard`，`status` 在值里。
那个键**在生产的 board 上根本不存在** —— 于是 ④⑤⑥ 三个计数
**永久是 0，而 `known` 为真**：一个我们没资格做的断言，正是 `counts.js` 文件头
那段 `storageState` 教训的同一形状。

而单元测试一直是绿的，因为它自己造了 `{ storyboardStatus: "completed" }` ——
**一个生产里不存在的形状**（§2.6.3 第二次现形，这次的代价是三个计数）。

> **判据一：跨模块的读模型，fixture 必须由生产的那个函数产出。**
> `stageOf` 的形状由 `shotstage.stageBoard` 决定，那么测试就该调它，
> 而不是手写一个「看起来像」的对象。手写的那个只证明代码能读懂自己想象的输入。
>
> **判据二：形状不认识时返回「不知道」，不是 0。** 这是「不知道 ≠ 0」在**读取**这一端
> 的形状 —— 下一次形状再变，屏幕会显示「—」，而不是静默地少数一半。

#### 二、独立审查的误报也有**系统性**的一种：diff 窗口伪影

5A 两轮 codex 都把 `FINALIZE_DEPENDENCIES` 报成模块加载期的 TDZ `ReferenceError`，
而声明顺序本来就是对的（`STAGE_DEPENDENCIES` 在第 81 行，它在第 160 行）。
成因：审查者读到的是 **diff 的窗口**，而那个未改动的 `const` 声明不在窗口里。

> **两轮同形不是两次巧合，而是审查者的输入结构决定的。**
> 处理方式：**用可执行证据反驳**（import 正常 / 前端 1715 全绿 / 真实项目 0 page error），
> **不为一条误报改动正确的代码** —— 那样做才会真的把 bug 引进来。
> 但要在原地写下这条约束（「这一块必须留在依赖表之后」），
> 让下一个人（和下一个审查者）看得见它。

### 2.5k 批次 5B 的三条（**链尾适用**）

#### 一、守卫把代码原样抄回来，等于没有守卫

5B 第一版写成 `ctx.episode.references(shotId)` —— **那个方法不存在**
（真正的是 `ctx.shot.references`）。而我为它写的守卫是：

```js
assert.match(region, /ctx\.episode\.references\(shotId\)/);
```

**1726 项测试全绿**，真实屏幕上整块面板炸掉：`ctx.episode.references is not a function`。

这条守卫只证明了「我写下了这个字符串」。它与被测代码引用的是同一个错误名字，
所以它永远同意。§2.5f 第三条早就说过「往 ctx 上挂一个名字之前先 grep 它」——
本批的新发现是**守卫本身也会犯这个错**，而且犯了之后看起来更安全。

> **判据：守卫不得把被测代码的字面量抄一遍当作断言。**
> 它要问一件**独立可查**的事。这里改成了：本批调用的每一个 `ctx.x.y(`
> 在 `app.js` 里都必须**另有调用方**（本批不引入新的 ctx 能力，只消费既有的）——
> 我凭空发明的那个只会出现在这一处，于是当场被抓。

#### 二、为子集发明的词汇，在集合变大的那一刻开始说谎

5A 给 `postPhase` 造了 `waiting`（等画面对齐）：`completed` 但 `canFinalize` 为假。
那对配音 / 音效成立。5B 第一次把 **`video`** 放进同一份派生，它立刻错了 ——
`video` 没有对齐前置，于是 `canFinalize === canStart`，一条**已经有视频**、
但关键帧从未做过的镜头被读成「等画面对齐」（真实含义是：产物在，上游那道闸门
此刻已经无意义）。

修法不是给 `video` 开特例，而是**把「有没有对齐前置」从 `FINALIZE_EXTRA` 派生出来**
（`hasAlignmentGate`）。

> **与 §2.5i 第一条同源，隔了一批复现**：单数形态的所有权在第二个成员到场时崩塌；
> 为子集发明的词汇在集合变大时崩塌。**判据一样：今天就问「这套说法对全集成立吗」。**

#### 三、审查脚本「退出码 0」不等于审查跑了

5B 的第一次审查启动**没有跑起来**：PowerShell 的工作目录不是仓库根，
相对路径的 `.ps1` 找不到，而包装进程**照样 exit 0**。
输出里只有一句 "The argument … does not exist"，没有任何 `VERDICT:` 行。

> **判据：只认 `VERDICT:` 那一行。** 退出码、任务「completed」通知、
> 日志里有几行，都不是审查发生过的证据。启动用**绝对路径**。
> （这一条恰好是 skill 自己写的：「No parseable `VERDICT:` line → treat as fail」。
> 本批是它第一次真的救了一批 —— 否则 5B 会以「审查通过」进链尾，而它一轮都没跑。）

### 2.6 从 TASK-094 那条链买来的三条教训（2026-08-18，**本节优先级高于 §2.1–2.5**）

094 那条链 10 个批次、codex 每轮独立审查、链尾 3278+6 项 pytest 与 1452 项前端全绿。
**它交出的最有价值的东西不是代码，是下面这三条** —— 本链有 13 个批次，
同样的陷阱有十几处复现机会。

#### 2.6.1 任何「检查这 N 项」的清单都是可疑的 —— **要派生，不要手写**

094 的收口卡给了四项核对清单（剧本 / 分镜 / 资产绑定 / 生成记录），
**漏了 `timelines`**，而 `timelines` 引用着四个剧集。
实施方把核对做成**派生扫描**，第一次跑就抓到了。
**手写清单会归档掉仍被引用的剧集。**

**本链的适用处（每一处都必须派生，不得手写枚举）**：

| 处 | 不得手写的是 |
| --- | --- |
| §2.5 的每个计数 | 「哪些登记表算作有内容」 |
| ⑤ Keyframe 的输入 | 「哪些资产参与合成」 |
| TASK-096 §2.4 的 QC 缺口 | 「哪些 status 算缺」 |
| 新增 `storyboard` / `keyframe` kind | 「哪些地方消费 asset kind」 |
| 软删除 shot | 「哪些地方引用 shotId」 |

**判据**：如果我在卡里写了一个「N 项」的列表，**那就是一处待办的派生**，不是规格。

#### 2.6.2 每个计数都有多个消费者 —— **改一个，其余继续说谎**

094 的实测：分集规划页已经显示 16，而**rail 徽章、「共 48 集」、EPISODES 列表、
Director 四处仍然显示 48**。这与审计里 GAP-06（目标 24 / 规划 12 / 实体 48
三个数字互不校验）是**同一个形状**。

**本链每引入一个数字，必须先枚举它的全部消费者并一起改**：
`14 个镜头已就绪` / `0/10 已生成、还差 10 个` / `1/14 已合成` /
Storyboard 通过数 / Keyframe 通过数 / 视频完成数 —— 每一个都要问
**「还有谁在显示这件事」**，而答案要**派生**（见 2.6.1），不是回忆。

#### 2.6.3 守卫会静默失效，而 fixture 会**发明字段**

094 查出三个**已经什么都不拒绝**的守卫：一个版本钉死的 digest 测试、
一个只认 version 1 的 `skill_digests()` 查表、一个名为「outline cap works」
实际在量 `prompt.md` 长度的断言。**它们全是绿的。**

**更值得记的是实施方自己那个 `finishedAt` bug**：
测试 fixture **发明了一个不存在的字段**，于是守卫保持绿色，而界面是错的。

**本链的纪律**（本链几乎每个批次都靠守卫测试守着不变量，因此这条是硬约束）：

1. **守卫必须派生**，不得钉死版本号、字段名清单或计数常量 ——
   钉死的守卫会在下一次版本变更时静默变成永真。
2. **fixture 必须从真实文档构造**（真实项目的导出或它的裁剪），
   **不得手写一个「看起来像」的对象** —— 手写的 fixture 会发明字段，
   于是守卫在校验一个产品里不存在的世界。
3. **每个新守卫都要有一次「它真的会拒绝」的证明**：
   先让它失败一次，再让它通过。
   （本仓库已有先例：`tests/test_motv_banner_narrow_console.py` 的第一个测试
   就是证明那个隐患真的会复现的控制测试。）

#### 2.6.4 顺带：**去看真实屏幕**，测试不替代它

094 在真实项目上看屏幕，查出四个全部测试都放过的缺陷：`标题` 列渲染成空、
每一行都在训人「0 条 · 少于建议的 3～6 条」、`故事核心` 同一段打印两次、
以及 2.6.2 那个 16/48 不一致。

**本链每个批次收口前必须在 `照见未明rev2` 上真的打开看一眼**，
不是「测试绿了」。这与 AGENTS.md 第 20 条「真实 Connected Project 是主要验收环境」
同一条，但 094 证明了它**不是形式主义**：四个缺陷里没有一个是测试能抓的。

### 6.6 §2.5b 那个可证伪预测的最终账

§2.5b 预测：消费已打硬的模块 ⇒ 后续批次的 P1 会显著少。**结果是被证伪了一半**，
而且四批数据给出了一个更好的估法：

| 批次 | 新接的缝 | 轮数 | P1 | 落点 |
| --- | --- | --- | --- | --- |
| 4D | 多（跨状态 / 跨持久化 / 跨异步 全有） | 8 | **11** | **全部在新接的线上**，0 个在已打硬的不变量里 |
| 4F | 中 | 3 | 1 | 新接的线（`request()` 说了一件不成立的事） |
| 4G | 6 条（其中 4 条是「消费一个已打硬的判断」） | 4 | 4 | 3 条在缝上 + **1 条是我自己把 fail-closed 改成了 fail-open** |
| 4E | 几乎没有新缝（复用 batchpay 全套） | 1 | **0** | — |
| 5A | 2 条（新证据通道 + 新判定词汇） | 2 | 0（两轮同一条误报） | — |
| 5B | 3 条（新判据 × 三种证据来源） | 3 | 1（真实屏幕抓到，不是审查抓到） | ctx 上一个不存在的方法 |

> **结论：预测「消费能省事」对**（0 个 P1 落在 refset / batchpay / counts 的不变量上），
> **但「所以批次会便宜」错** —— 成本几乎全部来自**新接的缝的数量**，与领域大小无关。
> 4D 的 11 个 P1 和 4E 的 0 个 P1 是同一条规律的两端。
