## 0b. 这条解开了审计里一个悬着的矛盾

审计第一轮的结论是「**不要把项目变成一块画布**」——依据是 LibTV 那部 2 分 56 秒的
《黑翼天使终章》：创作者**手工复制了 20 遍相同的 5 节点结构**、手工编号
`1没有日出的圣城…20没有神的第一场日出`、用 `- 副本` 手工管版本、再手工排成网格。

产品负责人这句话给出了正确的粒度，**两者不再矛盾**：

```
跨集 / 跨镜的结构      →  Episode / Scene / Shot 真实模型     我们的优势，保留
一个 Shot 之内的制作   →  一块画布                            LibTV 的优势，借
```

**而那 20 个手工复制的组，本来就是 20 块 shot 画布** —— 手工模拟出来的，
因为 LibTV 没有 shot 模型。**我们有，所以每个 shot 自动拥有一块画布，
创作者一次都不用复制。** 这是我们相对目标产品在这一点上的实际优势，不是妥协。

---

## 0c. 「一个 shot 一个画布是不是有点奢侈了」——产品负责人同日追问

> 「一个 shot 一个画布是不是有点奢侈了。」

**取决于「画布」指什么，而这决定本卡最重要的一条纪律。**

| 画布是 | 成本 |
| --- | --- |
| **要管理的文档**（起名、导航、维护） | 12 集 × 30–60 镜 = **360–720 个文档**。**比没有画布更糟** |
| **派生视图**（从 records 算出来） | **零**。720 个镜头和 1 个镜头一样便宜 |

LibTV 的画布是**前者**——149 个节点是创作者手工摆的，所以他只有 4 块画布，
而那 20 个镜头组是他自己复制出来的。

**我们的是后者**：`shotgraph` 今天没有画布文档、没有名字要起、没有东西要维护。
点到哪个镜头，那张图就在那儿。

### 因此本卡的第一条纪律（比任何交付项都优先）

> **骨架永远派生。用户只能在骨架上加东西，而且加的东西也写回既有登记表。**
> **不是「一块空白画布，你随便摆」。**

一旦用户摆的节点变成自由文档，就真的有 720 个文档要管了 —— 那正是产品负责人
担心的「奢侈」。§3.1 与 §6 的守卫测试都指向这一条。

### 顺带：Storyboard 的连贯性检查需要不止一个镜头

产品负责人给 Storyboard 列的六条确认项，最后一条是**「前后 Shot 接起来是否顺」**
—— **Shot 级画布看不见这个**。所以正确形态是**两层，不是二选一**：

```
Shot 级    制作链：参考 → Prompt → 主帧 → 视频     shotgraph（已存在，派生）
Scene 级   横着看的带子：前后接不接得顺             ⑨ 粗剪审片的三列形状（已存在）
```

**两层都是派生视图，都零文档零维护。** 一个答「这一镜怎么做出来」，
一个答「这几镜连不连得上」（后者即 TASK-092 §2.7 第 3 条）。

`src/workflow/shotgraph.js`（651 行）文件头第一行：

> 当前 Shot Production Graph（TASK-065 §9 / §10）—— 「这一个镜头怎么被做出来」
> … a second READ MODEL over the same records, **scoped to ONE shot**,
> laid out as the production chain actually runs（Image First → Video）

它已经：**一镜一图**、按真实制作链布局、节点是 参考 / Image Prompt / 主帧 / 视频，
渲染在 ⑧ 镜头制作的中栏（截图里那个「S1-01 … 制作流程图」）。

**缺的是一件事**：它自称 **READ MODEL** —— 只读投影，不是能干活的画布。
不能自由加节点，节点自己不是生成器，没有「从这个生成下一个」。

## 2. 从 LibTV 借什么（都有实测截图，不用重新调查）

产品负责人：「shot 的设计和资产准备可以参考 libtv 的内容」。
目标截图登记在 [manifests/screenshots.md](../../src/ui-gap-audit/manifests/screenshots.md)。

### 2.1 Shot 设计 —— 节点自己就是一个生成器（T-047）

LibTV 选中一个图片节点时，**一张卡上同时有**：

```
[参考 ①②③ 缩略图 chip —— 内联在 Prompt 文本里]
[Prompt]
[模型 General image Pro]  [21:9 · 2K · 1张]  [⚡14]  [提交]
[高级设置 / 联网搜索 / 智能引用]
```

节点标题栏常驻 `AI生成` 徽章 + `2752 × 1536` 尺寸。

**我们的对应工作已经排好，本卡只负责把它放到画布节点上**：
- 参考内联进 Prompt（`[[ref:N]]`）+ 模型/规格可选 + 报价常驻 → **ADR-0071**
- 一次生成 = 一张卡 → **TASK-078 批次 B**（已完成「可见」，「可选」因 ADR-0041
  packet-only 停在停止条件，见那张卡的 §3）

### 2.2 「引用该节点生成」——通用链式（T-080）

LibTV 任意节点右侧 `⊕` → **「引用该节点生成」** →
`文本 / 图片 / 视频 / 智能剪辑 / 导演台 / 逐帧拉片 / 音频 / 脚本 / 参考节点`。
**任意类型 → 任意类型，一个统一动作。**

我们今天只有**一条**：资产「🎬 用作视频首帧」。
这是 **GAP-19**（[TASK-087](TASK-087-followup-ledger.md) 已登记），
本卡把它实现在 shot 画布上 —— 那是它最自然的位置。

### 2.3 自由添加节点（T-020 / T-050 / T-051）

LibTV：`文本 / 图片 / 视频 / 智能剪辑 / 导演台 / 逐帧拉片 / 音频 / 脚本▸ / 素材库▸`
+ `上传` / `从生成历史选择`。

**我们只做当前能力覆盖的那几种**：文本 / 图片 / 视频 / 音频 / 参考。
逐帧拉片与 3D 导演台**明确不做**（[ui-correction-plan §0.2](../../src/ui-gap-audit/reports/ui-correction-plan.md)：
需视频理解 / 3D 引擎，超出当前授权）。
**不可用的类型灰掉并写出原因，不隐藏**（TASK-079 §1.2 的既有姿态）。

### 2.4 资产准备（T-024 / T-023 / T-048 / T-022）

产品负责人点名的第二半。LibTV 有四样：

| LibTV | 我们 | 归属 |
| --- | --- | --- |
| **角色库**：20+ 预设原型 × 全身图/面部特写/表情九宫格/人物呈现板 ×「应用至画布」 | 无 | GAP-17 / [TASK-083](TASK-083-phase3-adrs-first.md) ADR-C |
| **图上右键「创建主体」**（从一张图升格成可复用角色） | 无 | 同上。**这条用户价值高、范围窄，建议先做** |
| **风格库 / 特效库**（可「新增风格节点 / 新增特效节点」） | 无 | GAP-16 / ADR-B |
| **我的工具箱**：运镜/特效预设（左弧滑行 / 360旋转 / 瞳孔拉近…） | 无（运镜是自由文本，真实项目 60 镜**填充率 0/60**） | GAP-16 / ADR-B |

**这四样都需要 ADR，不在本卡**。本卡负责的是：**画布上要有它们的入口位**，
以及 §2.5 的那条纪律。

### 2.5 五个一级分类落在画布的参考区

产品负责人同一轮定的：**人物｜场景｜道具｜视觉参考｜声音**（`referenceType` 区分）。

**零迁移**（`kind` 数据不动，界面派生分组；真实项目只用了 `character-reference`），
**但必须保住一条事实**：合并进「视觉参考」的五个横跨 `ROLE_USE` 分界——
`style` 的图**进模型**，`video-style` / `motion` / `camera` / `performance` 的
**不进模型**，只被 Skill 读成 Prompt 里的文字。
**合并的是归类，不是那个事实**（TASK-077 §1.3 修的正是这个谎）。

## 3. 交付

1. **`shotgraph` 从只读投影变成可编辑画布**：保留它现有的自动布局（那是我们的优势——
   节点从 records 派生，不用手工搭），**加上**自由添加/连接节点的能力。
   **不新建第二份状态**：画布上的节点仍然是 records 的投影，新增节点写回既有登记表。
2. **节点 = 生成器**（§2.1）：Prompt + 参考 chip + 模型 + 规格 + **报价** + 提交同卡。
   报价仍只来自 Gateway preflight（ADR-0071 决策 6 的不变量）。
3. **「以此生成 →」**（§2.2）：落点必须**预填输入**，不可用的组合灰掉并说明原因。
4. **节点上标事实**：`AI生成` / 尺寸 / 模型 / **092 那六个 stage 的状态**
   —— 画布是那六个状态最自然的显示面。
5. **参考区按五个一级分类**（§2.5），并如实标注「进不进模型」。
6. **资产准备的入口位**（§2.4）—— 位置留出，能力等各自的 ADR。

## 4. OUT OF SCOPE

- 六个 stage 的状态模型本身 —— TASK-092（本卡的前置）。
- 参考数组化 / Provider 多图 —— ADR-0071（Proposed，等付费口径拍板）。
- 角色原型库 / 运镜风格特效预设库 / 从图创建角色 —— 各自的 ADR（§2.4）。
- 逐帧拉片 / 3D 导演台 —— 明确不做。
- **整集级的画布** —— 产品负责人说的是「不同的 shot 对应不同的画布」，
  不是「一集一块画布」。整集的面是 TASK-091 的九步 rail 与 ⑨ 的故事板。

## 5. 风险分级

**高**：从只读投影变成可写面 = 新增写路径 + 资产/生成登记 + 跨层合同
→ **2 轮审查 + 全量**。

分批次：
- **A**：`shotgraph` 可编辑（加节点 / 连线 / 写回既有登记表），节点仍显示现有信息
- **B**：节点 = 生成器（§2.1）+「以此生成 →」（§2.2）
- **C**：五分类参考区 + 六 stage 状态上节点 + 资产准备入口位

## 6. 测试

- 画布上新增的节点**写回既有登记表**，不新建第二份状态（守卫测试）
- 自动布局仍然从 records 派生 —— 删掉一条 record，对应节点消失（不是留一个孤儿）
- 「以此生成 →」的每个落点**确实预填了输入**；不可用组合给出原因而不是消失
- 参考区的五个分类是**派生**的（`categoryOf(kind)`），`kind` 数据未被改写
- 「视觉参考」里 `style` 与其余四个的「进不进模型」**分别显示正确**（对着 TASK-077 §1.3）
- 报价来自 preflight，不是画布自算（沿用 TASK-078 批次 B 的守卫）
- 节点上的状态与 TASK-092 的六个 stage **同源**，不新建第四份真相
