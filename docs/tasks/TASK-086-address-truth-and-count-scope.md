## 1. `capture_current.py` 在生产误导性证据（**最要紧的一条**）

**实测（2026-08-16 重抓 24 张）**：

```
07-episode-workbench.png  →  实际落点 #/照见未明rev2/story/brief?...
08-provenance-graph.png   →  实际落点 #/照见未明rev2/story/brief?...
```

两张名叫「制作台」「生成溯源」的截图，**里面是「项目与创意」页**。
`capture.json` 里记了落点地址，但**没有把它标成 finding** —— 工具照常写图、照常报成功。

**根因**：`resolveModule("workbench")` 返回 `{module: PAGES[0], resolved: false}`，
而工具**不看 `resolved`**，拿着 fallback 就去截图了。

TASK-081 §5 写的是「**落回落地页**的情况记为 finding 而不是伪造一张截图」——
但它落的是 `brief`（`PAGES[0]`），不是落地页，所以那个检查没触发。

**要做**：
1. 导航前检查 `resolveModule(module).resolved`；`false` → **记 finding，不截图**。
2. 导航后再核对一次实际 hash 与请求 hash 的 module 段；不一致同样记 finding。
   （**两道都要** —— 第一道防「工具自己解析错」，第二道防「应用落到别处」。）
3. 已经存在的 `07-episode-workbench.png` / `08-provenance-graph.png` **删除**，
   不要留着当证据。

> **这是审计工具在做审计要防的那件事。** 优先级高于下面两条。

## 3. 项目卡「0 镜」与看板「60 个镜头」

**实测（同一项目、同一次运行）**：

| 位置 | 数字 |
| --- | --- |
| 落地页项目卡（`landingcard.js`） | `48 集 · **0 镜** · 0 已生成` |
| 本集看板（`#/…/episode/board/overview`） | **`60 个镜头`** |

**两个都不算错，但读者只有一个。**
`landingcard.js:41-49` 的注释写明它数的是「**the shots its scenes really own**」
（`scene.shotIds` 去重）。真实项目 60 个镜头**全部未归入任何场景**，
所以 `shotIds.size === 0`。

**为什么这是缺陷而不是口径差异**：创作者拆了 60 个镜头，回到落地页看见
**「0 镜」**，读到的是「我什么都没做」或「我的分镜没了」。
这与 GAP-06（分集规划同屏三个「集数」）是同一族 —— 这个项目已经因为
**同一个词指两件事**吃过一次亏。

而且对照 `夜班沉默` 卡上写的是 `1 集 · 3 镜 · 1 已生成`（它的镜头有场景归属），
**不一致只在未归组的项目上显形** —— 最容易漏测的那种。

**要做**：
1. 项目卡改成数**存在的镜头**（`draftShots`），或**两个都写**
   （`60 镜 · 0 已归组`）。**不要只留一个没有口径的数字。**
2. 与看板的口径**对齐或显式说明差异**（守卫测试：两处对同一项目不得
   给出无解释的不同数）。
3. `landingcard.js` 那段注释很准确 —— **保留它**，但把「为什么这个口径对读者是对的」
   补上，或按 1 改口径。

**风险：低**（纯展示）→ 不强制审查，但要有守卫测试。
