## 2. 交付

### 2.1 rail 顺序改成「作品设定在最后」

```
今天：项目与创意 → 故事大纲 → 作品设定 → 分集规划 → 本集剧本
改成：项目与创意 → 故事大纲 → 分集规划 → 本集剧本 → 作品设定
```

- 只改 `NAV[0].items` 的**顺序**，**不改成员集合** —— 因此不碰
  `PAGES.length === 11` 那条冻结守卫（`workspaces.test.mjs`），**不需要 ADR**。
- `resolveModule` / 地址 / 历史键**全部不变**（TASK-086 已让每个键有稳定地址）。
- 顺序在测试里是**断言过的**（`workspaces.test.mjs` 断言 `NAV[0].items` 的键序），
  **改断言是本卡的正当范围**，但必须在卡里写明「规则变更由产品负责人决定，本卡执行」
  —— 不得当成「为通过而改」。

### 2.2 `script-breakdown` 加 `assets` 输入

这是产品负责人那句「**根据已经上传的资产**」的落点。

- `manifest.json` 的 `optionalInputs` 加 `assets`；**发新版本**（ADR-0067：
  已被历史 Run 引用的版本不得原地覆盖）。
- `prompt.md` 要求它：识别出的人物/场景地，**先尝试连到已有资产**，
  而不是提议一个重复的新条目。
- 端点侧把资产清单映射进上下文（`_PAYLOAD_TO_CONTEXT["bible-breakdown"]`
  今天只给 `episodeScript`）。
- **`asset-librarian` 不要合并进来** —— 它是「给资产提分类/标签建议」，
  职责不同（ADR-0067 的 Skill 单一职责）。

### 2.3 `relationship-director` 接上入口

能力已存在、输入齐全，**界面上没有任何地方能叫它**。

- 在作品设定的「人物关系」区给一个主行动：**「AI 梳理关系（按当前剧本）」**。
- 产出仍是**提案**，逐条确认；**已确认档案绝不被静默覆盖**（M8 提案卡既有纪律）。
- 提案要能表达「**关系变了**」而不只是「新增关系」——
  产品负责人：「人物关系应该是随着剧情推进有变化的」。
  落到既有的**各集关系推进**结构上，不新建第二份。

### 2.4 世界观梳理 —— **需产品负责人先定一件事**

`worldws` 有页面，没有 AI 能力。两条路：

| | 做法 | 代价 |
| --- | --- | --- |
| **A** | 扩 `relationship-director`，让它同时梳理世界规则 | 不增加能力数。但「关系」和「世界规则」是两种判断，混在一个输出里会互相稀释 |
| **B** | **新增 `world-director`** 能力 | 单一职责（ADR-0067 的姿态）。能力从 21 → 22 |

**实施 Agent 建议 B。** 但这条**开工前要产品负责人点头**——它改的是能力目录的规模。
**未定之前，本卡只做 2.1–2.3，把 2.4 留在卡里等答复。**

### 2.5 那一页的默认姿态反过来

```
今天：打开是空表单，等你手填；AI 拆解是旁边一个辅助按钮
改成：打开是「AI 从当前剧本 + 已上传资产梳理出来的样子」
      每一条：✓ 已确认 / 待确认 / 与已确认档案有冲突
      你只处理有分歧的那些
```

产品负责人原话：「作品设定的内容**不应该在故事开发的时候准备**」——
所以这一页不是录入面，是**核对面**。

**「随剧情推进重新梳理」= 剧本更新后可以再跑一次**，
它要说得出「第 7 集之后，林照和许渡的关系从交易变成了什么」。
