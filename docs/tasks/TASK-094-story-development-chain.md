## 1. 共同机制：做一次，三处复用

**批次 0 先把这三样抽出来**，后面三段直接用。这是合链的全部意义所在。

### 1.1 「AI 改」的统一形状（照 `script-draft` 的既有样板）

`script-draft` 已经是**两个能力两个模式**（`script-writer` / `script-reviser`），
而且它的注释写明了为什么当前内容必须是**声明输入而不是 steer**：

> TWO MODES, TWO CAPABILITIES. Revising is not writing … the base script is its
> **DOMAIN CONTEXT, not a steer** —— steer 会被 `compile_prompt` 丢掉，
> 「silently cost the revision mode its base script until a test caught it」。

**三段一律照这个做**：
- 每处新增一个 `*-reviser` 能力，声明输入 = 当前内容 + 修改要求
- `_skill_id_for(slug, payload)` 按「有没有当前内容」选 writer / reviser
- `_EXTRA_FENCED` 里对应的 steer **删除**
- 产出仍是**提案**，应用才成版本，旧版本全留（既有纪律）

**分集规划今天连「改」都没有**（`_PAYLOAD_TO_CONTEXT["episode-plan"]` 只给 `outline`），
这是 48 集那个缺陷的根因；故事大纲已经带 `current`，要确认它的 `instruction`
是否也走 steer。

### 1.2 「审阅面」的统一姿态

- **AI 写了的**：正常显示、可编辑。
- **AI 没写的**：显示为空，**不摆成待填的格子**。
  （分集规划今天摆 288 个人物推进格，产品负责人原话：「为什么那么多重复的内容要写呢」）
- 有范围的字段（如「主要剧情 3～6 条」）：**不足/超出标出来，不拦死**。
- 列表字段一行一条，可增删。
- 保存一律走「追加新版本」这条既有写路径，**不建第二条**。

### 1.3 Skill 包新版本的统一纪律（ADR-0067）

**已被历史 Run 引用的版本不得原地覆盖** → 一律**发新版本**。
`skillDigest` 让 Run 指向确定内容，这是既有机制，别绕。
