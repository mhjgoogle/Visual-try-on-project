## 三个判断

**一、进度从仓库派生，不手写。** 卡头引用的 `REQ-NNN` + 卡所在目录（目录即状态，
ADR-0083）。手写的进度板比手写的索引更危险：索引过期只是找不到东西，**进度板过期
会让人按一个不存在的状态做决定** —— 本仓库有实例（一张卡的错标签把两条真缺陷盖了
十天，ADR-0082 §2）。所以它与 `STATUS.md` **同一个生成器、同一条命令、同一道闸**。

**二、满格写「卡都做完了」，不写「完成」。** 这两件事不是一回事：REQ-006 的判据 1
在 TASK-128 落地前一直是 `PARTIAL`，而如果那时引用它的卡恰好都在 `done/`，一根满格
绿条就会骗人。这一列衡量的是「这条需求的工作做了多少」，**不是「这条需求满足了多少」**。

**三、多一节「在办但不服务任何需求的卡」。** Bug / 工装 / Refactor 写的是技术目标
而不是 REQ（AGENTS §20）。不列它们，一块只显示需求的板子会让人以为「没别的事在做」。

## 为什么不做判据级进度（那才是理想粒度）

8 份 REQ 里**只有 3 份**把判据写成了可解析的顶层有序列表（REQ-006/007/008），其余
混在散文与版本说明里。硬做会让 5 条需求显示「0 条判据」—— **比没有更糟，因为它
看起来像事实**。

要做得先统一 REQ 文件的判据格式，那是**改需求文件**，而本次的原话是「不要写需求」。
理由写在生成器注释里，下一个人不必重新推一遍。**这条不是遗漏，是记在案的边界。**
