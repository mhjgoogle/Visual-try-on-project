## 他问的那个问题，原来的答案不够好

在这之前，「这句话是要改作品，还是对应用的意见」**完全由模型每轮判断**：动作表里只有
作品类动作，`feedback.ui` 在提示词里描述成「对这个应用本身的意见」。实测分类是准的
（他提的两条意见都归对了），但**没有硬保证** —— 他没有任何办法说「我现在就是要提意见，
别动我的东西」。

## 形状：一根流，两条线，一行 tab

| 窗口 | 线程 | 能做什么 |
| --- | --- | --- |
| **作品** | 按页面分（每页一条，REQ-004 v3） | 动作注册表里的全部动作 |
| **开发** | `__feedback__`，**项目级一条线** | 只有 `feedback.ui` / `proposal.decide` / `note` |

「开发」是项目级而不是按页面：一条「这个界面不好用」不属于某一页（在哪一页说的仍然记在
那一轮的 context 里）。**简约的做法是没有第二块面板** —— 只是同一根流换了一条线，
标题栏那一行就是切换器；未答复的提案数显示成 tab 上的小圆点。

## 强制在服务端，不是靠模型自觉

- 提示词按窗口分岔：「开发」窗口的提示里**根本没有作品类动作**，词汇表本身就是那道闸。
- 即使模型自己编一个 kind，落地那一步（`_conv_reconcile`）也会按
  `_CONV_FEEDBACK_ONLY_KINDS` 筛掉，并把被筛掉的那条如实放进「本应用还做不到」，
  附一句「这是在「开发」窗口里说的，作品不会被改动 —— 要改作品请切回「作品」窗口」。
- 归线同理：`_conv_key` 看的是这一轮 run 自己的 `context.intent`，不是前端事后声称的。
