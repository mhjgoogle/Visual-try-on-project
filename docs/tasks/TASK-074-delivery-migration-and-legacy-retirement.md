| # | 来源 | 缺陷 | 修法方向 |
| --- | --- | --- | --- |
| a | 064 §4h-1（blocking） | `_agent_mix_shot` 输出 basename 只过 `_NAME_RE`，**未强制 `mix-` 保留前缀** → 构造请求可占用属于对白 / 音效音频链的带版本文件名 | 与其它写入路径一致地用 `_slug_reserved` 家族的规则挡住；`mix-` 是 ADR-0044 为合成产物预留的命名空间 |

### 1.4 真实项目全流程验收

**在真实 Connected Project 上跑完整流程一遍**（AGENTS.md 第 20 条：
demo seed 与 SVG 占位素材不作为主要验收依据）：

```
创建项目 → 设置规格/预算 → 创意 → 大纲 → 设定 → 分集 → 剧本(锁定)
→ 分镜 → 绑定参考 → 主画面 → 视频候选 → 单镜定稿
→ 自动粗剪 → 整集审片(含一次退回重做) → 后期 → 质检 → 导出
```

必须验到的边界情况：

1. 镜头未全定稿时提交正式审片 → **被 G1 拒绝**，可生成测试粗剪。
2. 审片通过后改镜头顺序 → **审片状态回落 `needs_rereview`，画面锁定解除**（G3）。
3. 存在 blocking 质检问题时导出 → **被 G4 拒绝**并列出问题。
4. 长任务运行中刷新页面 → **状态从后端恢复**。
5. 长任务取消 → **子进程真实退出**。
6. 后端不可用 → 页面显示错误，**不显示空列表**。
7. runtime 不可用 → 手工兜底路径可完成同一动作。
8. 每次粗剪 / 每次导出 → **新版本，旧版本仍在**。

**发现真实数据问题时优先如实报告，不得用 mock 绕过。**

### 4.1 §1.1b 后期交付端点加固 —— 四条全部修完，各带守卫

按卡的要求**先复现再修**，`c` / `d`（可被构造请求触发）优先。

| # | 复现 | 修法 |
| --- | --- | --- |
| **c** | `math.isfinite(10**400)` → `OverflowError: int too large to convert to float`（实际跑过） | **范围比较前移**到 `isfinite` 之前：整数与浮点比较对任意大整数安全，且顺带挡掉 NaN / ±inf（它们的比较恒为 False）。修的是**类**不是行 —— 同一个 `_num` 模式在 `mix-shot` 与 `render-episode` **两处**，都改了 |
| **d** | 一次 mix 最多 60 个 clip，每个都在 `_RENDER_LOCK` **之外** 起一个 ffprobe | 新增进程级 `_PROBE_SEM`（`BoundedSemaphore(4)`）+ `_PROBE_WAIT_SECONDS`。**不用 render lock**：探测是只读的、并行几个是安全的，要的是**上限**不是互斥；把校验搬进锁内会让所有调用方排在「不产出任何东西」的工作后面。`finally` 里释放，泄漏一个 permit 会永久缩小上限 |
| **a** | `mix-` 是保留前缀，其它写路径都检查 `_slug_reserved` 以**留在命名空间外**；这一条**写进**命名空间却从不检查自己是否留在里面 → 构造请求可用 `voice-shot-1` 占用对白链的带版本文件名 | 强制输出名以 `mix-` 开头 |
| **b** | `in` 允许到 36000 **闭区间**，而 `out` 被**夹到** 36000 → 开放式片段 `in == 36000` 变成**零长度**（混音失败或静默消失） | 两端用同一个上界；`in >= 36000` 直接 400。**检查点放在读文件之前** —— 它只依赖请求本身，输入问题不该排在媒体读取后面才被报告（第一版我放在 probe 之后，守卫立刻暴露了它永远先撞上 `file missing`） |

守卫：`tests/test_motv_mix_hardening_task074.py`（6 项），含 `10**400`、
`NaN`/`Infinity`/`-Infinity` 字面量、命名空间占用、零长度片段、
上限真的会绑（取满 permit 后第 5 次必须失败）、以及**探测队列打满时诚实失败而不是
假设一个时长**。

### 4.2 §1.2 交付质检（检查层 3）—— 领域实现完成

新增 `src/workflow/deliveryqc.js`：七项检查 + `runDeliveryQc()` 产出 QCReport

**最要紧的一条规则已落地并被守卫**（§1.2 / ADR-0064 决策 6）：

`passed === false` 且 `issues.length === 0`。

§6.1 的互不相交对齐）、每个未知都带原因、warning 不阻断导出但也不算通过、
质检问题 `source === "agent"`（测量是观察，不是结论）并真的喂给 G4。

| `server.py` `_build_delivery_probe` | **新增**纯函数：把 ffprobe JSON 与 ffmpeg stderr 翻成 `deliveryqc` 读的 `probe` |
| `services/query.js` `deliveryProbe()` | 测量是观察不是命令（ADR-0064 决策 6 / §6.2），所以归 query 而不是 command；`timeoutMs: 0`，真正的上限由后端持有（900s → 504） |
| `app.js` `DELIVERY_PROBE` / `runDeliveryProbe` / `_latestCut` | 探测状态**不持久化**：一次探测描述的是**某一个成片文件**，新成片一合成，数字就是在说另一个文件 |
| `ui/qcpanel.js` `probeBar` | 按钮 + 状态；`ui/production.js` 绑定并**渲染两次**（先让按钮变「正在探测…」，再渲染结果） |

**为什么一个测不出来的字段必须缺席而不是填 0。** 解析是**逐字段全有或全无**：
ffprobe 会大方地给出 `N/A`、省略 `nb_frames`；任何一处填默认值，`deliveryqc` 就会把
「我们没测」渲染成创作者屏幕上的「合格」——正是 §1.2 / ADR-0064 决策 6 要防的事。
`tests/test_motv_delivery_probe_task074.py` 的一半断言钉的就是这一条。

**音画同步测的是什么、不是什么。** 用的是两条流的**容器层起始时间差**，
不是内容层的唇音同步——ffmpeg 没有可靠的内容级检测，硬说有就又是编数字。
但对**我们自己 concat/mix 出来的**成片，容器层错位正是真实的失败模式
（合成步骤把音频接错位置）。两条流都必须报出 `start_time`，否则该项保持缺席。

**`blackSpans: []` 是一次真实测量，不是缺席**：blackdetect 干净时一行都不打印。
所以只有**存在视频流**时才给空数组——没有视频流时那是「没得测」，不能说「干净」。

**帧率按有理数除出来**：`30000/1001` → 29.97 而不是 30。缺帧检查用
`时长 × 帧率` 算期望帧数，一个被舍入上去的帧率会凭空造出「少了几十帧」。

**`nb_frames` 缺失时保持缺席**：真数帧要再解码一遍整片，代价不值；缺帧项如实报未检查。

测试：`tests/test_motv_delivery_probe_task074.py` 15 项（纯函数）、
`tests/qcpanel.test.mjs` 6 项新增（三种「未检查」状态必须可区分、探测必须说出它测的是
哪个成片）。全量：pytest 3153 + 5，前端 1061，ruff 全绿。

**成片从哪来（这条链跨五个模块，断了只表现为「按钮不亮」，所以写全）**：

```
时间线「渲染本集」 → command.renderEpisode → 后端 _agent_render_episode
  → render-ep-v<N>.mp4（uploads 目录，版本化不覆盖）
  → timelinectl.js:280 assetlib.addFinal(...) 登记为 kind="final" 资产
  → assetreg.listAssets 把 reg.finals 扁平出来
  → app.js _latestCut() 取最后一条、从 url 提取文件名
  → POST /api/delivery/probe → _resolve_upload_file 过上传白名单正则
  → ffprobe + ffmpeg → probe → 五项真判
```

最脆的一环是**文件名白名单**：两条产出路径命名不同
（`render-ep-v<N>` / `final-cut-v<N>`），而单元测试拿假名字跑得好好的；正则一旦
收窄，界面上只显示「探测失败」，没人会想到是白名单。
`test_the_probe_accepts_the_names_the_render_paths_really_produce` 用**真实产出的
名字**钉住它，并配一条反例测试防止有人顺手放宽（`../secret.mp4` / `a/b.mp4` /
`.exe` / 带空格）。

**`compose` 端点前端仍无调用方**（`ctx.composeFinal` 存在但没有 UI 入口）——它是
agent 直接从镜头视频合成的另一条路径，与上面这条并行。不影响本轮：成片由时间线
渲染产出。多版成片时由创作者选哪一版来测，属 §1.1「成片预览」的范围；当前取最后
登记的一条并在界面显示其文件名。

### §1.2 交付质检 —— 领域层 + 界面完成

`workflow/deliveryqc.js` 早已有七项检查的领域实现，但**一个调用点都没有** ——
⑩ 后期交付页的「交付质检」分区是空的。本轮补上界面（`ui/qcpanel.js`）与
视图模型（`ctx.deliveryQc()`）。

**这一屏的全部意义在于如实说出它没测什么。** 浏览器跑不了 ffmpeg，所以
音画同步 · 音量 · 削波 · 黑帧 · 缺帧五项确实测不了，它们渲染成**未检查**并附
原因，`passed` 保持 false。颜色上用中性色，不是绿也不是红：它是一个待答的问题。
给它们喂一个编造的 probe 把屏幕填绿，正是 §1.2 / ADR-0064 决策 6 要防的事。

今天真能判的两项，数据页面本来就有：

| 检查项 | 数据来源 | 现状 |
| --- | --- | --- |
| 字幕 | 字幕轨（空 cue / 时序倒置 / 越界） | 真判 |
| 素材权限 | **本片剪辑用到的**资产的 `origin` 标记 | 真判 |
| 规格 | ⚙ 成片规格 | 缺的是**设置本身**，界面明说去哪儿填 —— 与「装个 ffmpeg」是两个动作 |

字幕越界按**当前剪辑**的时长判，不是按成片文件（还没渲染），也不是按 ⚙ 的
`episodeSeconds`（那是目标不是测量）。空时间线给出 null 而不是 0 —— 0 会把每条
字幕都判成越界。

「素材权限」看的是**这条片子用到的**素材，不是整个资产库。传整个 registry 会让一条
与本片无关的旧记录（没有 `origin`）判成阻断，反过来绿行数的也是片子外面的素材，
等于什么都没说。剪辑里有 clip 指向查不到的资产时，清单**不完整**，报 unavailable
而不是权限失败 ——「查不到这个素材」和「这个素材没标来源」是两个不同的发现。

G4 的结论由界面**渲染**而不是重新推导：两个地方决定能不能导出，就是多了一个。
绿字只看 `report.passed` 而不是 `g4.ok`：G4 只清阻断级问题，一次警告级不合格会让
`g4.ok` 为真而报告并不合格。

### G4 为什么还没接到渲染上（明确记录，不是遗漏）

§1.2 要求「存在 open 的 blocking 问题时 `exportDelivery` 拒绝执行」。当前代码里
**没有 `exportDelivery`**：`controllers/timelinectl.js` 的 `render()` 一步同时
渲染成片并把它登记为 Final。

把 G4 接在那一步是错的：质检要探测的正是那次渲染的产物，先渲染才有东西可检。
闸门装在那里会挡住产出被检对象的动作本身，于是永远进不到能通过的状态。

正确顺序是系统合同 §6.5 的四段生命周期 —— **候选 → 质检 → 用户确认导出 →
Final**。要接 G4，得先把 `render()` 拆成「产出候选」与「确认导出为 Final」两步。
那是 §1.1「导出及导出记录」分区的工作，本轮没做，因此 G4 的结论目前只在质检
面板上**显示**，还没有拦住任何写操作。

界面上没有假装它拦住了：面板写的是「G4 拒绝导出 / 不阻断导出」，说的是结论本身。
