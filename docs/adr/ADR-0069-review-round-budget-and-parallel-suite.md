## 背景

ADR-0068 已经诊断出「全量测试被跑在错误的位置」并把它挪到链尾。但它保留了一句
话：审查**不放松**、**审到 pass**。那句话本身成了下一个瓶颈——因为
`SKILL.md` 把它实现成了 `until pass; no fixed round cap`。

git history 里的实测代价：

| 证据 | 数字 |
| --- | --- |
| 提交信息含「审查轮 N」的提交 | **21 个** |
| TASK-072 批次一（ADR-0068 §背景自记） | **23 轮** |
| TASK-061 | **13 轮**（轮 A / A2–A7 + B2–B4） |
| TASK-062 | **10 轮**（轮 2–10） |
| 2026-08-12 单日提交 | **39 个**，其中约 20 个是审查返工 |
| 净负值实例 | 轮 B4 **撤回**了轮 A4 的修复 |

**根因是规则，不是态度。** `SKILL.md` 的决策表写着「Any P1 **or P2** present →
fix them, then run the next round」：每个 P2 都换来一整轮再审，而审查者永远能
找到更窄的 P2 变体。这个循环在结构上不收敛，「progress」这个终止条件挡不住它，
因为每轮确实都有新的 P2 可修。

同时存在一条**自相矛盾**：AGENTS.md 第 20 条的分级表说低风险改动只要「相关前端
测试 + 手动 smoke」，而 CLAUDE.md 实施纪律说「任何 feat / fix / refactor 完成后
必须立即调用 codex-review-loop，不得跳过」。两条规则冲突时严格的那条总是赢，
**所以那张分级表从未真正生效过**。

最后，「审查前不得 commit」这条纪律在审查者不可用时**直接死锁整条交付**。
2026-08-14 实测发生一次：TASK-075 批次 C 代码已完成、测试已绿，卡在 codex 触到
workspace spend cap 且 `claude` CLI 未安装（fallback 不存在），无法提交也无法
推进。

## 决策

### 决策 1：审查按风险分级触发，与测试用同一张表

低风险改动（CSS、布局、间距、文案、纯展示组合，或修复**不触及**中/高任何类别的
局部 bug）**不调用** `codex-review-loop`，以定向测试收口。这不是新标准，而是让
AGENTS.md 第 20 条那张表**第一次真正生效**。

### 决策 2：轮次预算

| 风险 | 轮次预算 |
| --- | --- |
| 低 | **0** |
| 中 | **1 轮** |
| 高 | **2 轮**（仅当第 2 轮仍报 **P1** 才允许第 3 轮，硬上限 3） |

预算是**轮数**，不是发现数。达到预算是正常结果，不是失败。

### 决策 3：只有 P1 买得到下一轮

- **P1**（正确性 / bug / 安全）→ 必修，且值得再花一轮复审。
- **P2** → 修，跑**定向测试**收口。**低 / 中**风险不再开一轮再审；
  **高**风险若预算还剩一轮，**用掉它**复审那些 P2 修复——持久化 / schema /
  身份 / 安全的代码不该带着没人看过的修复出门，高风险那第 2 轮正是为此存在。
  （独立审查 round 3 的 finding：原表述让高风险的 P2 修复零复审，
  让步范围比本 ADR「后果」小节声称的更大。）
- **P3 / P4** → 不修，记为 follow-up，不阻塞交付。

这是对 ADR-0068 决策 2「不放松」的收窄，理由是**「审到 pass」与「有界」在数学上
不兼容**：只要 P2 能触发再审，而再审总能产出新 P2，循环就不终止。保留下来的强度
是：P1 一律必修，且 P1 的修复不得是循环的最终状态（预算内必须复审）。
被放弃的是「零发现」这个目标本身。

### 决策 4：分级取改动触及的最高一档

永远不按 diff 大小或「原因是否明显」降档。一行修复只要落在持久化、schema/迁移、
身份、登记、渲染/文件操作、存储生命周期、付费、并发、安全、Windows 可移植性或
跨层合同里，就是高风险。无法分类按高风险处理。

> 这一条是 codex 独立审查（2026-08-14 round 1）的**唯一 blocking finding**：
> 低风险档原本写「单点明确 bug」，与高风险的持久化/安全类别重叠且没有优先级
> 规则，于是一个持久化或安全的局部 bug 可以被归为低风险从而**绕过强制审查**。
> 已按 class 修掉三处同源表述。

### 决策 5：审查不是提交的前置门槛

**发布闸门 = 用户验收标准满足 + 相关测试通过 + 无未闭合 P1。**
不是「零发现 + 全量测试 + 完美架构」。`VERDICT: pass` 不是闸门。

审查在提交**之后**进行，发现 P1 用后续提交修。这样审查者的可用性不再能锁死交付。

### 决策 6：审查者不可用时照常推进，并如实记录缺口

在提交信息与任务卡里写明「未经独立审查 + 原因」。**不假装审过，也不用「测试
全绿」冒充独立审查**；但也**不因此停下交付**。这一条替换 CLAUDE.md 原先的
「两者都不可用时：停下并如实报告」——如实报告保留，停下取消。

配套要求：`claude` CLI 必须安装，使 fallback 审查者始终存在
（2026-08-14 已安装 2.1.232，订阅凭据可用，`claude -p` 验证通过）。

**高风险改动的审查是后移，不是取消。** 未经审查就提交的高风险改动必须登记到
[待复审清单](../design/active/pending-codex-rereview.md)，审查者恢复后立即补审，且
**push / merge / 交接 / 人工验收之前必须完成补审**——与 ADR-0068 决策 6 同一
逻辑：可以推迟，不可以跳过。

> 这一条是独立审查（2026-08-14 round 1，reviewer=codex）的 blocking finding：
> 决策 5 / 6 的原始表述允许安全、持久化、身份类改动在**完全没有**独立审查的
> 情况下提交并继续交付，于是「审查者不可用」就成了永久移除安全门的通道。
> 产品负责人对「审查不阻塞提交」的决定保留不变，加上的是**到期约束**。

同一轮审查还报了两处本 ADR 引入的自相矛盾，均已修：
（a）中风险只有 1 轮预算时，若那唯一一轮发现 in-scope P1，决策 2 的三个预算耗尽
选项**无一匹配**（「多给一轮」原本写成高风险专属），工作流走不下去 —— 现在
「fix P1 only」适用于**每个档位**，上限为 **档位预算 + 1**，未闭合的 P1 永远买得到
它需要的那一轮；
（b）CLAUDE.md 的「非本任务 bug 的 P0/P1 立即处理」与 AGENTS.md 第 17 条
「不修改当前任务范围之外的代码」冲突 —— 现在一律记录到 follow-up，唯一例外是
它阻塞当前任务，且只在最小范围内修并说明为什么绕不开。

### 决策 7：全量 pytest 改两阶段并行

1. `pytest -n 8 -m "not serial"` —— 并行
2. `pytest -m serial` —— 串行，真实进程树测试

原生 Windows 实测（3191 项，同一台主机）：**串行 469s → 两阶段 179s，2.6×**，
每次省约 290 秒。收益来自 fsync I/O 重叠：Windows 没有 `/dev/shm`，根
`conftest.py` 的 tmpfs 路由在这里是 no-op，每次 persist 都 fsync 到 NTFS。
`-n 8` 是实测值，不用 `auto`（12）——fsync 主导后更多 worker 不再付费。

`serial` marker **只**给断言真实 OS 进程状态的测试用。`-n 8` 下唯一失败的是
`tests/test_motv_run_lifecycle_task072.py`（串行 10.8s 通过），它 spawn 真实
进程树再 kill，无法容忍 sibling worker 并发杀自己的树。**它不是绕开并行的通用
逃生口**；新增 `serial` 标记必须给出同等强度的理由。

两个 commit gate 与 CI 的两个 job 用同一套拆分（ADR-0062 决策 3：两壳同判定）。
`pytest-xdist` 进 `[project.optional-dependencies].dev`，是全量提交的**硬依赖**
（缺它 gate fail-closed）。

## 后果

### 正面

- 高风险任务的审查从 10–23 轮降到 2–3 轮；低风险改动完全不进审查通道。
- 全量测试从 469s 降到 179s，UI 迭代不再触发 6.5+ 分钟的惩罚。
- 审查者不可用不再锁死交付。
- AGENTS.md 第 20 条的分级表第一次真正生效。

### 代价与风险

- **P2 的修复只经过定向测试，没有第二双眼睛看过。** 这是本 ADR 最实质的让步。
  接受它的理由是 P2 按定义是「回归 / 边界情况」而非正确性缺陷，且定向测试正是
  为覆盖它而写。P1 的强度一分未减。
- **「零发现」不再是目标**，因此某些真实但低优先级的问题会以 follow-up 的形式
  长期存在。必须真的记下来，否则「记为 follow-up」等于「丢掉」。
- **并行测试引入了顺序无关性要求**：新写的测试若隐含共享全局状态，会以
  flaky 的形式出现而不是稳定失败。`serial` marker 是逃生口，滥用它会把并行收益
  一点点还回去。
- **审查后置意味着历史里存在未经审查的提交点**。如实记录，且 P1 必须用后续提交
  修掉，不得停留。

## 明确不做

- **不降低高风险类别本身的标准。** 持久化、身份、安全、并发、迁移、付费、
  破坏性操作、Windows 可移植性的判定一字未改；fail-closed 语义不变。
- **不取消独立审查。** 取消的是「无上限轮数」与「审查作为提交门槛」，不是审查。
- **不设永久关闭测试的全局开关**（延续 AGENTS.md 第 20 条）。
- **不改 ADR-0061 的三空间十一页封闭集合**、不改 ADR-0066 的三层检查：
  那些是产品结构决策，与本 ADR 的验证节奏无关。
- **不动 `server.py` 的 6723 行单体**。它使「定向测试」被撑宽到 33 个测试文件
  （约 180s），是真实的架构债，但拆它属产品负责人拍板的范围，本 ADR 不涉及。

## 补记：WIP 才是当日的硬瓶颈

同日发现一件比审查流程更急的事，记在此处以免丢失：工作区上同时存在**三个**
未完成的在制品——TASK-075 批次 C（已完成）、TASK-072 批次二（自记「部分完成，
24 / 30」）、TASK-073（任务卡状态仍写「已规划，未开始」，前置 TASK-072 未完成，
但代码已在工作区）。

TASK-073 改了 `shell.js` 的 NAV 与中心页，导致 1 个 pytest 守卫 +
7 个前端 IA 守卫红。因为这些红，**任何 `full` tier 提交都过不了闸**——包括早已
完成的批次 C。当日唯一能落地的提交是纯 Markdown（`lint` tier）。

结论：**「去掉门槛」不会让交付变快，因为门槛不是瓶颈；同一工作区上的在制品数量
才是。** CLAUDE.md 已据此写入 WIP 上限（1 个主要用户需求 + 最多 1 个阻塞它的
技术任务，Finish before starting more）。
