# ADR-0057：Shot 生产状态与连续审片（Dailies）

- 状态：Accepted
- 日期：2026-08-12
- 关联：[ADR-0052](ADR-0052-workflow-page-as-derived-provenance-graph.md)、
  [ADR-0055](ADR-0055-unified-asset-registration.md)、
  [TASK-060](../tasks/TASK-060-shot-production-and-dailies.md)
- **被 [ADR-0066](ADR-0066-product-refactor-fixed-ia-review-layers-and-system-contract.md)
  拆分**：本 ADR 的单层「审片」拆成三层 —— 逐镜通过归「镜头制作 · 对比候选并选定」
  （检查层 1），整集连播归新的「粗剪审片」页（检查层 2），并新增「交付质检」
  （检查层 3）。派生优先、`生成成功 != 镜头完成`、无视频不可通过等规则全部保留。

## 背景

Workflow 今天能把「生成过什么」画成溯源图（ADR-0052），Production 能把
「作品是什么」立起来（ADR-0054），资产能被正确登记（ADR-0055）。中间缺的是
**一集究竟做到哪一步了**，以及**审片**：

1. **「生成成功」被当成了「镜头完成」**。一个镜头有视频，不等于导演看过并
   认可。系统里没有任何地方记录「我看过，通过了」，于是没人能回答
   「这一集还剩几个镜头要审」。
2. **参考图没有被镜头引用**。ADR-0055 把参考做成了有版本链的 canonical
   对象，但没有任何东西把「SH01 / SH02 / SH05 都用 林照 Ref」记下来，所以
   「这个参考被哪些镜头用」只能靠猜，Reference Planning 也无从谈起。
3. **没有连续审片**。要看完一集，只能一个镜头一个镜头点开，看完退出再点
   下一个。这是审片这件事最基本的形态缺失。

## 决策

### 决策 1：只持久化**推导不出来**的两件事

    production.shotProduction = {
      reviews:    { [creativeShotId]: { approved: true, approvedAt, note } },
      references: { [creativeShotId]: [referenceKey, …] },
    }

其余镜头状态**全部派生**：

| 状态 | 判定 |
| --- | --- |
| 待设计 | 设计字段全空 |
| 已设计 · 待生成 | 有设计字段、无图片 |
| 已生成 | 有图片、无视频 |
| 待审片 | **有视频**、且没有生效的通过记录 |
| 已通过 | 有视频**且**有通过记录 |

「已设计」与「待生成」在本系统里是**同一个条件**（设计好了、还没生成），
分成两个状态会让其中一个永远不可达——一个界面能打印、数据却永远产生不了的
标签。因此只保留一个状态。

存一份重复的 `status` 字段，会在切换变体或删除资产的那一刻立刻与资产注册表
矛盾。唯一无处可存的是**人的判断**，所以只有它落盘。

**生成成功 != 镜头完成**：没有任何代码路径因为生成成功而写入 approval。
镜头到达「已通过」，只因为有人这么说了。

**通过需要有视频**，且这条规则由**域**（`ctx.shot.approve`）强制，不只是界面：
审片判断的是「这个镜头最终被看到的样子」。只有界面拦一道，其他调用方就能绕过。

**通过记录会保留，但它只在被通过的视频还在时才描述「现在」**：视频被删除或
切走之后，镜头不再是「已通过」（回落到由媒体推导的状态），但**记录不删**——
创作者确实做过那个判断，抹掉它就是销毁一个真实决定。界面用
`hasStaleApproval` 明说这件事，并提供「清除失效的通过记录」。

### 决策 2：`approved: false` 不存在

未通过的状态是「**没有通过记录**」，不是 `approved: false`。后者会声称
创作者**主动否决**了这个镜头——那是另一件事，而且系统并没有记录它。
撤销审片是**删除记录**，不是写 false。校验层同样拒绝 `approved !== true`
的记录。

### 决策 3：镜头引用的是**共享的 canonical Reference**，不是副本

`references[shotId]` 存的是 `ref-…` 链的 **key**，不是 assetId：

- 十个镜头用同一个参考，就是十条相同的 key，**一个**参考、**一个**版本指针；
- 把链切到 v3，十个镜头同时跟着走——这正是参考要做成 canonical 对象的理由；
- 具体某次生成**实际用了哪一版**，仍然由 Generation 的
  `referenceAssetIds` 冻结记录（ADR-0055 的诚实 lineage 不变）。

一个 shot 的引用列表里**不允许重复 key**：重复会渲染出两个一样的 chip，
并让该参考的使用计数翻倍。

### 决策 4：Dailies —— 按 canonical 顺序连续审片

按 Scene / Shot 的 canonical 顺序（场景内 shotIds 顺序，然后未分配池）
逐镜播放：

    播放 · 上一镜 · 下一镜 · Shot Design 摘要 · 状态 · 通过 · 跳过

**没有视频的镜头不得让流程崩溃**：它照常出现在序列里，显示「还没有视频」，
并且**不能**被标记通过——审片是对**已有画面**的判断，对不存在的画面点通过
是伪造。

### 决策 5：删除参考后不留幽灵

参考被永久删除时，指向它的 shot 绑定必须被清理（`pruneShotReferences`）。
悬空的 key 会渲染成一个点不开、也说不清是什么的 chip。这与 Generation
的 `referenceAssetIds` 不同——那是**溯源**，按 M5 设计允许悬空，因为它记录的
是「当时确实用了它」这个历史事实。

### 决策 6：canvas schema v13

`migrateV12ToV13` 纯追加：`production.shotProduction = {reviews:{}, references:{}}`。

**两个映射都从空开始**。迁移无法知道创作者会通过哪些镜头；因为一个镜头
「有视频」就把它标成已通过，正是决策 1 明令禁止的混淆。既有镜头因此显示为
**待审片**——这就是事实：没有人审过它们。

## 后果

正面：

- 「这一集做到哪了 / 还剩什么」第一次可以被如实回答，且不依赖任何重复状态；
- 参考第一次真正被镜头共享，Reference Planning 与「这个资产被哪里用」有了
  同一份数据来源；
- 审片成为一个可以连续走完的动作。

代价：

- 又一次 schema 迁移（v12 → v13），高风险流程；
- 既有项目的全部镜头都会显示为「待审片」——这是诚实的代价，不是缺陷；
- 本批只做**域 + 审片**：Reference Planning 的完整界面、剧本↔分镜合并视图、
  Generation Input Set 的完整 UI 留待后续任务（见 TASK-060 §6）。
