# ADR-0099：重启之后的续跑不是重试 —— 孤儿付费任务接回已经存在的那一条路

- 状态：**Accepted**（2026-09-05，实施 Agent 依 AGENTS.md §1 自行 Accept ——
  这是纯技术决策：字段形状、状态语义、失败语义、跨包依赖方向）。

  本 ADR 定的恰恰是「什么时候**不许**再花第二次」。

## 背景

TASK-136 立卡时的判断是「本仓库还没有续跑语义，要从零定」。核过代码之后，
**那句话只对了一半**：

**核心库（原 M1 付费路径）已经把这三个概念实现完了**，一个不缺：

| 概念 | 它在哪 |
| --- | --- |
| 远端任务 id 必须持久化 | `budget/reservation.py` 的 `record_external_task_ref` → `external_task_ref` 落在 `budget/reservations/<task_id>/<operation_id>.json` |
| 孤儿任务 | 预留停在 `HELD` / `NEEDS_RECONCILIATION`（`_OUTSTANDING`）而没有任何执行体在跑 |
| 续跑 | `app/paid_coordinator.py` 的 `resume_media(shot, task_id, operation_id)` —— **完全从持久化的预留记录重建**，调用方只给 id；**从不重新提交、不重新定价、不再付一次**。已 `COMMITTED` 的只重新取媒体，否则按预留里存着的报价记一次账再 commit |
| 显式失败 | `external_task_ref is None` → 落 `needs_reconciliation`（`"no external task id persisted; cannot resume safely"`），**不回退成重新提交** |

**Studio 侧（`mockups/motv-workspace/runstore.py`）则一无所有**：
`_sweep_locked` 把跨重启的 `queued` / `running` / `cancelling` 一律打成 `failed`，
给 `provider:*` 的补一个 `sideEffect: "unknown"`，然后就结束了。Run 记录里
**没有任何字段**通向上面那条已经存在的续跑路径。

于是 §5.8 的 `unknown` 在结构上是个终点：合同说「不知道就不许自动重试、要由用户
显式决定」，而用户能做的决定只有「再来一次」（即再花一次钱）——因为**没人知道该去问谁**。
远端那次生成可能已经成功、已经计费，产物就躺在供应商那里，而本地这份记录里
连它的任务 id 都没有。

### 而今天重启之后**唯一走得通的那条路，恰好就是重复扣费**

这不是推演，是把 `runstore.create()` 的去重规则接在清扫结果后面读出来的：

1. 重启清扫把那条 `provider:*` Run 打成 `failed` + `sideEffect: "unknown"`；
2. 用户再发同一个意图 → `create()` 命中 `sideEffect in ("applied", "unknown")`
   那道闸，**拒绝**并说「可能已经执行过（结果未确认）……确实要重跑请显式重试」；
3. 于是他只剩一条出口：带 `retryOfRunId` 的**显式重试** —— 而重试的定义就是
   **重新提交**（§5.7 规则 3），也就是第二次扣费。

三步每一步都对：那道闸是 codex 轮 10 加的，`unknown` 挡重放挡得和 `applied` 一样死，
这是对的；重试是新 Run，也是对的。**错的是这条路上少了一个出口** ——
「别重新提交，去把上次那个接着跑完」。本 ADR 补的就是这个出口，
上面三条规则一条都不改。

时间点是有利的：**Studio 今天还没有任何 `provider:*` Run 的写入方**
（写这份 ADR 时以为付费生成命令
[TASK-041](../tasks/done/TASK-041-workspace-generation-command-and-evidence.md) 会是它，
当天核实后发现不是 —— 见决策 8 的订正框）。现在定，成本是一份文档；接上之后再定，
第一次事故已经发生了，而事故的形式是**用户被扣了两次钱、只看到一次失败**。

## 决策

### 1. 续跑路径只有一条，而它已经存在

Studio **不得**再存一份 provider 任务 id，**不得**自己写第二个轮询器。
远端任务的权威记录是核心库的预留文件，续跑入口是 `resume_media`
（CLI 侧是 `poll-media`）。

理由与 ADR-0095 决策 1 是同一句：**多一份账就多一处漂移**。这里漂移的表现会是
「Studio 说它失败了，供应商那边的成品和账单都在」—— 而这正是本 ADR 要防的那件事。

代价（接受）：Studio 由此依赖核心库的预留布局，是一条跨包依赖。接受它，因为那份
布局是已经冻结的持久化合同，而复制一份远端 id 的代价（两份账各说各话）更贵。
依赖方向仍是 Studio → 核心库，不反向，[TASK-134](../tasks/active/TASK-134-import-linter-layering-contract.md)
的分层契约不受影响。

### 2. Run 上加的是**句柄**，不是副本

```
operationRef   { taskId, operationId } | null
```

`provider:*` 执行器把请求交给核心库付费协调器的那一刻写上；其余执行器恒为 `null`。
这是**加法字段**（AGENTS.md 第 13 条：加法字段优先于破坏性变更），老记录读出来
就是 `null`，不需要迁移。

它存的是「去哪儿问」，不是「问到了什么」。远端 id、状态、报价、已计的账全都留在
预留记录里，只有一份。

### 3. 孤儿**不是**新状态

§5.2 的八态**冻结不动**。「孤儿」是一个**派生判断**：

> 重启后发现的、执行器为 `provider:*`、带 `operationRef` 的非终态 Run。

不新增枚举值，因为它描述的不是任务的一种新处境，而是**我们对它的了解程度**——
而那件事已经由 `operationRef` 与预留状态说清楚了。

### 4. 续跑复用 `queued → running`，区分点在 `operationRef`

清扫规则（§5.4 第 4 条「后端重启不留僵尸，**不得永久停在 `running`**」）**一条不改**：
跨重启的 `running` 仍然必须离开 `running`。改的只是它落到哪儿：

| 重启时发现 | 落到 | 为什么 |
| --- | --- | --- |
| `provider:*` **带** `operationRef` | **`queued`**（等槽续跑） | 远端那次任务还活着，本地缺的只是一个执行体去接着轮询与下载 |
| `provider:*` **不带** `operationRef` | `failed` + `sideEffect: "unknown"` | 见决策 6 |
| 其余执行器 | `failed`（`backend_restarted`，今天的行为） | 宿主进程没了就不可能再有结果，一个字不改 |

执行体据 `operationRef` 走 poll / collect，**不走 submit**。用 `queued → running`
不是凑合：它确实要占一个执行槽、确实在跑（轮询 + 下载），把它说成别的才是编造。

### 5. 续跑不是重试，因此不碰 §5.7 的任何字段

**同一个 Run 接着跑**：`retryOfRunId` 保持 `null`，`idempotencyKey` 不变，
不新建 Run，不重新记账。

这一条必须写死，否则续跑会被 §5.7 规则 2（付费 kind 的终态去重）当成
「同键再来」拒掉，或者更糟——被当成一次新的付费决定。**重试才是新 Run**
（§5.7 规则 3），而重试意味着重新提交、可能重新扣费，那是一次**用户的**决定，
不是重启的后果。

实现上它有一个直接推论：**续跑不经过 `create()`**，它推进的是既有那条记录。
于是 `create()` 里那三道闸（非终态去重 / `unknown` 挡重放 / 重试授权用一次即作废）
一道都不会被绕过，也**一道都不需要放松** —— 这是本 ADR 不改任何既有规则的原因。

顺带一个好性质：续跑中的 Run 停在非终态，所以用户在等待期间重发同一个意图时，
第一道闸（非终态去重）会把他**接到那条正在续跑的记录上**，而不是开第二次。
这正是那道闸本来就要做的事，不是新行为。

### 6. 拿不到远端 id 就显式失败，禁止回退成重新提交

`operationRef` 缺失、预留记录找不到、供应商侧任务已过期或查无此任务 ——
一律落 `failed` + `sideEffect: "unknown"`，由用户按 §5.8 规则 2 显式决定，
**不得**自动改走「那就重新提交一次吧」。

这不是新规则，是 §5.8 三条硬规则在「重启」这个触发场景上的复述：不确定的时候
宁可报错，也不做一次「可能是第二次」的付费调用。核心库那边同一处判断已经这么写了
（`"cannot resume safely"`），Studio 侧照抄这条纪律，不发明第二种口径。

### 7. 启动时**自动**接管是允许的 —— 因为续跑不花钱

§5.8 禁的是自动**重试**（可能造成第二次扣费）。续跑不重新提交、不重新定价、
不再付一次，所以它不在那条禁令的射程里。而且自动接管是让 §5.4 第 1 条
（「刷新可恢复」）在付费任务上真正成立的**唯一**办法：让用户手动去点一个
「接着上次那次」的按钮，等于把一件机器完全有把握做对的事变成人的记性问题。

边界仍是决策 6：自动接管**只**在拿得到远端 id 时发生；拿不到就显式失败。

### 8. 本 ADR 不建任何机制，实施顺序被它固定住

**在 `provider:*` Run 有真实写入方之前，决策 2 与 4 一行代码都不许写。**

一个没有写入方的字段加一套没人触发的续跑执行体，就是
[TASK-087 §1.2](../tasks/active/TASK-087-followup-ledger.md) 那条被 codex 判 P1 的东西：
导出了、测了、没人用，而且让「续跑已经接通」这句话看起来成立。
本 ADR 的产物是**合同**，不是代码。

因此 TASK-136 的前置从「缺一份 ADR」变成**一个条件**，而不是某一张卡：
**直到有东西真的在 runstore 里建出 `provider:*` Run。**

> **2026-09-05 当天订正。** 这句原先写的是「等 TASK-041 的付费写入方」，那样写有错。
> 041 当天收口进 `done/`（产品负责人决定不跑那次付费证据，出处与原话在卡上），
> 而**写入方并没有因此出现** —— 041 交付的是付费命令与 UI 接线，**不是**「谁在
> runstore 里建 `provider:*` 执行器的 Run」。把前置挂在一张已经收掉的卡上，
> 下一个人打开它会以为这道闸已经解开。
>
> 正确的说法是：**今天还没有任何一张卡去造那个写入方**。要推进 TASK-136，
> 得先立一张「Studio 的付费生成走 Run 注册表」的卡 —— 那才是这道闸的钥匙。
> 前置写成条件而不是卡号，也让它不会再随某张卡的状态漂移。

## 射程：不建 Run 的同步外部调用不在里面（2026-09-05 补，实测）

本 ADR 的对象是**在 runstore 里建了 Run 的 `provider:*` 执行器**。一次
**同步的请求-响应、不建 Run** 的外部调用不在射程内 —— 它没有 `runId`、没有执行器
字段、不占队列槽，重启之后**不会留下任何记录**，因此上面八条决策对它无从谈起。

现存的例子是 TASK-139 的 `/api/agent/image-gen-account`（用创作者自己账号的额度
出图，[ADR-0100](ADR-0100-account-quota-is-not-a-paid-gate.md)），形状与
[ADR-0045](ADR-0045-prototype-paid-image-generation.md) 那条付费图片路一致：
去重集合 `_ACCOUNT_IMAGE_INFLIGHT` **是进程内的**，代码注释里写明了它不跨重启、
也不假装能跨。

**它的「重启后怎么收」由产物回答，不由状态记录回答**：出图落的是带版本的新文件
（第 13 条），刷新一看就知道有没有多一版。这比一条状态记录更硬 —— 状态记录会说谎，
文件不会。

所以决策 8 的「等真实写入方」**不再指向任何一张现存的卡**
（[TASK-041](../tasks/done/TASK-041-workspace-generation-command-and-evidence.md) 已于
2026-09-05 收口，它交付的不是这个写入方 —— 见决策 8 的订正框）。
**2026-09-05 复核**：`mockups/motv-workspace/` 的 `.py` 与 `src/**/*.js` 里
`"provider:` 字面量零命中（唯一命中是 `runstore.py:90` 那个前缀常量本身），
Studio 侧创建 `provider:*` Run 的写入方仍然是零个。

## 后果

**变好的**：第一个付费 Run 落地时，「重启后怎么办」已经有答案，而且答案不是
新发明的——它是核心库跑了一整个里程碑的那条路。

**变差的 / 已接受**：

- 一个等着续跑的 `queued` Run 与一个从没跑过的 `queued` Run，在状态词上分不出来。
  界面要靠 `operationRef` 把它说清楚（「接着上次那次跑」），否则用户会以为它从头开始。
- Studio 与核心库之间多了一条跨包依赖（决策 1 的代价，已在那里权衡过）。
- 合同（§5.3 字段表、§5.4 第 4 条）**现在不改**：那两处是「当前事实」，而
  `operationRef` 今天并不存在。写进去会让合同声明一件此刻不成立的事 ——
  TASK-134 从 ArcReel 借来的那条纪律（「一个声明了假事实的契约比没有契约更糟」）
  在这里同样适用。**实施落地的那个提交负责同时改合同**，这是那张卡的完成判据之一。
