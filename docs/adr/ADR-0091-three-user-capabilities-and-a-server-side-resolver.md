## 1. 背景

ADR-0089 让创作者说一句话就能改作品，但**只能改字段**：真正的专业工作（发展故事、
搭世界观、写剧本、查一致性）仍然要他自己去「能力」面板里挑一个、填声明式输入、
选执行器。他说的是「帮我搭建世界观」，得到的是一句「你可以去用世界观导演」。

第一版实现（本卡的前半程）把 26 个能力包里带路由元数据的那些**逐条列进提示词**，
每条带 4–6 句中文触发例句。装到第 8 个的时候，两个问题同时出现：

| 问题 | 具体表现 |
| --- | --- |
| **提示词随目录线性膨胀** | 8 个能力 ≈ 40 行；26 个包全部参与就是 130 行，而它每一轮都要重发 |
| **触发词互相抢** | 「检查一下」同时点中 `story-zoom` / `script-doctor` / `continuity-reviewer`，谁的 priority 高谁赢 —— 而 priority 与「他此刻在说什么」毫无关系 |

第二个问题更要紧，因为它**看不出来**。模型判错「这句话属于哪一类」，创作者一眼就
知道；模型在 20 个近义能力里挑错一个，屏幕上是一次跑起来的运行和一份看起来合理的
答案，没有任何一处会喊。

## 2. 决策

### 决策 1：前端 Agent 只看得见三个「用户能力」

对话模型的能力词汇表**固定为三条**，与装了多少包无关：

| id | 他会怎么说 | 覆盖 |
| --- | --- | --- |
| `story-development` | 「帮我把这个想法发展成故事」「梳理世界观」「他们什么关系」 | 创意、世界观、角色关系、结构大纲、分集规划 |
| `episode-production` | 「写这一集的剧本」「拆成分镜」「这一镜怎么写」 | 分集规划、剧本、拆解、分镜、提示词、素材、声音、字幕、剪辑 |
| `story-review` | 「这一集剧本有什么问题」「镜头对得上吗」「各层还同步吗」 | 剧本诊断、连续性、跨层一致性、观众视角审读 |

**模型返回的是 `capability`，不是 `skillId`。** 它给出的任何 skillId 在边界上就被
丢掉 —— 内部执行什么，从来不由模型说了算。

三个名字与它们的文案住在 `product-skills/user-capabilities.json`（产品资产，与
`skill-inputs.json` 同类）；**id 的权威是 `skillpkg.USER_CAPABILITIES`**，文件只提供
给人看的标题与说明，两者不一致即整份加载失败。两处各持一份名单必然漂移，而漂移的
表现是「某一类请求安静地永远选不中」。

**为什么模型只做一级分流**：它擅长的是「这句话属于哪一类」，那是语义判断，而且判错
了创作者一眼看得出来。它不擅长的是「在 20 个近义能力里挑一个」，而那件事恰好可以用
确定性规则做对。

### 决策 2：内部能力由**服务端的 resolver** 用确定性规则选

`_conv_resolve(catalog, capability, goal, scope, ready, shot_id)`，排序键从高到低：

1. **关键词命中** —— 他的话里点到了这个能力的 `selectWhen`。这一条压过优先级，
   所以「各层同步」选跨层诊断，而泛泛一句「检查一下」不会。
2. **修改动作匹配** —— 句子里带「改 / 重写 / 调整 / 润色」时选修订类，不带时选创作类。
   名词（剧本、大纲、分集）由创作类与修订类**共同**声明，动作由这一条规则分开：
   「写这一集的剧本」与「改一下这一集的剧本」命中同一个名词，靠动作区分。
3. **范围一致** —— 与他此刻站的位置一致。
4. **就绪** —— 必要输入都有。**不是硬闸**（见决策 3）。
5. `priority`，最后 `skillId` —— 让顺序完全确定，不随目录遍历漂移。

内部选择的依据写在包自己的 `internalRouting` 里（`intent` / `kind` / `scope` /
`priority` / `selectWhen`），**永远不进提示词**。`selectWhen` 是**关键词**不是例句：
最多 6 个、每个最多 24 字，由格式强制 —— 一个包维护一长串自然语言触发词，正是这次
要去掉的东西。

**就绪状态由前端报**（`context.readyInputs`）。创作文档只活在浏览器里（ADR-0089
决策 2b），服务端读 canvas 再自己判一遍，等于把内容判定在 Python 里重抄一份；两份
判定一旦不一致，屏幕上会显示「可以跑」而跑起来被必要输入闸拒掉。前端用的是
**同一个** `missingInputs`，所以这边说够的，那边一定也说够。

### 决策 3：缺材料是**一个答案**，不是一次失败

不就绪时 resolver **仍然选出最合适的那个**，`action` 变成 `ask` 并列出缺的材料（用
他看得懂的名字，不是上下文键名）。「我不知道你要什么」和「我知道你要什么但还缺
材料」是两个不同的答案，后者他能照着补。

这条同时解决了「从零创建」被错误路由的问题：世界观导演要 `episodeScript` + `world`，
关系导演要 `characters`。一个空项目里说「帮我搭建世界观」，选中的仍然是世界观导演，
但回答是「还缺本集剧本、世界观档案」——而不是拿一个空投影跑出一份凭空编的设定。

### 决策 4：三道运行前提，最后一道在浏览器

服务端解析出计划之后，**浏览器再判一次能不能跑**：目录里有没有这个包、这一轮是不是
已经跑过、输入够不够、执行器在不在。为什么最后一关在前端：文档在那边，判定就该在
那边落定。服务端那次判定拿的是前端报的就绪状态，是**同一份事实的两次读**，不是两套
标准。

**幂等排在输入检查之前**：跑过之后文档可能变了，这时重算的「缺什么」与当时那次无关，
屏幕上会出现一条对不上号的理由。

自动起跑的是**运行**，不是接受：答案照旧落成 pending 的提案，走 schema 校验、
版本化写入、撤销那条既有路径（ADR-0089 决策 3）。跑不起来时给出手工那条路
（ADR-0065 决策 2）。

### 决策 5：他看得见的是**这一类工作**，不是内部能力的 id

屏幕上说「按检查问题来处理」，不说「调用了 script-doctor v2」。但**服务端记全**：
facade、最终 skillId、skillVersion、选择理由、scope、缺什么，都写在这一轮上 ——
没有这几个字段，「它选错了」就无从复核。

### 决策 6：结构性变更之后**建议**查一次，不自动跑

一次真的落到作品上的结构性写入（创意 / 大纲 / 分集规划的新版本）之后，如果被改的那
一层下游**真的已经有东西**，在对话里给一条建议。三条门槛：**有根**（确实产生了新
版本）、**跨层**（下游至少一层已存在）、**只一次**（以「哪个文档的第几版」作幂等键）。

普通编辑一条都不满足：指针切换、软删除与撤销、交付规格、未保存的草稿都不产生新版本。

**是建议不是自动跑**：即使三条全满足，「要不要现在花一次运行去查」仍然是他的决定。
他点了之后走的是**一轮普通对话**，同一条路由、同一个 resolver —— 所以「跨层诊断该由
谁做」只有一处判定。

## 3. 后果

- **好的**：提示词长度与目录规模脱钩（三条能力 6 行，装到第 50 个包还是 6 行）；
  近义能力不再互相抢路由；「为什么选这个」可复核可测试；新增一个内部能力不需要动
  前端，也不会挤占别人的路由。
- **要接受的**：模型不再能表达「我要的正是这一个专业能力」，二级选择的准确度由
  `selectWhen` 关键词与那几条规则决定，调它们要改包或改 resolver。中文子串匹配是
  粗糙的，修订/创作那一类靠一条专门的动作规则兜住，其余靠名词。
- **不做的**：不给模型直接指定 skillId 的能力、不在编辑后自动跑审查、不把页面里的
  专业按钮也收敛成三类（那些是明确的入口，继续直连专业能力）、不引入付费路径。
