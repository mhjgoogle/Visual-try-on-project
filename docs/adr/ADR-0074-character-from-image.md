# ADR-0074：从一张图创建角色 —— 只登记这张图给出的东西，不臆造档案

- 状态：**Accepted（2026-08-18，实施 Agent 依 CLAUDE.md「ADR 的 Accept 权」自行 Accept）**
  —— 架构 + 写路径 + 身份，属技术范畴；**不涉及付费口径**，
  **不不可逆动用户数据**（新建一个角色是加法；它的参考图是引用而非复制）。

## 背景

审计实测：真实项目 6 个角色里 **3 个「还没有参考图」**，而建角色的入口是一张
**空表单**。目标产品的做法是在图上右键 **「创建主体」** —— 从一张已经存在的图
直接升格成一个可复用角色（T-048）。

TASK-083 §3 的建议是「**先只做『从图创建』**，原型库等有使用数据再说」。
本 ADR 采纳它，并且把范围收得更窄：**只做从图创建**。

## 决策

### 决策 1：它写入的是**身份 + 一条参考绑定**，不是一份档案

从一张图能诚实地知道的只有两件事：

```
这是一个新角色（创作者给的名字）
这张图是它的参考图（assetId + version）
```

**外貌 / 服装 / 气质 / 声音 / 画面指令一律留空。** 它们是档案内容，而这张图
**没有告诉我们任何一项**。填上「一位女性」就是本仓库反复禁止的那种发明
（M8 提案卡纪律 / `promptc.compileEntityBasePrompt` 的既有做法：
缺的 facet 报进 `missing`，绝不写成看起来合理的默认值）。

因此创建之后，角色卡上会如实显示「还缺外貌 / 服装 / 画面指令」——
**那是真话，而且是可操作的下一步**，比一张编造出来的档案有用得多。

### 决策 2：名字**必须由人给**，不从文件名猜

`IMG_2481.png` 不是角色名。文件名派生出来的名字会立刻污染
`shotentity.buildEntityIndex` 的识别（它按名字在画面描述里找实体），
于是一个叫 `IMG_2481` 的角色永远匹配不到任何镜头，而创作者以为建好了。

**没有名字 → 不创建**，并说明为什么。

### 决策 3：参考图是**引用**，不是复制

新角色的 `referenceAssetIds` 指向**那张图已有的 assetId**（ADR-0055 决策 3：
引用不复制）。同一张图可以同时是某个镜头的画面和某个角色的参考图 ——
它们是两个用途，不是两份文件。

**因此这个操作不产生任何新的媒体字节**，只产生一个角色条目和一条绑定。

### 决策 4：只从**已登记**的图创建

一个还没有 `assetId` 的节点（生成失败、尚未上传）不能创建角色：那条绑定会
立刻是一个悬空引用。界面上该动作灰掉并说明原因，**不隐藏**
（TASK-079 §1.2 的既有姿态）。

### 决策 5：重名**不合并**，如实拒绝

同名角色已存在时**不静默合并**、也不悄悄建第二个。合并会把两个人的档案搅在
一起，建第二个会让实体识别在两者之间随机命中。**拒绝并指出那个角色已存在**，
让创作者决定是绑到已有角色上，还是换个名字。

---

## 后果

### 好的

- 「3 个角色没有参考图」这件事第一次有一个**一步**的解法。
- 不产生新媒体字节；同一张图的两种用途各自成立。
- 新角色的空档案是**如实的空**，而且界面已经会说它缺什么。

### 代价

- 创作者仍然要手写外貌 / 服装 —— 本 ADR 刻意不替他写。
- 重名要人来决定，不能一键了事。

### 明确不做

- **角色原型库**（20+ 预设 × 四件套 × 「应用至画布」，T-024）——
  TASK-083 §3 的建议是等有使用数据再说，本 ADR 维持该建议。
  预设库的正确粒度取决于创作者实际怎么用角色，而我们现在没有那份数据。
- 从图**推断**档案内容（长相、年龄、服装描述）—— 需要视觉理解，
  且它产出的是猜测而不是设定；创作者的设定才是权威。
