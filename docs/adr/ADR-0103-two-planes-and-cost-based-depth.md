# ADR-0103：开发流程分两个面，深度按代价判 —— 不是继续加规则，是把规则分层

- 状态：**Accepted**（2026-09-08，实施 Agent 依 AGENTS.md §1 自行 Accept）。
  这是**技术合同**（Agent 工作流与记录规则）：不动付费边界、不碰用户数据、
  不改任何一条来自 AGENTS.md 或既有 ADR 的权威规则 —— 只改它们**住在哪里**、
  以及**深度怎么判**。
- 关联：[TASK-144](../tasks/done/TASK-144-dev-workflow-v03-two-planes.md)（本 ADR 的实施卡）·
  [ADR-0101](ADR-0101-idea-intake-level-and-milestone-gate.md)（Idea Intake 与六层，
  本 ADR **细化其决策 6**，不取代）· [ADR-0083](ADR-0083-docs-partitioned-by-completion.md)
  （目录即状态）· [ADR-0087](ADR-0087-document-lifecycle-and-default-agent-context.md)
  （文档生命周期）· [ADR-0088](ADR-0088-traceability-and-requirement-fulfillment-review.md)
  （四闸审查）· ADR-0080 / ADR-0081（测试归属与审查协议，**一条不改**）

## 1. 背景：规则不缺，规则太多且都堆在入口

产品负责人 2026-09-08 通读 dev-workflow v0.2 之后的判断：

> 「内容本身大约 80% 都合适。现在最大的问题不是缺规则，而是规则已经太多，
> 需要重新分层。」
> 「不是继续增加开发规则，而是把现有规则压缩成「人类控制面」和「Agent 执行面」
> 两层，并让 QUICK / STANDARD / DEEP 自动决定需要展开到哪一层。」

两个可量化的成因：

**成因 A —— 入口正文承担了七种治理。** v0.2 的 `SKILL.md` 381 行，一份正文同时是
路由器 + 产品需求治理 + 架构治理 + 文档生命周期 + 测试治理 + 审查治理 + Git 流程
治理，后半段已经具体到 `lifecycle_check.py`、`gen_docs_status.py`、auto-push 子命令
与 merge gate。**每一次开发任务都要把这 381 行读一遍**，其中大部分与手上这件事无关。

**成因 B —— 深度按代码规模判，会在两个方向同时判错。** v0.2 的分档判据是「单模块 /
多文件 / 跨模块 / schema / 高不确定性」，混了两种不同量纲：

| 实际的活 | 按规模判 | 应该是 | 判错的代价 |
| --- | --- | --- | --- |
| 挪一个按钮，碰 6 个文件 | 「大」→ 建卡 + 影响分析 + 治理 | QUICK | 一个可逆的展示改动付了 DEEP 的流程税 |
| 字段 `nullable → required`，3 行 | 「小」→ 直接改 | **DEEP** | 存量 null 在下一次读取时炸；回滚要写反向迁移 |

第二行是致命的那一种：**LOC 少不等于任务小。**

**成因 C —— 人类审阅层和 Agent 执行层没分开。** v0.2 已经在影响分析上做对了一半
（只输出「要改 / 明确不动」，明说目的是定范围不是造报告），但任务卡仍然允许承载
「哪个函数怎么改、哪个文件加什么 class、API 用什么参数、DB 哪列怎么处理」。
后果不是文档多几行，而是**整张卡没人审**：三条要审的判断被埋进三十条不用审的步骤里。

## 2. 决策

### 决策 1：三条最高原则，其余全部为它们服务

1. **复杂度增加可以加分析深度，不自动增加文件种类。**（v0.2 已有，升为第一条）
2. **控制面与执行面分开。**（新）
3. **深度管流程重量，影响面管验证重量。**（v0.2 已有，措辞收紧为「各判各的」）

### 决策 2：四层，前三层人审，第四层是 Agent 的工作记忆

| 层 | 回答什么 | 住在哪 | 谁读 |
| --- | --- | --- | --- |
| **Requirement** | 用户最终看到什么行为 | `docs/requirements/REQ-*.md` | 人 |
| **Design** | 系统用什么结构解决它 | ADR + [当前架构合同](../current-architecture.md)；普通选择写卡内结论 | 人 |
| **Task** | 哪几个可验证切片完成这个 Design | `docs/tasks/*/TASK-*.md` | 人 |
| **Execution detail** | 改哪个文件、哪个函数、哪个字段、按什么顺序 | 会话记忆 / `.claude/tmp/` | **只有 Agent** |

**判据一句话：这一行变了，人的判断会跟着变吗？** 会 → 控制面；不会 → 执行面。

**Design 不是新文件种类** —— 它落在已有的 ADR 与当前架构合同上。这一点是本决策
能成立的前提：ADR-0101 §4 已经裁决过「给每层建一种新记录类型」，本 ADR 不重访。

执行细节按 AGENTS §26 属 C 类一次性产物：**任务结束即删**，有长期价值的先提炼成
卡上的结论几行 / 一条 ADR / 合同里的一行，再删原件。

### 决策 3：深度 = `max(U, I, R, C)` —— 按错误决策的代价判，不按代码量

| 变量 | 问什么 |
| --- | --- |
| **U** 不确定性 | 我现在说得出验收判据和它的证据吗 |
| **I** 影响面 | **错了会波及谁**（不是改了几个文件） |
| **R** 可逆性 | 撤销要做什么动作 |
| **C** 合同变更 | 动了 schema / API / 持久化格式 / 公共接口 / 架构边界 / 外部合同吗 |

**取最高，不平均、不投票。** 理由是这四个变量各自都能单独毁掉一次改动：需求理解
错了、波及面估小了、撤不回来、把别人的合同改了 —— 任何一个成立，剩下三个再干净
也救不了。刻度表、边界情形与「拿不准取高档」的代价论证在
[references/depth.md](../../.claude/skills/dev-workflow/references/depth.md)。

**R 是四个里唯一可以主动改变取值的** —— AGENTS §1「回不了头是缺陷」本来就要求
先把不可逆性消掉（带版本新路径 / 可回滚旧数据 / 加法字段 / 软删除），
**消掉之后按降下来的档走**。

**深度与验证强度仍然分开，而且分得更干净了**：深度（四变量取最高）决定**成果物**；
**验证与审查只看 I 一个变量**（AGENTS §20 / ADR-0080 / ADR-0081，一条不改）。
所以「持久化里改一行」= QUICK 流程 + backend/studio 两个域的验证 + 一轮审查。

### 决策 4：Decision Brief 是卡头，不是新文件

案件控制面（为什么出现这个案件 / 有多重 / 会产生什么 / 做完没有）**必须有一个
落点**，否则 ADR-0101 决策 6 那三行「说过就丢」。落点是**已经存在的任务卡头部**，
比 v0.2 **只多两行**：

```
- 起因：<用户原话 / 缺陷现象 / 上一条决策> · 闸：放行（第 2 问，阻塞 TASK-106）
- 类型：… · 深度：DEEP（C=DEEP：改持久化格式）
- 成果物：REQ-009 · ADR-0104 · 本卡 · 提交          ← 新增
- 关联 Requirement：… # 或 技术目标：…
- 架构约束：CA §…
- 状态：…（写「交付了什么」，不得与所在目录矛盾）
```

- `起因` 是 `ORPHAN_TASK` 的人类版本：机器查的是有没有追溯句柄，人问的是这张卡
  为什么存在。
- `成果物` 是**防文档蔓延的闸**：开工时申报「本卡 + 提交」，收口时冒出三份新文档
  就是范围扩散，当场看得见。
- **`Done` 状态不进 Brief** —— 目录即状态（ADR-0083）。卡上既有的 `状态：` 行写的
  是「交付了什么」，`lifecycle_check` 只保证它与目录不矛盾。
- **QUICK 没有卡**，它的 Brief 就是提交信息那两行。

**这是对 ADR-0101 决策 6 的细化，不是取代**：Idea Intake 的产出**仍然**是对话里
三行、仍然不产生新文档；本 ADR 只规定 —— 当案件重到已经要建卡了，那三行就写在
卡头，而不是留在聊天记录里。

### 决策 5：入口正文只说「什么时候想什么」，六个环节

`Intake → Classify → Depth → Contract → Execute → Close`。条件触发的细则全部
下沉 `references/`（新增 `depth.md`，其余沿用）。

**旧步号不回改，改的是解析方式。** `docs/adr/` 是历史证据（ADR-0087），里面的
「dev-workflow 第 9 步」永远不会改；`SKILL.md` 末尾因此留一张「旧步号 → 新环节」
映射表。**当前事实类**文档里的旧步号则必须就地改（AGENTS.md、
`docs/current-architecture.md`、auto-push Skill）—— 当前事实过期即缺陷。

## 3. 代价（已接受）

- **多一层间接。** 具体细则从「读入口就看到」变成「按条件去 reference 里看」。
  换掉的是每次任务都读 381 行；代价是偶尔要多打开一份文件。这个交换在
  AGENTS §25「默认只加载当前事实」下本来就是既定方向。
- **四变量比一句话难判。** 判一次要问四个问题而不是「大改还是小改」。压制手段是
  **判错的代价不对称**（判高了多付一张卡，判低了付的是脏数据），因此规则写死
  「拿不准取高档」。
- **`起因` / `成果物` 是两行新 ceremony。** 只对 STANDARD/DEEP 生效，QUICK 一行
  不加。如果实测下来这两行变成了填空题而不是判断，就删掉它们（可逆，按 AGENTS §1
  直接做）。
- **「不写执行细节」判不了。** 这条不加机器检查（AGENTS §26「判不了的不判」）：
  区分「这一行有没有审阅价值」需要语义判断，误杀的代价比漏报大。它靠审查第 1 闸
  与收敛检查兜底。
- **映射表本身是一处冗余。** 它存在只是因为历史 ADR 不能回改。等到某天没有活跃
  文档再引用旧步号，可以删掉那一节。

## 4. 被否掉的方案

| 方案 | 为什么否 |
| --- | --- |
| 新建 `docs/decision-briefs/DB-NNN.md` 作为控制面 | 就是 ADR-0101 §4 裁决过的「给每层建一种新记录类型」，且会立刻变成第二份 PRD。卡头已经是这个位置 |
| 把 Design 单独立成 `docs/design/DESIGN-NNN.md` 一类记录 | 同上。ADR 记 WHY、当前架构合同记 WHAT IS TRUE NOW，两者合起来已经是 Design 层 |
| 深度改成打分（四个变量各 1–3 分求和） | 求和会让「三个 QUICK 压过一个 DEEP」，而这四个变量**任何一个单独成立就足以毁掉一次改动**。取最高是唯一正确的聚合 |
| 保留 v0.2 的步号，只搬内容 | 六环与十步不是一一对应（0/0.5 合成 Intake，8/9/10 合成 Close），硬保号会让编号骗人 |
| 给「不写执行细节」加 lifecycle_check 规则 | 判不准。一条正当的结论（「改用 pathlib，因为 CA §5.4」）和一条执行步骤长得很像 |
| 顺手把卡上的 `状态：` 行删掉（它与目录重复） | 那一列写的是「交付了什么」，目录只答「做完没有」，`test_plan_status_matches_folder.py` 的 docstring 已经论证过不删。**范围外，不顺手改**（AGENTS §17） |
