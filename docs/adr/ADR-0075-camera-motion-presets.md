# ADR-0075：运镜预设是**文本模板**，落到镜头上就与预设脱钩

- 状态：**Accepted（2026-08-18，实施 Agent 依 CLAUDE.md「ADR 的 Accept 权」自行 Accept）**
  —— 架构 + 版本语义，属技术范畴；**不涉及付费口径**，**不不可逆动用户数据**
  （应用预设写的是镜头上一个既有的可编辑字段，可以直接改回去）。

## 背景

**实测证据**：真实项目 60 条镜头，`cameraMotion` 填充率 **0/60**。
TASK-078 §2.1 已经把输入口补上了（在此之前它在 HTTP 边界被 `_parse_shots` 丢掉），
但**逐镜手打自由文本这条路走不通**这一点没有变 —— 60 次从零想一句运镜描述，
结果就是一次都不写。

目标产品用「我的工具箱」预设：左弧滑行 / 360 旋转展示 / 瞳孔拉近 / 机械臂视角…

TASK-083 §2 给 ADR-B 列了四个必答问题，其中最难的一个是：

> **预设改了，已经用过它的镜头怎么办（这是版本语义问题，最容易做错）？**

## 决策

### 决策 1：预设是**文本模板**，应用即**复制文本**，不留引用

```
镜头.cameraMotion  ←  预设的文本（一次复制）
```

镜头上**不存**预设 id。应用之后，这一镜与那个预设**再无关系**。

这一条同时回答了那个最难的问题：**预设改了，已经用过它的镜头什么都不会发生。**
而这正是想要的语义 —— 一句已经写进镜头的运镜描述是**创作者当时的决定**，
后来有人改了模板不该追溯改写他的镜头。反过来的设计（存 id、渲染时解引用）会让
改一个模板悄悄改掉 60 个镜头的画面意图，那是本仓库最不能接受的那类写入。

**代价如实写出**：没有「哪些镜头用了这个预设」这个查询。它需要引用才能回答，
而引用会带来上面那个追溯改写的问题。今天没有人要这个查询；真要时再加是加法。

### 决策 2：预设是**内置常量**，不是新的登记表

TASK-083 §2 问「项目级还是账户级」。答案是**都不是**：既然应用即复制文本
（决策 1），预设本身就不需要持久化，**不新增任何 schema、任何迁移、任何文档**。

一份内置清单 + 复制文本，就把填充率从 0/60 变成可用。**创作者自定义预设**
留到有人真的抱怨内置不够时再做 —— 那时它是一张新登记表，是加法。

### 决策 3：文本是**可编辑的起点**，不是不可改的枚举

复制进去之后 `cameraMotion` 仍然是那个自由文本字段，创作者可以改。
预设的作用是消除「从零想一句」这个成本，不是把运镜变成下拉框 ——
运镜本来就不是闭集。

### 决策 4：应用预设**不覆盖已有内容**，先问

`cameraMotion` 已经有文字时，应用预设是一次**覆盖用户内容**的写入
（AGENTS.md 第 13 条）。做法：**追加而不是替换**，或者由创作者明确选择替换。
默认动作是**追加**——它可逆（删掉那一行就回去了），而替换会丢掉他写过的话。

### 决策 5：预设文本必须**自足**

外部工具看不到我们的项目数据，所以预设文本里不能出现只有本项目才知道的名字
或 id（与 `image-prompt-director` 的既有要求同一条）。
「镜头从左向右缓慢弧形滑过」是自足的；「像第 3 镜那样推」不是。

## 后果

### 好的

- 0/60 这个数字有了一个**一次点击**的解法。
- 零 schema、零迁移、零新文档。
- 「预设改了怎么办」这个最容易做错的问题，被**设计成不会发生**。

### 代价

- 没有「哪些镜头用了这个预设」的查询（决策 1 已写明理由与将来的加法路径）。
- 内置清单要有人维护；它是源码常量，改它要发一次版本。

### 明确不做

- **特效库 / 风格库**（T-022 / T-023）—— 与运镜不同：特效与风格**会进生成**
  （风格参考图是 `model-input`），所以它们需要的是资产与版本绑定，
  不是一段可复制的文本。那是另一个 ADR，且应该等 ADR-0071 的多图路线有真实
  provider 之后再设计。
- **自定义预设**（创作者自建）—— 见决策 2，等使用数据。
