# ADR-0068：连续修改链 —— 中间批次定向验证，链尾统一全量

- 状态：**Accepted**（产品负责人 2026-08-13 下发）
- 日期：2026-08-13
- 范围：**只改验证节奏**，不改任何验证项的标准。产品代码、CI 必跑项与最终验收
  要求全部不变。
- 覆盖 / 修订：
  [ADR-0060](ADR-0060-risk-based-local-commit-gate.md)（风险分级本地 commit gate）
  的「高风险改动必须跑全量」在**连续修改链的中间提交**上的应用方式；
  AGENTS.md 第 20 条与 CLAUDE.md 实施纪律同步。
- 实施任务：[TASK-076](../tasks/TASK-076-continuous-chain-gate.md)

## 背景

TASK-072 批次一是一次真实的教训：批次内跑了 **23 轮 codex 审查**，每一轮修完都要
跑一次全量 pytest（本机约 6.5–7.5 分钟）+ 全量前端。全量测试在这条链上的作用是
**重复确认同一件事**——因为每轮改动都很小，而定向测试已经覆盖了它。

更糟的是它改变了行为：全量太贵，于是倾向于把多个批次攒成一个提交再验一次；
而 ADR-0066 §0.2 刚刚要求**每个批次单独提交**。两条规则互相拉扯，最后总有一条
被牺牲。

同时必须承认全量的真实价值：它抓的是**跨批次的相互作用**——批次一改了状态枚举，
批次三的门槛代码读它；定向测试按定义看不到这种耦合。

结论不是「少测」，而是**把全量放在它真正能发现问题的位置**：链的末尾。

## 决策

### 决策 1：连续修改链必须由用户明确授权

「连续修改链」是一次**被明确授权**的、跨多个任务或批次的连续实施。它不是默认
工作方式：没有用户的明确授权，每一次提交仍按 ADR-0060 的原规则执行。

授权时必须列出：

1. **连续的任务 / 批次清单**（例如 TASK-072 批次二 → 批次三 → TASK-073）；
2. **最终全量检查点**在哪里（哪一个提交之后必须跑全量）。

清单与检查点写进任务卡；**没有写下来的链不算被授权**。

### 决策 2：中间批次的执行序列

```
实现 → 定向测试 → Codex review loop → 修复时定向回归 → Codex 通过 → 立即独立 commit
```

- **定向测试**：本批次新增与直接触及的测试文件，必须全绿。
- **Codex review loop**：**不放松**。中间批次照样要审到 pass（或只剩 P3/P4）。
  这是本 ADR 敢于推迟全量的**唯一理由**：独立审查看的是 diff，而 diff 是完整的。
- **修复时定向回归**：审查修复后重跑定向测试，而不是全量。
- **立即独立 commit**：审查一通过就提交，不攒。

### 决策 3：中间提交不跑全量 pytest / 全量前端

中间提交**跳过**全量 pytest 与全量前端。**仍然跑** ruff（check + format）与
commit gate 的 diff 检查——它们是秒级的，没有任何理由推迟。

### 决策 4：链尾统一跑一次完整验收

整条链结束后，统一跑一次：

```
全量 pytest + 全量前端 + ruff + 最终验收（任务卡的验收标准）
```

这一次是**硬门槛**，不是形式：它要抓的正是中间批次之间的相互作用。

### 决策 5：最终全量失败时的回路

```
修复 → 定向测试 → Codex 复审 → 修复提交 → 重新跑全量
```

**重新跑全量**，不是「只跑失败的那几个」。一次失败说明链内有跨批次耦合没被看见，
那种问题不会只表现在一处。

### 决策 6：push / merge / 交接 / 人工验收之前必须完成最终全量

这四件事任何一件之前，最终全量必须已经跑完并全绿。**未完成最终全量的链不得交付**
——它的状态是「中间态」，而中间态不进入别人的视野。

### 决策 7：`MOTV_CONTINUOUS_CHAIN=1`，且没有永久开关

规则必须真实生效，因此 commit gate 认一个**显式环境变量**：

| 项 | 内容 |
| --- | --- |
| 变量 | `MOTV_CONTINUOUS_CHAIN=1` |
| 何时可用 | **仅**用户已授权的连续修改链的**中间**提交 |
| 效果 | 跳过全量 pytest / 全量前端；**仍跑** ruff 与 diff 检查 |
| 最终检查点 | **不设**该变量 → 恢复 ADR-0060 的原高风险 full gate |
| 平台 | PowerShell 与 Bash gate **行为必须一致**（ADR-0062 决策 3） |
| 单元测试 | `commit_gate_policy` 必须有覆盖该模式的单测 |
| **不提供** | **任何永久关闭测试的全局开关**——变量是**逐次**设置的，不写进 settings，不写进 profile |

最后一条是本决策的要点。一个可以永久设置的「跳过测试」开关，一周之内就会变成
默认状态，然后没有人记得它开着。逐次设置意味着每一次跳过都是一个**当场的、
可见的决定**。

## 后果

### 正面

- 每个批次单独提交（ADR-0066 §0.2）不再与验证成本冲突。
- 全量测试从「每轮重复确认同一件事」变成「在唯一能发现新问题的位置跑一次」。
- Codex 独立审查在中间批次**完全不放松**——质量的主要保障没有被动过。

### 代价与风险

- **中间提交的历史里存在未经全量验证的点。** 如实记录：链中间的某个提交，
  单独 checkout 出来可能是红的。这是本 ADR 用来换取「批次可独立提交」的代价，
  并由决策 6（交付前必须完成最终全量）兜住。
- **链越长，最终全量失败时的定位成本越高。** 因此决策 1 要求授权时就写下清单：
  一条没有边界的链等于没有检查点。
- **依赖 Codex 可用。** 审查者不可用时，中间批次**不得**用本 ADR 的节奏提交——
  那会同时失去两道门。此时回落到 ADR-0060 原规则，并如实报告。

## 明确不做

- 不放松任何验证项的标准，只改它们跑在哪里。
- 不放松 Codex 独立审查（决策 2）。
- 不提供永久性的测试跳过开关（决策 7）。
- 不改 CI：CI 永远跑全量。
- 不改 ADR-0060 的风险分级表本身。

## 补记：降级审查模式（2026-08-13 → 2026-08-18）

产品负责人 2026-08-13 批准了一个**有时限的降级审查模式**，因为 codex 触到
workspace spend cap，**在 2026-08-18 之前不可用**，且 `claude` CLI 未安装
（本 ADR 决策 2 与「明确不做」原本要求此时停下）。

### 批准的替代安排

| 项 | 内容 |
| --- | --- |
| 审查者 | **一个全新的、独立的 Claude Opus 会话**（无本次实施的上下文） |
| 适用 | **每一个**中/高风险检查点，**逐个**都要 |
| 记录 | **必须显式注明审查者已降级**，在提交信息与任务卡中都要 |
| 等价性 | **不等于**最终的 codex 批准 |
| 债务 | **所有高风险改动在 2026-08-18 之后、最终集成 / 发布之前，必须补一次 codex 复审** |
| 底线 | **不得在没有独立审查检查点的情况下使用连续修改链** —— 降级的是审查者，不是「有没有审查」 |

### 为什么这仍然算一道门

本 ADR 决策 2 敢于把全量测试推迟到链尾，唯一的理由是**独立审查看的是完整的 diff**。
那个理由不依赖审查者是哪个模型，只依赖它**没有实施者的上下文**——一个全新会话
满足这一点。失去的是**跨模型独立性**：同一个模型家族会共享盲区，因此它发现不了的
东西与实施者发现不了的东西相关性更高。

这正是它**不等于** codex 批准、并且必须留下复审债务的原因。
