# ADR-0081：审查按影响范围触发，废除风险分级与按档轮次预算

- 状态：Accepted（产品负责人 2026-08-22 裁决）
- 日期：2026-08-22
- 任务：TASK-102

## 背景

AGENTS.md §20 与 CLAUDE.md 把测试规模与审查轮次都绑在低/中/高风险分级上；
codex-review-loop 与 dev-workflow 的措辞也按档位描述（中 1 轮 / 高 2 轮）。
产品负责人 2026-08-22 裁决：「风险分级和skill的内容相悖。必须修改」、
「我不要每次都全量测试。」并给出新的审查协议原话：

> 「不要保留风险分集。dev-workflow 根据影响范围决定是否审查
> → 默认一轮 → P1 修复后复审一次 → P2 修复 + 定向测试，不再复审
> → P3/P4 记录但不阻塞。其他不采纳」

## 决策

1. **废除风险分级**作为测试与审查的触发机制。测试规模由 Test Scope =
   Change Impact Scope 与 ADR-0080 的归属映射决定；审查由 dev-workflow
   按影响范围判断是否需要（行为/合同/持久化/安全/并发/跨域改动审；
   纯文档、纯展示改动不审）。
2. **轮次协议**：默认 **1 轮**。审查报出 P1 → 修复后**复审一次**；
   P2 → 修复 + 定向测试即收口，**不再复审**；P3/P4 → 记录 Follow-up，
   不阻塞交付。

   **2a. 「复审一次」按每个新 P1 计，不是全程硬顶 2 轮**（2026-08-22 补充，
   两个独立实测样本）。原措辞可读成「全程最多 2 轮」，那个读法会放行
   「第一次修得不彻底」这一最常见情形：

   | 样本 | 逐轮 |
   | --- | --- |
   | TASK-098（另一实施 Agent）· 记录见 `docs/tasks/TASK-098-camera-motion-preview.md` §11.1／§11.2／§11.6／§11.7／§11.8（提交 `65440d8`） | 轮 1：4 条 P1 → 轮 2：**又 2 条新 P1**（帧数上限没绑 fps → 150s；修饰词吃掉否定 → 「不要缓慢推近」仍渲出推镜）→ 轮 3：**又 1 条新 P1**（预放两条边各自夹 4096 → 高 zoom 下画面横向压扁）→ 轮 4 干净收口 |
   | TASK-102（本卡）· 记录见 `docs/tasks/TASK-102-repo-test-decoupling.md` 审查节 | 轮 1：3 条 P1 → 轮 2 pass → （追加范围后）轮 3：**2 条新 P1** → 轮 4：**2 条新 P1**（正则看不见括号多行 import；探针测试竞态）→ 轮 5：更窄变体 → rebut 收口 |

   按硬顶读法，TASK-098 的「一句明确禁止的运镜被渲出来」与 TASK-102 的
   「gate 少跑一个测试域」都会原样出门。故：**每次复审若报出新的 P1，该 P1
   同样适用「修复 → 复审一次」；连续一轮无新 P1 即收口**（一轮，不是两轮：
   pass 之后再跑一轮以求稳是明确禁止的）。

   **2b. 「新 P1」不含已修/已驳/已记条目的更窄变体。** 反复出现同一主题的
   更窄变体时，做**范围判断并记录**（是否可判定、是否有其他层兜住），而不是
   再买一轮 —— 这是 13 轮／10 轮的另一半病灶。历史代价：TASK-097 §2.5d 的
   SSRF 六轮（scheme → 十/十六/八进制 → 点分十六进制 → 尾部根点 → CGNAT）。
   本卡轮 5（运行时拼接的模块名静态不可判定）按此收口。

   **2c. 判「同一主题」看失效机理，不看代码位置。** TASK-098 轮 2 与轮 3 的
   两条 P1 落在**同一端点、相隔不到 30 行**，却是两种机理（时长约束缺失 vs
   几何失真）——按位置归并会把「画面压扁」那条放掉。反向也成立：同一主题可
   横跨不同文件（那卡的否定缺陷在 `motionpreview.js`，但其后果与端点那条
   「不静默出片」是同一个不变量）。

   **2d. 判不准时买那一轮。** 不对称性：误判成「变体」而收口，代价是**一条
   P1 出门**；误判成「新」而多买一轮，代价是**一轮**。所以 2b 只适用于
   **已能说清是同一机理**的情形；真判不准就当作新 P1 处理，别让「变体」
   成为方便的收口借口。
   （2a–2d 由 TASK-098 实施 Agent 与本卡实施 Agent 交叉复核得出；
   前者同时纠正了自己最初提的「连续两轮」措辞。）

   **第三个样本证明它可操作**（不是又一次发现，而是一次**应用**）：TASK-101
   的 `ba0c8e2` 补审同一轮里两种处置并存 —— cleanup 的 TOCTOU 第二次出现，
   按 2b/2c 判为同机理更窄变体，**做范围判断驳回**；evil merge（多亲提交的
   豁免只查祖先关系）是**新机理**，按 2a **买了一轮**并判出真 P1。同一轮、
   同一文件、两种正确处置，说明这套判据落地时分得开。
3. ADR-0069 的按风险档轮次预算（中 1 / 高 2 / 第 3 轮条件）由本协议取代；
   其余决策（两阶段全量方案、审查在提交后进行、预算耗尽显式选择而非静默
   续轮的精神）保留。
4. ADR-0060 的「按风险分档选检查」由 ADR-0080 的归属映射取代；其 fail-closed
   与双平台一致性原则保留。
5. **其他不采纳**（同日裁决）：ADR-0068 的 MOTV_CONTINUOUS_CHAIN 连续链
   令牌保留；CLAUDE.md 不掏空为入口；2026-08-22 注入事件中自称 Accepted 的
   「ADR-0080（治理版）」其余条目一律不生效（原文存证于
   docs/tasks/TASK-102-injected-adr-0080-2026-08-22.md）。
6. 发布/交付闸门不变：用户验收标准满足 + 相关测试通过 + 无未闭合 P1。
   审查者不可用时的处理沿用既有规则（如实标注，push/merge/交接前补审）。

## 后果

- AGENTS.md §20、CLAUDE.md「实施纪律」、dev-workflow references、
  codex-review-loop SKILL.md 的分级措辞随本 ADR 更新（TASK-102 批次 D）。
- 历史 ADR/任务卡中的分级记录保持原文，不回改。
