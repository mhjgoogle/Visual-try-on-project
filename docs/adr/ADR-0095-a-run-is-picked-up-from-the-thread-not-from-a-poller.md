# ADR-0095：还在跑的那一轮，从线程里认出来，不从轮询器里认

- 状态：**Accepted**（2026-09-04，实施 Agent 依 AGENTS.md §1 自行 Accept ——
  这是纯技术决策：机制形状、身份来源、失败语义）
- 关联：[REQ-004](../requirements/REQ-004-three-pane-shell-and-agent-conversation.md) 判据 6 ·
  [TASK-106](../tasks/active/TASK-106-frontend-run-path-and-legacy-endpoint-retirement.md) §4 ·
  [ADR-0089](ADR-0089-conversational-agent-write-path.md) 决策 2b（落地只能发生在浏览器）·
  [ADR-0064](ADR-0064-ai-director-operationalization.md) 决策 6（不可用就说不可用）

## 背景

后端的异步面 2026-08-25 就齐了：`X-Motv-Async: 1` → `202 {run_id}`、
`GET /api/runs`、`GET /api/runs/<id>`、cancel / confirm / submit。
**缺口全在前端**，而且不是一次接线，是一个机制：

- `GET /api/runs` 与 `GET /api/runs/<id>` 在 `src/services/` 里**零调用点**
  （唯一那处是 `POST /api/runs/<id>/cancel`）；
- 一轮对话的等待活在**那个标签页的内存里**。刷新一次，等待没了。

后果不是「少个转圈」。线程是服务端的，所以**问题**还在；**运行**不在。
屏幕上于是是一个没有答案、也没有任何「还在做」迹象的问题 ——
他会再问一遍，而先起的那一轮落地时**没有人在等**（决策 2b：落地只能发生在浏览器），
改动就这么丢了。

## 决策

### 1. 那一轮的身份**从线程本身推出来**，不另存一份

用户那条 turn 携带发送时拿回的 `runId`；服务端 `_conv_reconcile` 用**同一个 id**
写回 Agent 那条。所以：

**两种「还没完事」，而第二种才是常见的那一种**：

| # | 形状 | 它长什么样 |
| --- | --- | --- |
| 1 | **问了，还没答** —— 用户那条 turn 的 `runId` 没有配对的 Agent turn | 那一轮还在跑（或刚刚才结束） |
| 2 | **答了，改动却没落地** —— Agent turn 带着 `edits`，却**没有 `applied` 回执** | **关掉标签页就是这个样子**：run 在服务端跑完了，答案被折进线程，而它提议的改动没有任何浏览器落过 |

第 2 种是 codex 轮 2 报出来的 P1。把「有一条 Agent turn」读成「落地已经完成」，
是**从一件不能证明它的事上做推断** —— 与决策 2 里「终态 = 没事可做」是同一种错，
代价同样是**静默且永久**地丢掉那些改动。

两个答案都来自线程**已经带着的东西**：发送时拿回的 `runId`，与浏览器落地之后写回的
`applied` 回执。不新增「pendingRunId」这类字段 —— **多一份账就多一处漂移**，
而这里漂移的表现恰好是「它明明还没落地，界面说完事了」。

**宁可重落，不可丢失。** 回执没存下来会让一条已经落过的 turn 看起来没落过，于是被再落
一次 —— 那产生的是创作者文档的**又一个版本**（什么都没被覆盖，AGENTS.md 第 13 条）。
丢一次改动是静默且永久的，多一个版本是看得见、退得回的，所以这个平局刻意这么破。

推出来的是**候选**，不是结论：线程读回来那一刻它可能刚好结束了。只有
`GET /api/runs/<id>` 能回答，所以画任何东西之前先问一次。

### 2. **两个**答案，不是三个 —— 终态不是「没事可做」

| 后端说 | 做什么 | 为什么 |
| --- | --- | --- |
| `queued` / `running` / `cancelling` | 报状态（「排队中」/「正在想…」），**接着等，然后落地** | 这就是要恢复的那件事 |
| 四个终态之一 | **照样落地** | 线程是在读状态**之前**读的，所以刚结束的那一轮有一条页面从没见过的 Agent turn。把终态当成「没事可做」正好丢掉它的 edits（codex 轮 1 的 P1） |
| **问不到**（超时 / 500 / 断网） | 屏幕说 **「状态未知」**，**一次都不落地** | **问不到 ≠ 没在跑**。说「没在跑」会让他再起一份，而两轮同时改同一份文档。这是 ADR-0064 决策 6 在运行状态上的那一次应用 |

判定因此是一个纯函数 `resumePlan(run)` → `"land" | "unknown"`：**只有问不到才是
`unknown`**。落地本身是幂等的（先重读线程，跳过已有回执的），所以对「刚结束」
和「上周就结束了」都安全。

### 3. 恢复**落地**，但**不起跑**

这条是刻意不对称的，因为两件事的代价不对称：

- **落地必须做。** 答案回来了却没人应用它的 edits，等于改动丢了（决策 2b）。
- **起跑不许做。** 一次能力调用是真实动作（花时间、可能花钱、写作品）。
  刷新时自动来一发，正是 `convroute.test.mjs`「读线程的路径上没有任何起跑代码」
  这条守卫存在的理由。

实现上因此把「等 → 刷新 → 落地 → 回执」抽成 `landRun`（**不含任何起跑代码**），
发送链在它之后自己接 `runRouteFor`；恢复链**止步于** `landRun`。
守卫的名单同时加上 `resumePendingRun` 与 `landRun` —— 一条结构性的不变量，
而不是一句注释。

### 3b. 恢复的判定与顺序住在 `workflow/convresume.js`，不住在 shell 的闭包里

这段逻辑原来长在 `ui/production.js` 的一个闭包里，于是它**只能被源码断言测** ——
拿不到它，就没法真的跑一遍「后端答不上来时屏幕上说什么」。而这条链上每一个错误
都是**静默**的（改动丢了、任务看起来没在跑），静默缺陷恰恰最需要被真的跑一遍。

所以决策与顺序抽成 `resumeThreadRun({ readRun, land, claim, onStatus, … })`，
依赖全部注入；shell 里只剩一个把状态绑上去的适配器，并由守卫钉住
**它不许自己再判一次**（一份影子判定正是「发送时对、恢复时不对」的产生方式）。
它返回 `action: "none" | "claimed" | "unknown" | "landed"`，因为
「什么都没做」和「问不到」在一块不仔细看的屏幕上长得一样 —— 而那正是缺陷本身。

### 4. 一轮只接一次

`ensureConversation` 在**每次渲染之后**都会跑。因此 `resumePendingRun` 在 `await`
**之前**就把 `st.pendingRun` 占住：两次恢复同一轮会轮询两遍、落地两遍。

### 5. 只覆盖对话这条链，不做通用轮询器

本轮不引入「全局运行轮询循环」。理由是 AGENTS.md 第 2 节的
Minimum Necessary Foundation：**不做通用循环，当前用户功能能否安全完成？**
能 —— 对话是唯一一条「运行结果必须回到浏览器才能落地」的链，其余长任务
（渲染 / 混音 / 生成）的产物由后端自己写盘，刷新之后从文件读得回来。

因此 TASK-106 的另外两半 —— 16 处同步长调用改走 `run_id`、`/api/agent/*` 创作端点
退役 —— **仍然开着**，只是不再挡着「刷新不丢」这条用户可见的承诺。

## 代价（已接受）

- 恢复只在**进入这一页**时发生。他停在另一页时那一轮照跑，但要等他回来才落地 ——
  比起「永远不落地」这是严格的改进，而做成后台常驻循环属于决策 5 里推迟的那部分。
- `landRun` 的超时（180s）仍在。超时之后线程里已有答案（服务端折进去的），
  只是 edits 要等下一次进入这一页才落 —— 与超时前的行为一致，不是新缺口。
